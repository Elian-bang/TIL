# NoSQL — Elasticsearch · Redis · MongoDB

## 30초 요약

- **역색인**: RDB 인덱스는 *행 → 값*, ES는 **값(단어) → 그 단어가 든 문서 목록**. 그래서 전문 검색이 빠르다. RDB의 `LIKE '%키워드%'`는 인덱스를 못 탄다 — **이게 ES를 쓰는 첫 번째 이유**
- ES의 **`text` vs `keyword`**: 분석되어 검색용 / 분석 안 되어 **정확 일치·집계·정렬용**
- ES는 **Near Real-Time**(기본 1초 refresh), **트랜잭션·조인 없음**, **업데이트가 사실상 삭제 후 재색인**
- **Redis는 싱글 스레드**로 명령을 처리한다 → `KEYS *` 같은 O(n) 명령이 **서버 전체를 멈춘다**
- 판단 기준 한 줄: **정합성이 생명인 원장은 RDB, 양이 많고 조회 패턴이 다양한 이력·검색은 NoSQL**

## 원리 — 왜 그런가

### 2-1. NoSQL이 왜 나왔나 · 4분류

**RDB가 못 하는 것이 생겼기 때문이다.** 정확히는 세 가지.

1. **수평 확장** — RDB는 조인과 트랜잭션 때문에 여러 장비로 쪼개기 어렵다. 스케일 업(더 좋은 장비)에 의존
2. **스키마 유연성** — 컬럼을 추가하려면 ALTER TABLE. 대용량 테이블에서는 위험한 작업
3. **특수 접근 패턴** — 전문 검색, 시계열, 그래프 탐색은 RDB의 B+Tree로는 비효율

| 유형 | 대표 | 데이터 모델 | 쓰는 자리 |
|---|---|---|---|
| Key-Value | **Redis** | 키 → 값 | 캐시, 세션, 분산락, rate limit |
| **Document** | **Elasticsearch**, MongoDB | JSON 문서 | 유동적 스키마, **검색·집계** |
| Wide-column | Cassandra, HBase | 행 + 동적 컬럼 | 시계열, 초대용량 쓰기 |
| Graph | Neo4j | 노드 + 엣지 | 관계 탐색 |

**CAP 정리** (한 줄로)
> 분산 시스템에서 **네트워크 분할(P)은 선택할 수 없는 전제**다. 그래서 실제 선택은 **분할이 일어났을 때 일관성(C)을 지킬 것인가, 가용성(A)을 지킬 것인가** 둘 중 하나다.
- 과금·결제 → **C** (틀린 값을 주느니 에러를 준다)
- 발송 통계 조회 → **A** (조금 늦은 값이라도 응답한다)

**RDB vs NoSQL을 가르는 질문은 하나다**:
> *"조인과 트랜잭션이 필요한가, 아니면 쓰기 처리량과 유연한 스키마·다양한 조회가 필요한가."*
- 돈·과금·계약처럼 **정합성이 생명**인 원장 → **RDB**
- 로그·이력·검색처럼 **양이 많고 조회 패턴이 다양한 것** → **NoSQL**

⚠️ **"NoSQL이 더 좋다"는 프레임 자체가 틀렸다.** 정답은 **원장은 RDB, 검색·집계는 ES처럼 둘을 나눠 쓰는 것**이다.

### 2-2. Elasticsearch

**정체**: Lucene 기반 **분산 검색·분석 엔진**. JSON 문서를 저장하고 **역색인**으로 검색한다.

#### (1) 역색인 — 왜 빠른가

RDB에서 `WHERE content LIKE '%예약%'` 이 왜 느린지부터. 인덱스는 **컬럼 원본 값의 정렬**이다([DB 인덱스](../database/b-tree-index.md) §2-6). 앞이 와일드카드면 **시작점을 찾을 수 없다** → 전체를 읽으며 문자열 비교. 100만 행이면 100만 번.

**역색인은 방향을 뒤집는다.**
```
RDB 인덱스 :  문서1 → "예약 발송이 실패했습니다"
역색인     :  "예약"   → [문서1, 문서7, 문서93]
             "발송"   → [문서1, 문서2, 문서7, ...]
             "실패"   → [문서1, 문서5]
```
검색은 **단어로 목록을 바로 꺼내는 것**이 된다. 문서가 100만 건이든 1억 건이든 **"예약"이라는 키 하나를 찾는 비용**이다.

**대가는 색인 시점에 치른다.** 문서를 넣을 때 **애널라이저**가:
1. **토크나이즈** — 문장을 단어로 쪼갠다 (한국어는 형태소 분석기, 예: Nori)
2. **정규화** — 소문자화, 불용어 제거, 어간 추출
3. 그 결과를 역색인에 넣는다

→ **쓰기가 비싸고 읽기가 싸다.** RDB와 반대 방향의 거래다.

#### (2) `text` vs `keyword`

| | `text` | `keyword` |
|---|---|---|
| 애널라이저 | **통과함** (토큰으로 쪼개짐) | **통과 안 함** (통째로 저장) |
| 쓰임 | 전문 검색 (`match`) | **정확 일치**(`term`), **집계**, **정렬** |
| 예 | 메시지 본문 | 채널 코드, 에러코드, 수신번호 |

**왜 나눠야 하나**: `"010-1234-5678"`을 `text`로 넣으면 `010`, `1234`, `5678`로 쪼개진다. 그러면 **정확히 그 번호를 찾는 것도, 번호별로 집계하는 것도 안 된다.**
→ 실무에서는 **멀티 필드**로 둘 다 둔다: `message`(text, 검색용) + `message.keyword`(keyword, 집계용)

#### (3) 구조 용어 — 헷갈리기 쉬운 것

- **인덱스(Index)** = RDB의 **테이블**에 해당. ⚠️ **DB 인덱스가 아니라 저장 단위**다. 제일 헷갈리는 용어
- **샤드(Shard)** = 인덱스를 나눈 물리 단위. **프라이머리 샤드 수는 생성 후 못 바꾼다** (split/shrink API로 재색인 성격의 작업은 가능)
  → 왜 못 바꾸나: 문서가 어느 샤드로 갈지를 `hash(_id) % 샤드수`로 정하기 때문. 샤드 수가 바뀌면 **기존 문서의 위치 계산이 전부 틀어진다** (Kafka 파티션과 **똑같은 이유**다 — [메시징](../messaging/kafka-and-rabbitmq.md) §2-4)
- **레플리카(Replica)** = 샤드 복제본. 가용성 + **읽기 처리량 분산**. 이건 나중에 바꿀 수 있다
- **매핑(Mapping)** = 필드 타입 정의. 스키마리스처럼 보이지만 **실무에서는 명시적으로 잡는다** (자동 추론이 틀리면 재색인해야 하므로)

#### (4) Near Real-Time — 왜 바로 안 보이나

**색인 직후 검색하면 안 나온다.** 기본 **1초**(`refresh_interval`) 뒤에 보인다. 이유는 Lucene의 구조에 있다.

- Lucene은 데이터를 **세그먼트(segment)** 라는 **불변(immutable) 파일**에 쓴다
- 새 문서는 일단 메모리 버퍼에 쌓이고, **refresh 시점에 새 세그먼트로 만들어져야** 검색 대상이 된다
- 문서마다 즉시 세그먼트를 만들면 파일이 폭증한다 → 그래서 **모아서 1초에 한 번**

**여기서 파생되는 것들:**
- **업데이트가 사실상 삭제 후 재색인이다.** 세그먼트가 불변이니 수정이 불가능하다. 기존 문서를 "삭제됨"으로 **표시만** 하고 새 문서를 쓴다 → **잦은 업데이트에 불리하다**
- 삭제 표시가 쌓이면 **세그먼트 병합(merge)** 이 일어나 실제로 정리된다. 이때 I/O가 튄다
- **대량 색인 시 `refresh_interval`을 늘리거나 끄는 것**이 정석 튜닝이다 (초기 적재에서 몇 배 차이)

#### (5) RDB와 다른 점 정리

- **트랜잭션 없음.** 문서 단위 원자성만. 여러 문서를 묶어 롤백할 수 없다 → **원장으로 쓰면 안 되는 이유**
- **조인 없음.** 필요하면 **색인 시점에 비정규화**해서 합쳐 둔다
- **집계(Aggregation)가 강하다** — 발송 성공/실패율, 채널별·시간대별 추이. RDB에서 `GROUP BY`로 수백만 건을 훑는 것보다 압도적으로 빠르다
- **`from`/`size` 딥 페이징이 위험하다** — `from=100000`이면 각 샤드가 10만+size건을 정렬해서 코디네이터로 보낸다. 대안은 `search_after`

#### (6) ILM — 보존 기간 정책

- **ILM(Index Lifecycle Management)**: hot(활발히 쓰고 읽음) → warm(읽기만) → cold → **delete**
- **시계열 인덱스 전략**: `send-log-2026.08` 처럼 **날짜 단위로 인덱스를 쪼갠다**
  → 오래된 것을 **인덱스 통째로 삭제**할 수 있다. 행 단위 DELETE보다 압도적으로 싸다 (세그먼트 병합도 안 생긴다)
- **제품 정책으로 자주 보이는 형태**: *"발송 상세 내역은 최대 3개월까지만 조회, 이후엔 성공/실패 건수만"*
  → 이런 문구는 대개 **상세 로그를 보존 기간이 있는 별도 스토어에 두고, 집계만 원장에 남기는 구조**라는 신호다
  → RDB로 같은 정책을 구현한 것이 [DB 인덱스](../database/b-tree-index.md) §2-12의 파티셔닝이다. **발상은 같다 — 행 단위로 지우지 말고 덩어리째 버린다**

### 2-3. Redis — 실무에서 자주 물음

#### (1) 왜 빠른가, 그리고 왜 싱글 스레드인가

- **인메모리**라서 빠르다 (1차 이유)
- **명령 처리는 싱글 스레드**다. 이건 한계가 아니라 **설계 선택**이다:
  - 락이 필요 없다 → 락 획득·경합 비용 0
  - 컨텍스트 스위칭 없다
  - **모든 명령이 원자적이다** → `INCR`, `SETNX` 같은 게 그냥 안전하다
  - 병목이 CPU가 아니라 **메모리와 네트워크**라서 멀티스레드 이득이 작다
  - (Redis 6+는 **네트워크 I/O만** 멀티스레드로 처리한다. 명령 실행은 여전히 하나)

**⚠️ 그래서 O(n) 명령이 서버 전체를 멈춘다.**
- `KEYS *` — 전체 키를 훑는다. **운영에서 금지.** 대신 **`SCAN`**(커서 기반, 나눠서)
- `FLUSHALL`, 큰 `HGETALL`, 큰 컬렉션 `DEL` 도 같은 위험
- **한 명령이 100ms 걸리면 그동안 모든 클라이언트가 대기한다.** 이 지적을 하면 "운영을 아는구나"가 된다

#### (2) 자료구조 — 어디에 쓰는지까지

| 타입 | 발송 도메인에서 쓸 자리 |
|---|---|
| String | 캐시, 카운터(`INCR`), **멱등키(`SET key NX EX`)** |
| Hash | 객체 캐시 (발신프로필, 템플릿) |
| List | 간단한 큐 (`LPUSH`/`BRPOP`) |
| Set | **중복 수신자 제거** |
| **Sorted Set** | **예약 발송** — score를 발송 예정 시각으로 두고 `ZRANGEBYSCORE`로 도래분만 꺼낸다 ★설계 질문 카드 |
| **Stream** | 컨슈머 그룹이 있는 로그형 큐 (Kafka 축소판) |
| HyperLogLog | 대략적 유니크 카운트 (오차 ~0.8%, 메모리 극소) |

#### (3) 영속성 — 왜 원장으로 못 쓰나

- **RDB 스냅샷**: 주기적으로 메모리 전체를 파일로. **마지막 스냅샷 이후는 유실**
- **AOF(Append Only File)**: 명령을 로그로 기록. `appendfsync everysec`(기본)이면 **최대 1초치 유실**
- → **둘 다 완전한 무손실이 아니다.** 그래서 **과금·계약 데이터를 Redis에 두면 안 된다.** 캐시·임시 상태용이다

#### (4) 캐시 전략과 3대 문제

- **Cache-Aside** (가장 흔함): 조회 → 없으면 DB → 캐시에 저장. 갱신 시 **캐시를 지운다**(갱신하지 않고 삭제하는 게 정석 — 경합 시 낡은 값이 남는 걸 막는다)
- **Write-Through**: 쓸 때 캐시와 DB를 같이. 일관성 좋고 쓰기 느림
- **Write-Behind**: 캐시에 쓰고 DB는 나중에. 빠르지만 **유실 위험**

**3대 문제**
| 문제 | 무엇 | 대응 |
|---|---|---|
| **캐시 스탬피드** | 인기 키가 **동시에 만료**돼 요청이 전부 DB로 몰림 | **TTL에 지터** 추가, 뮤텍스로 하나만 갱신 |
| **캐시 관통(penetration)** | **없는 키**를 계속 조회 → 매번 DB까지 감 (공격 벡터이기도) | **빈 값도 짧게 캐싱**, 블룸 필터 |
| **정합성** | DB는 바뀌었는데 캐시가 낡음 | 갱신 시 **삭제**, TTL을 짧게, 중요하면 캐시 안 씀 |

#### (5) 분산락 — 발송 중복 방지의 도구

```
SET lock:campaign:123 <고유값> NX EX 30    -- 없을 때만 생성 + TTL
```
- **NX(없을 때만)와 TTL을 한 명령으로** 걸어야 한다. 따로 걸면 그 사이에 죽었을 때 **락이 영원히 남는다**
- 해제할 때는 **자기 락인지 확인 후 삭제** (Lua 스크립트로 원자적으로). 안 그러면 TTL로 만료된 뒤 남의 락을 지운다
- **Redlock**(여러 노드 과반 획득)은 강한 보장을 노리지만 **논쟁이 있다**. 알고 있다고만 언급하고 단정하지 말 것
- ⚠️ **가장 중요한 인식**: **분산락은 성능 최적화이지 정합성의 최종 보장이 아니다.** GC 정지나 네트워크 지연으로 락이 만료된 줄 모르고 진행할 수 있다. **최종 방어선은 DB 유니크 제약**이다

### 2-4. MongoDB — 개념만

- **문서 지향**: BSON 문서. 컬렉션 = 테이블, 도큐먼트 = 행. 스키마 고정 아님
- **임베딩 vs 레퍼런스**: **같이 읽는 데이터는 문서 안에 넣고**(조인 회피), 독립적으로 크는 데이터는 참조로 분리
  → **"조인을 쿼리에서 하는 대신 문서 설계 단계에서 미리 합쳐 두는 모델"** — 한 줄 요약은 이것
- **인덱스**: B-Tree 기반. 복합·부분·**TTL 인덱스**(자동 만료) ← 발송 이력 보존 기간에 쓸 수 있음
- **레플리카 셋**: Primary 1 + Secondary N, 자동 페일오버. 읽기를 세컨더리로 분산 가능(**복제 지연 감수**)
- **샤딩**: **샤드 키 선택이 전부**. 단조 증가 키(타임스탬프, ObjectId)를 쓰면 **항상 마지막 샤드로만 쓰기가 몰린다**(hot shard) → 해시 샤드 키나 복합 키
- **트랜잭션**: 4.0부터 다중 문서 지원. 단 **비용이 크므로 문서 설계로 피하는 게 정석**

### 2-5. 그래서 무엇을 어디에 — 판단 프레임

설계할 때 그대로 쓸 수 있는 표.

| 데이터 | 저장소 | 이유 |
|---|---|---|
| 고객사·계약·**과금 원장** | **RDB** | 정합성이 생명. 트랜잭션 필요 |
| 발송 요청·발송 상태 | **RDB** | 상태 전이와 중복 방지(유니크 제약) |
