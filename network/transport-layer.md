# 얼마나 빨리 보낼지 누가 정하나

## 30초 요약

- TCP 연결 수립은 왕복 1.5회(3-way handshake), 종료는 4번이다. 종료가 한 번 더 많은 건 **양방향을 따로 닫기** 때문이다
- 보낼 양을 정하는 창이 둘이다. rwnd(수신자가 감당할 양)와 cwnd(네트워크가 감당할 양). 실제 전송량은 **`min(cwnd, rwnd)`**
- **혼잡 제어의 본질은 추측이다.** 네트워크가 얼마나 막혔는지 알 방법이 없어서, 손실을 신호로 삼아 늘렸다 줄였다 한다
- 그 규칙이 **AIMD**다. 성공하면 조금씩 더하고(+1), 실패하면 절반으로 깎는다(×½). 늘릴 땐 신중하고 줄일 땐 과감하다
- 백프레셔·레이트 리미팅·서킷 브레이커가 전부 이 구조의 응용이다. **TCP가 40년 전에 푼 문제를 애플리케이션 계층에서 다시 푸는 것**이다

## 원리 — 왜 그런가

### 2-1. 연결 수립은 왜 3번이고 종료는 왜 4번인가

**수립이 3번인 이유**: 양쪽이 각자 "내 시작 번호는 이거다"를 알리고 상대가 받았음을 확인해야 한다. 각 방향에 SYN 하나 + ACK 하나씩 = 4번인데, 가운데 두 개를 한 패킷으로 합쳐서 3번이 된다.

```
클라이언트 → SYN(내 시작번호=x)          → 서버
클라이언트 ← SYN(내 시작번호=y) + ACK(x+1) ← 서버   ← 두 개를 합침
클라이언트 → ACK(y+1)                    → 서버
```

**종료가 4번인 이유는 합칠 수 없어서**다. "나는 더 보낼 게 없다"(FIN)와 "알겠다"(ACK)는 양쪽이 독립적으로 판단한다. 내가 할 말이 끝났다고 상대도 끝난 건 아니다. 상대는 아직 보낼 응답이 남아 있을 수 있다. 그래서 한쪽만 닫힌 상태(half-close)가 존재하고, FIN과 ACK를 못 합친다.

**TIME_WAIT: 왜 다 끝나고도 기다리나**

먼저 닫은 쪽은 마지막 ACK를 보낸 뒤에도 한동안 소켓을 붙잡고 있는다. 이유가 둘이다.

1. **마지막 ACK가 유실될 수 있다.** 그러면 상대가 FIN을 재전송하는데, 내가 이미 소켓을 지웠으면 응답할 주체가 없어 상대가 계속 재전송한다
2. **같은 포트 조합의 새 연결에 옛 패킷이 섞이는 것**을 막는다. 네트워크에 떠돌던 지연 패킷이 뒤늦게 도착했을 때, 그 자리에 새 연결이 있으면 데이터가 오염된다

**실무에서 이게 문제가 되는 지점**: 서버가 먼저 연결을 닫는 구조에서 TIME_WAIT 소켓이 수만 개 쌓인다. 포트가 고갈되면 새 연결을 못 맺는다. `ss -tan | grep TIME-WAIT`으로 세는 그 숫자다(→ [리눅스 장애 조사](../os/linux-troubleshooting.md)).

→ **근본 해법은 연결을 자주 안 맺는 것**이고, 그게 §2-2다.

### 2-2. 커넥션 풀이 왜 필요한가

연결을 맺는 데 왕복이 필요하다.
```
3-way handshake:  SYN → SYN-ACK → ACK    (왕복 1.5회)
TLS 협상 추가하면:                        (왕복 1~2회 더)
```
서버가 멀면 왕복 한 번에 수십 ms다. **요청마다 이걸 내면 실제 데이터를 보내기도 전에 100ms를 쓴다.**

**→ 그래서 연결을 재사용한다.**
- **HTTP Keep-Alive**: 응답 후에도 연결을 끊지 않고 다음 요청에 재사용
- **커넥션 풀**: 미리 만들어 두고 빌려 쓴다 (DB도, HTTP 클라이언트도 같은 원리 → [트랜잭션 · 락](../database/basics/transaction-and-lock.md) §2-10)

**⚠️ 커넥션 풀의 함정**: 서버 쪽이 먼저 연결을 끊었는데 클라이언트가 모르고 그 커넥션을 쓰면 에러가 난다. → `maxLifetime`을 서버의 idle timeout보다 짧게 잡는다.

> 재사용에는 숨은 이득이 하나 더 있다. 갓 맺은 연결은 §2-4의 cwnd가 작아서 처음엔 느리다. 연결을 재사용하면 이미 커진 창을 물려받는다. "첫 요청만 유독 느린" 현상의 원인 중 하나가 이것이다.

### 2-3. 흐름 제어는 수신자가 감당할 만큼만

보내는 쪽이 아무리 빨라도 받는 쪽 버퍼가 넘치면 소용없다. 그래서 수신자가 매 ACK마다 "내 여유 공간은 이만큼"(rwnd)을 같이 알려준다.

```
수신자: "ACK. 그리고 내 남은 버퍼는 64KB"
송신자: 64KB를 넘겨 보내지 않는다
```

이게 슬라이딩 윈도다. 확인된 만큼 창이 앞으로 밀리고, 그만큼 더 보낼 수 있다.

**핵심은 "확인을 기다리지 않고 창 크기만큼 미리 보낸다"는 것**이다. 한 건 보내고 ACK 기다리기를 반복하면 처리량이 왕복 시간에 갇힌다. 창이 있어야 파이프를 채운다.

> 이 구조가 [대용량 처리](../system-design/high-throughput.md) §2-2의 백프레셔와 정확히 같다. RabbitMQ의 prefetch가 하는 일이 rwnd와 같다. 소비자가 "한 번에 이만큼만"을 정한다. 이름만 다르고 발상은 하나다.

### 2-4. 혼잡 제어는 네트워크가 감당할 만큼만

흐름 제어는 수신자를 보호한다. 그런데 수신자는 멀쩡한데 중간 경로가 막히는 경우가 있다. 라우터 큐가 차서 패킷이 버려지는 상황이다.

**여기에 근본적인 어려움이 있다. 송신자는 네트워크 상태를 알 방법이 없다.** 라우터가 "나 지금 막혔어요"라고 알려주지 않는다. 보이는 건 내가 보낸 게 도착했는지 여부뿐이다.

그래서 추측한다. 손실을 혼잡의 신호로 삼고, 창(cwnd)을 늘렸다 줄였다 하며 가능한 최대치를 계속 더듬는다.

실제 전송량은 두 창의 작은 쪽이다.

```
전송 가능량 = min(cwnd, rwnd)
              ↑      ↑
       네트워크 사정  수신자 사정
```

**(1) Slow Start: 이름과 달리 폭발적으로 늘린다**

연결 초기에는 적정선을 전혀 모른다. 그래서 ACK가 하나 올 때마다 창을 1씩 키운다. 왕복 한 번에 보낸 게 전부 확인되면 창이 두 배가 된다.

```
1 → 2 → 4 → 8 → 16 → 32 ...   (왕복마다 2배)
```

"느린 시작"은 처음 시작점이 1이라 작다는 뜻이지 증가가 느리다는 뜻이 아니다. **증가는 지수적이다.**

이 단계는 cwnd가 임계값(ssthresh)을 넘으면 끝난다.

**(2) Congestion Avoidance: 임계값을 넘으면 조심스럽게**

이제 적정선 근처다. 여기서도 두 배씩 키우면 바로 넘친다. 그래서 왕복 한 번에 1씩만 늘린다. 지수에서 선형으로 바뀐다.

**(3) 손실이 나면 절반으로**

혼잡을 감지하면 ssthresh를 현재 전송량의 절반으로 낮춘다. 늘릴 땐 1씩, 줄일 땐 절반이다.

**이 비대칭이 AIMD**(Additive Increase, Multiplicative Decrease)이고, 설계의 핵심이다.

| | 방향 | 이유 |
|---|---|---|
| 성공할 때 | **+1** (덧셈) | 남의 몫을 뺏을 수 있으니 신중하게 |
| 실패할 때 | **×½** (곱셈) | 이미 남에게 피해를 주고 있으니 빠르게 물러난다 |

**"늘릴 땐 신중하고 줄일 땐 과감하다."** 공유 자원을 여럿이 나눠 쓸 때의 일반 원칙이다. 반대로 하면(빨리 늘리고 천천히 줄이면) 모두가 밀어붙이다 전체가 무너진다.

### 2-5. 손실을 어떻게 아나

손실 감지 방법이 둘이고, 심각도가 다르게 취급된다.

**(1) 타임아웃.** 보냈는데 아무 소식이 없다. 최악의 신호다. 창을 1까지 떨어뜨리고 Slow Start를 다시 한다.

**(2) 중복 ACK 3개.** 뒤엣것은 도착하는데 중간 하나가 비었다.

```
송신: 1  2  3  4  5  6
수신: 1     3  4  5  6      ← 2번이 유실
ACK :    "2번 주세요" ×4     ← 3,4,5,6이 도착할 때마다 같은 ACK
```

**중복 ACK가 온다는 건 뒤 패킷들이 잘 도착하고 있다는 뜻**이다. 길이 완전히 막힌 게 아니다. 그래서 타임아웃보다 덜 심각하게 다룬다. 창을 1로 떨어뜨리지 않고 절반에서 재개한다(Fast Retransmit / Fast Recovery).

> **왜 하필 3개인가**: 1~2개는 패킷 순서가 뒤바뀐 것만으로도 생긴다(경로가 달라 늦게 도착). 유실이라고 단정하고 재전송하면 낭비다. 3개는 "순서 뒤바뀜치고는 너무 많다"는 경험적 기준선이다.

### 2-6. 그래서 애플리케이션이 다시 푸는 문제

TCP가 푼 문제와 [대용량 처리](../system-design/high-throughput.md)의 주제가 같은 문제의 다른 계층 버전이다.

| TCP | 애플리케이션 | 공통 발상 |
|---|---|---|
| **rwnd**(수신 창) | RabbitMQ prefetch, 유계 큐 (§2-2 백프레셔) | **소비자가 감당할 만큼만 받는다** |
| **cwnd**(혼잡 창) | 레이트 리미팅, 토큰 버킷 (§2-3) | **공유 자원이 감당할 만큼만 보낸다** |
| **AIMD** | 서킷 브레이커의 half-open 복귀 (§2-4) | **실패엔 과감히 물러나고 복귀는 조심스럽게** |
| **타임아웃 재전송** | 지수 백오프 재시도 (§2-5) | **실패할수록 간격을 벌린다** |

**한 가지가 결정적으로 다르다. 공정성이다.**

TCP는 각 연결이 서로 조율하지 않고 독립적으로 AIMD를 하는데, 그래도 대체로 균등하게 나눠 갖는다. 혼잡이 생기면 많이 쓰던 쪽이 절대량으로 더 많이 깎이기 때문이다(절반씩 깎으면 100→50, 10→5).

애플리케이션 레이트 리밋에는 이 성질이 없다. 워커 5대가 각자 "초당 100건"을 지키면 그냥 500건이 나간다. [대용량 처리](../system-design/high-throughput.md) §2-3의 그 함정이다. 그래서 Redis 같은 곳에 토큰을 공유해 전역으로 만들어야 한다. TCP는 공짜로 얻는 것을 애플리케이션은 명시적으로 만들어야 한다.

### 2-7. TCP vs UDP, 무엇을 포기하는가

| | TCP | UDP |
|---|---|---|
| 연결 | 수립·종료 필요 | 없음 |
| 순서·재전송 | 보장 | 없음 |
| 흐름·혼잡 제어 | 있음 | **없음** |
| 오버헤드 | 헤더 20B + 왕복 비용 | 헤더 8B |

UDP가 "가볍다"의 실체는 §2-3~2-5를 전부 안 한다는 것이다. 그래서 혼잡해도 안 줄인다. 배려가 없는 대신 지연이 예측 가능하다.

실시간 음성·영상이 UDP를 쓰는 이유가 여기서 나온다. 0.5초 전에 유실된 음성 조각을 재전송받아 봐야 이미 늦어서 쓸모가 없다. TCP는 그 한 조각을 기다리느라 뒤에 도착한 멀쩡한 데이터까지 붙잡아 둔다(head-of-line blocking). 끊기더라도 계속 흐르는 게 나은 종류의 데이터가 있다.

> HTTP/3가 TCP를 버리고 UDP 위에 QUIC을 얹은 것도 같은 동기다. TCP의 head-of-line blocking을 피하려는 것이다. **신뢰성은 포기한 게 아니라 상위 계층으로 옮긴 것**이다.
