# OSI 7계층은 왜 7개인가, 그리고 왜 안 맞는가

## 30초 요약

- 네트워크를 계층으로 쪼갠 이유는 하나다. **한 층을 통째로 갈아 끼워도 나머지가 안 바뀌게** 하려는 것이다. Wi-Fi로 바꿔도 HTTP는 그대로다
- **OSI 7계층은 참조 모델이고, 실제로 돌아가는 것은 TCP/IP 4계층**이다. 둘을 같은 층위로 외우면 현실과 안 맞는다
- 특히 **세션(5)·표현(6) 계층은 실제 구현에서 응용 계층에 흡수됐다.** OSI가 예측한 분리가 일어나지 않았다
- 데이터는 내려가며 **헤더가 겹겹이 붙는다**(캡슐화). 올라가며 하나씩 벗는다
- 실무에서 계층을 아는 값어치는 "L4 로드밸런서와 L7 로드밸런서가 뭐가 다른가", "이 장애는 어느 층인가"에서 나온다

---

## 원리 — 왜 그런가

### 2-1. 왜 계층으로 나누나

계층화의 목적은 교육이 아니라 **교체 가능성**이다.

유선 랜을 쓰다가 Wi-Fi로 바꿨다고 하자. 이때 바뀌어야 하는 코드가 어디까지인가?

```
계층이 없다면 : "Wi-Fi로 HTTP 보내기"를 새로 만들어야 한다.
                전송 수단 × 프로토콜 조합마다 구현이 필요하다
계층이 있으면 : 물리·데이터링크 층만 갈린다.
                그 위의 IP·TCP·HTTP는 한 글자도 안 바뀐다
```

각 층은 아래층에 "어떻게"를 묻지 않는다. TCP는 자기 세그먼트가 광케이블로 가는지 전파로 가는지 모르고, 알 필요도 없다. 이 무지가 곧 교체 가능성이다.

> 소프트웨어에서 인터페이스 뒤에 구현을 가두는 것과 같은 발상이다. [대용량 처리](../system-design/high-throughput.md) §2-10에서 채널사를 어댑터 뒤에 가두는 것도 정확히 같은 동기다. 변하는 축을 한 층에 몰아넣는 것이다.

### 2-2. 각 층은 무엇을 책임지나

| 계층 | 이름 | 책임 | 단위 | 실무에서 만나는 것 |
|---|---|---|---|---|
| 7 | 응용 | 사용자에게 서비스 | 데이터 | HTTP, DNS, SMTP |
| 6 | 표현 | 부호화·암호화·압축 | 데이터 | TLS, 문자 인코딩 |
| 5 | 세션 | 대화의 시작·유지·종료 | 데이터 | (실제로는 7에 흡수) |
| 4 | 전송 | **종단 간 전달**, 신뢰성·순서 | 세그먼트 | TCP, UDP, **포트 번호** |
| 3 | 네트워크 | **어느 길로 갈 것인가**(라우팅) | 패킷 | IP, 라우터, **IP 주소** |
| 2 | 데이터링크 | **바로 옆 장비까지** 오류 없이 | 프레임 | 이더넷, 스위치, **MAC 주소** |
| 1 | 물리 | 전기·빛 신호로 바꾸기 | 비트 | 케이블, 광섬유, 전파 |

3계층과 2계층의 차이가 헷갈리기 쉽다. 둘 다 "전달"인데 범위가 다르다.

- **2계층 = 바로 옆 장비까지.** 같은 네트워크 안에서 MAC 주소로 찾는다
- **3계층 = 최종 목적지까지.** 여러 네트워크를 건너뛰며 IP 주소로 길을 찾는다

택배로 치면 3계층이 "서울시 강남구 …"라는 최종 주소이고, 2계층은 "지금 이 트럭에서 다음 물류센터까지"다. 최종 주소는 안 바뀌지만 구간마다 트럭은 바뀐다.

### 2-3. 캡슐화: 헤더가 겹겹이 붙는다

내려갈 때 각 층이 자기 헤더를 앞에 붙인다.

```
응용    :                          [ HTTP 요청 ]
전송    :              [ TCP 헤더 | HTTP 요청 ]          ← 포트 번호가 여기
네트워크:   [ IP 헤더 | TCP 헤더 | HTTP 요청 ]          ← IP 주소가 여기
데이터링크: [ 이더넷 헤더 | IP 헤더 | TCP 헤더 | HTTP 요청 | 트레일러 ]
```

받는 쪽은 올라가면서 자기 헤더만 떼고 위로 넘긴다. **각 층은 위층 내용물을 열어보지 않는다.** 그냥 불투명한 덩어리로 취급한다.

여기서 실무 감각이 하나 나온다. 계층이 올라갈수록 헤더가 쌓이므로 실제 payload 비율이 줄어든다. 작은 메시지를 건건이 보내면 헤더 오버헤드가 본문보다 커질 수 있다. "배치로 묶어 보내라"는 조언의 근거 중 하나다([대용량 처리](../system-design/high-throughput.md) §2-8).

### 2-4. OSI는 왜 현실과 안 맞나

**OSI 7계층은 표준화 기구가 설계한 참조 모델이고, 인터넷은 그 표준을 기다리지 않고 TCP/IP로 먼저 돌아갔다.** 그래서 둘의 관계는 "이론과 그 구현"보다 "경쟁했고 진 쪽과 이긴 쪽"에 가깝다.

```
OSI 7계층                    TCP/IP 4계층 (실제)
─────────────────────────────────────────────
7 응용   ┐
6 표현   ├──────────→        응용 (Application)
5 세션   ┘
4 전송   ───────────→        전송 (Transport)
3 네트워크 ─────────→        인터넷 (Internet)
2 데이터링크 ┐
1 물리      ┴──────→        링크 (Link)
```

5·6계층이 사라진 게 핵심이다. OSI는 "세션 관리"와 "표현 변환"이 독립된 층으로 분리되리라 봤는데, 실제로는 각 응용 프로토콜이 자기 방식으로 알아서 처리했다. HTTP는 자기 안에 세션 개념(쿠키)을 갖고, 압축(`Content-Encoding`)도 자기가 한다.

> 그래서 "TLS는 몇 계층인가"에 깔끔한 답이 없다. 표현 계층(6)이라고도 하고, TCP 위에서 동작하니 4.5계층이라고도 한다. 모델이 현실을 다 담지 못한다는 증거이지 누가 틀린 게 아니다. 면접에서 이 질문이 나오면 "OSI 기준으로는 6, 실제 구현에서는 전송과 응용 사이"라고 답하는 편이 정확하다.

그럼 왜 아직도 7계층을 배우나. 공통 어휘로 쓰이기 때문이다. "L4에서 끊겼다", "L7 라우팅" 같은 말이 업계 표준어다. 모델이 실제 구현을 서술하지 못해도 대화의 좌표계로는 여전히 작동한다.

### 2-5. 계층을 아는 것의 실무 가치

**(1) L4 vs L7 로드밸런서**

| | L4 로드밸런서 | L7 로드밸런서 |
|---|---|---|
| 보는 것 | **IP + 포트**까지 | **HTTP 내용물**(경로·헤더·쿠키) |
| 할 수 있는 것 | 서버로 분배 | `/api/*`는 A로, `/img/*`는 B로. 헤더 기반 카나리 |
| 비용 | 싸다. 내용물을 안 열어본다 | **패킷을 조립해 파싱해야 한다** |
| TLS | 그대로 통과 | **여기서 복호화해야** 내용을 본다(TLS 종료) |

차이의 뿌리가 §2-3의 캡슐화다. L4는 헤더 두 겹만 보고, L7은 끝까지 벗겨야 한다. **"내용을 볼 수 있다"와 "싸다"가 맞바꿈 관계**인 이유가 여기 있다.

**(2) 장애를 어느 층에서 찾을지**

| 증상 | 의심 계층 | 확인 |
|---|---|---|
| 아예 연결이 안 됨 | 3~4 | `ping`(3), `telnet`/`nc`로 포트(4) |
| 연결은 되는데 응답이 없음 | 7 | 애플리케이션·스레드 덤프 |
| 인증서 오류 | 6 | 인증서 체인·만료 |
| 특정 경로만 실패 | 7 (L7 LB 라우팅) | LB 규칙 |
| 간헐적 끊김 | 2~3 | 패킷 손실·MTU |

**"위에서부터 의심하지 말고 아래에서부터 확인한다"**가 순서다. 3계층이 안 되는데 애플리케이션 로그를 뒤지면 시간만 쓴다. → [리눅스 장애 조사](../os/linux-troubleshooting.md)
