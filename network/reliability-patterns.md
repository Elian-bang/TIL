# 타임아웃과 멱등성

## 30초 요약

- **타임아웃은 두 종류다**: connect(연결 수립)와 read(응답 대기). 위험한 쪽은 read다
- **read timeout을 안 걸면 스레드가 무한 대기한다** → 스레드 풀 고갈 → "채널사 하나가 죽었는데 우리 서비스 전체가 멈췄다"
- 이때 **서킷 브레이커도 소용없다.** 실패로 카운트조차 안 되니 서킷이 안 열린다
- **멱등한 메서드**: GET/PUT/DELETE는 멱등이고 POST는 명세의 멱등 목록에 없다. 발송 요청은 POST다 → 재시도가 곧 중복 발송
- 그래서 **`Idempotency-Key`**를 붙인다. 같은 키의 요청은 새로 처리하지 않고 이전 결과를 돌려준다

---

## 원리 — 왜 그런가

### 2-1. 타임아웃을 안 걸면 무슨 일이 생기나

두 종류를 구분해야 한다.
- **connect timeout**: TCP 연결을 맺기까지. 상대가 죽어 있으면 여기서 걸린다
- **read timeout**: 연결은 됐는데 응답이 안 올 때. 이게 진짜 위험한 쪽이다

read timeout을 안 걸면:
1. 채널사가 응답을 안 준다 (죽었지만 연결은 살아 있음)
2. 스레드가 무한 대기한다. 몇 시간이고 기다린다
3. 요청이 계속 들어오면 스레드가 하나씩 묶인다
4. 스레드 풀 고갈 → 전체 서비스 마비

→ "채널사 하나가 죽었는데 우리 서비스 전체가 멈췄다"의 가장 흔한 원인이다.
서킷 브레이커도 소용없다. 실패로 카운트조차 안 되니 서킷이 안 열린다 (→ [대용량 처리](../system-design/high-throughput.md) §2-4).

> **코드 리뷰에서 타임아웃 없는 HTTP 클라이언트는 1순위 지적 대상**이다. `RestTemplate`을 기본 생성자로 만들면 Spring은 타임아웃을 걸어 주지 않는다. 레퍼런스가 *"By default, it uses the `SimpleClientHttpRequestFactory`"*라고 적고, 그 factory의 javadoc은 connect와 read 양쪽 모두 *"Default is the system's default timeout"*이라고 한다. 값을 정하는 주체가 Spring이 아니라 그 아래 JDK `HttpURLConnection`이라는 뜻이다. `URLConnection` javadoc은 *"A timeout of zero is interpreted as an infinite timeout"*이라고만 하고 초기값이 얼마인지는 적지 않는다. 결국 코드만 봐서는 상한이 몇 초인지 알 수 없고, 그게 문제다.

### 2-2. HTTP 메서드의 멱등성과 발송

RFC 9110이 두 성질을 따로 정의한다. 안전(safe)은 *"Request methods are considered "safe" if their defined semantics are essentially read-only; i.e., the client does not request, and does not expect, any state change on the origin server as a result of applying a safe method to a target resource."*이고, 멱등(idempotent)은 *"A request method is considered "idempotent" if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request."*다. 응답이 매번 같아야 한다는 뜻이 아니라 서버에 남는 결과가 같아야 한다는 뜻이다. DELETE를 두 번 부르면 200 다음에 404가 와도 멱등성은 깨지지 않는다.

| 메서드 | 멱등? | 왜 |
|---|---|---|
| GET | O | 읽기만 |
| PUT | O | "이 상태로 만들어라". 몇 번 해도 같은 상태 |
| DELETE | O | 이미 지워졌으면 여전히 지워진 상태 |
| **POST** | X | "새로 만들어라". 부를 때마다 새로 생긴다 |

표에 넷만 실었지만 명세가 멱등이라고 명시한 것은 *"PUT, DELETE, and safe request methods"*다. 안전한 메서드가 GET·HEAD·OPTIONS·TRACE이므로 멱등 집합은 여섯이고, 그 목록에 POST가 없다.

멱등성을 따로 정의해 둔 이유도 명세에 적혀 있다. *"Idempotent methods are distinguished because the request can be repeated automatically if a communication failure occurs before the client is able to read the server's response."* 그리고 반대쪽 규정이 이 절의 주제다. *"A client SHOULD NOT automatically retry a request with a non-idempotent method unless it has some means to know that the request semantics are actually idempotent…"* 재시도를 포기하라는 말이 아니라, 멱등임을 알 수단을 따로 만들어 두라는 말이다.

**발송 요청은 POST다.** 그래서 재시도가 곧 중복 발송이 된다.
**→ `Idempotency-Key` 헤더**: 클라이언트가 요청마다 고유 키를 만들어 보내고, 서버는 같은 키의 요청이 이미 처리됐으면 새로 처리하지 않고 이전 결과를 돌려준다.

IETF에도 초안이 올라와 있다. `draft-ietf-httpapi-idempotency-key-header`는 이 키를 *"a unique value generated by the client which the resource uses to recognize subsequent retries of the same request"*라고 정의하고, 같은 키를 다시 받은 서버가 *"SHOULD respond with the result of the previously completed operation, success or an error"* 하도록 적는다. 아직 RFC가 아니라 Internet-Draft라, 표준 헤더라고 부르기에는 이르다.

(결제 API에서 표준처럼 쓰이는 패턴이다. 발송도 돈이 나가는 도메인이라 같은 문제를 푼다. → [대용량 처리](../system-design/high-throughput.md) §2-6)

> **확인한 출처**:
> - [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) §9.2.1·§9.2.2 — safe와 idempotent의 정의 문장, 멱등 목록이 "PUT, DELETE, and safe request methods"라는 규정, 멱등성을 구분하는 이유("the request can be repeated automatically if a communication failure occurs…"), 비멱등 메서드 자동 재시도를 막는 SHOULD NOT 규정(§2-2)
> - Spring Framework 레퍼런스 `REST Clients` — "By default, it uses the `SimpleClientHttpRequestFactory`", `RestTemplate`이 `HttpURLConnection`을 쓰는 반면 `RestClient`는 `JdkClientHttpRequestFactory`를 고른다는 서술(§2-1): https://docs.spring.io/spring-framework/reference/integration/rest-clients.html
> - `SimpleClientHttpRequestFactory` javadoc — connect/read 타임아웃 모두 "Default is the system's default timeout", "A timeout value of 0 specifies an infinite timeout"(§2-1): https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/http/client/SimpleClientHttpRequestFactory.html
> - JDK 21 `java.net.URLConnection` javadoc — `setConnectTimeout`/`setReadTimeout`의 "A timeout of zero is interpreted as an infinite timeout"과 `SocketTimeoutException`(§2-1): https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/net/URLConnection.html
> - `draft-ietf-httpapi-idempotency-key-header-07` — 아직 Internet-Draft라는 것, 키의 정의 문장, 중복 키를 받았을 때 이전 결과를 돌려주라는 SHOULD(§2-2): https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/
> **미확인**:
> - **기본 `RestTemplate`의 타임아웃이 실제로 무제한인지**(§2-1) — Spring javadoc은 "the system's default timeout"까지만 적고, `URLConnection` javadoc은 초기값을 명시하지 않는다. `sun.net.client.defaultConnectTimeout` 같은 시스템 속성을 안 걸었을 때 0(무제한)이 된다는 서술을 문서로 확인하지 못해, 본문에서 "무제한"이라는 단정을 뺐다
> - **스레드 풀 고갈까지 이어지는 경로**(§2-1) — 서블릿 컨테이너의 요청당 스레드 모델을 전제로 한 서술이고 문서를 대조하지 않았다
> - **서킷 브레이커가 무한 대기를 실패로 세지 못한다**(§2-1) — Resilience4j 등 구현 문서를 대조하지 않았다
> - **POST가 멱등이 아니라는 명시 문장** — RFC 9110은 멱등 목록에 POST를 넣지 않을 뿐, "POST는 멱등이 아니다"라고 따로 쓰지 않는다. 본문을 목록 기준 서술로 바꾼 이유다
