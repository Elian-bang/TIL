# 타임아웃과 멱등성

## 30초 요약

- **타임아웃은 두 종류다**: connect(연결 수립)와 read(응답 대기). 위험한 쪽은 read다
- **read timeout을 안 걸면 스레드가 무한 대기한다** → 스레드 풀 고갈 → "채널사 하나가 죽었는데 우리 서비스 전체가 멈췄다"
- 이때 **서킷 브레이커도 소용없다.** 실패로 카운트조차 안 되니 서킷이 안 열린다
- **멱등한 메서드**: GET/PUT/DELETE는 멱등이고 POST는 아니다. 발송 요청은 POST다 → 재시도가 곧 중복 발송
- 그래서 **`Idempotency-Key`**를 붙인다. 같은 키의 요청은 새로 처리하지 않고 이전 결과를 돌려준다

---

## 원리 — 왜 그런가

### 2-1. 타임아웃을 안 걸면 무슨 일이 생기나

두 종류를 구분해야 한다.
- **connect timeout**: TCP 연결을 맺기까지. 상대가 죽어 있으면 여기서 걸린다
- **read timeout**: 연결은 됐는데 응답이 안 올 때. 이게 진짜 위험한 쪽이다

read timeout을 안 걸면:
1. 채널사가 응답을 안 준다 (죽었지만 연결은 살아 있음)
2. 스레드가 무한 대기한다. 몇 시간이고 기다린다
3. 요청이 계속 들어오면 스레드가 하나씩 묶인다
4. 스레드 풀 고갈 → 전체 서비스 마비

→ "채널사 하나가 죽었는데 우리 서비스 전체가 멈췄다"의 가장 흔한 원인이다.
서킷 브레이커도 소용없다. 실패로 카운트조차 안 되니 서킷이 안 열린다 (→ [대용량 처리](../system-design/high-throughput.md) §2-4).

> **코드 리뷰에서 타임아웃 없는 HTTP 클라이언트는 1순위 지적 대상**이다. `RestTemplate`을 기본 생성자로 만들면 타임아웃이 무제한이다.

### 2-2. HTTP 메서드의 멱등성과 발송

| 메서드 | 멱등? | 왜 |
|---|---|---|
| GET | O | 읽기만 |
| PUT | O | "이 상태로 만들어라". 몇 번 해도 같은 상태 |
| DELETE | O | 이미 지워졌으면 여전히 지워진 상태 |
| **POST** | **X** | **"새로 만들어라"**. 부를 때마다 새로 생긴다 |

**발송 요청은 POST다.** 그래서 재시도가 곧 중복 발송이 된다.
**→ `Idempotency-Key` 헤더**: 클라이언트가 요청마다 고유 키를 만들어 보내고, 서버는 같은 키의 요청이 이미 처리됐으면 새로 처리하지 않고 이전 결과를 돌려준다.

(결제 API에서 표준처럼 쓰이는 패턴이다. 발송도 돈이 나가는 도메인이라 같은 문제를 푼다. → [대용량 처리](../system-design/high-throughput.md) §2-6)
