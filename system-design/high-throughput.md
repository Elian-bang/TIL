# 대용량 처리 · 분산 시스템

## 30초 요약

- **처리량 vs 지연은 다른 목표다.** 대량 캠페인은 처리량, 인증번호는 지연 → 같은 큐에 넣으면 안 된다
- **백프레셔**: 소비자가 못 따라갈 때 생산자를 늦추는 것. 없으면 큐가 무한정 쌓여 어딘가는 반드시 터진다
- **서킷 브레이커**: 죽은 채널사를 계속 때리면 내 스레드가 먼저 고갈된다. 빠르게 실패시키는 게 나를 지키는 일
- **재시도는 지수 백오프 + 지터.** 지터가 없으면 재시도가 동시에 몰린다(thundering herd)
- **멱등성이 이 도메인의 심장이다.** 중복 발송 = 고객사 과금 사고. 3층 방어(Redis 키 → DB 유니크 → 채널사 요청 ID)
- **관측 가능성**: "조용한 실패"를 잡으려면 성공률 지표가 필요하다. 에러 로그만으로는 안 잡힌다

## 원리 — 왜 그런가

### 2-1. 처리량 vs 지연, 왜 큐를 분리하나

**둘은 다른 목표이고, 종종 충돌한다.**

- **처리량(throughput)**: 시간당 몇 건. 배치·묶음·버퍼링으로 올린다
- **지연(latency)**: 한 건이 얼마나 빨리. 묶지 않고 바로 보내야 한다

**배치는 처리량을 올리고 지연을 늘린다.** 100건을 모아 보내면 효율은 좋지만, 첫 번째 건은 100건이 모일 때까지 기다린다.

**발송 도메인에 적용하면:**
| | 요구 | 최적화 |
|---|---|---|
| **대량 캠페인** | 1천만 건을 6시간 안에 | **처리량**: 배치, 병렬, 묶음 전송 |
| **인증번호 문자** | 3초 안에 도착 | **지연**: 즉시, 우선 처리 |

→ 같은 큐에 넣으면 캠페인 1천만 건 뒤에 인증번호가 줄을 선다. **큐(또는 토픽·워커 풀)를 분리하는 근거가 이것이다.** 처리량이 목표인 작업과 지연이 목표인 작업을 한 큐에 섞으면 둘 다 잃는다.

> **규모 산정 감각**(설계 전에 먼저 잡는다): 1천만 건 / 6시간 = 약 460 TPS. 채널사 한 곳이 100 TPS를 받아준다면 채널을 나누거나 시간을 늘려야 한다. 설계는 숫자를 먼저 놓고 시작한다.

### 2-2. 백프레셔가 없으면 어디가 터지나

**소비자가 생산 속도를 못 따라갈 때 생산자를 늦추는 것.**

없으면 어떻게 되나. 큐에 계속 쌓인다 → 메모리 큐면 OOM, 디스크 큐면 디스크가 찬다. 그리고 쌓인 만큼 지연이 늘어난다. "느려진다"가 아니라 **"언젠가 죽는다"**가 정확한 표현이다.

**각 시스템이 백프레셔를 구현하는 방식:**
- **RabbitMQ**: prefetch(QoS)로 제한한다. 정확히는 "받아 갈 개수"가 아니라 *"the number of unacknowledged messages on a channel (or connection) when consuming"*이다. **ack를 늦추면 그만큼 유입이 막힌다는 게 요점이다**
- **Kafka**: pull 모델 자체가 백프레셔다. 컨슈머가 자기 속도로 가져간다
- **스레드 풀**: 유계 큐(bounded queue) + Reject 정책 ← [Java](../java/jvm-gc-concurrency.md) §2-5. 무제한 큐를 쓰면 백프레셔가 사라진다
- **HTTP API**: 429 Too Many Requests 반환. RFC 6585의 정의가 *"The 429 status code indicates that the user has sent too many requests in a given amount of time ("rate limiting")."*이고, 서버는 `Retry-After`로 언제 다시 오라고 알려 줄 수 있다. 한 줄 덧붙이면 *"Responses with the 429 status code MUST NOT be stored by a cache."*라 캐시가 이 거절을 대신 돌려주는 일은 없다

> 백프레셔는 **"거절할 수 있어야 한다"**는 뜻이다. 다 받아 놓고 나중에 죽는 것보다, 지금 거절하는 게 낫다.

→ **TCP가 40년 전에 같은 문제를 풀었다.** 수신 창(rwnd)이 정확히 prefetch와 같은 장치다 → [전송 계층](../network/transport-layer.md) §2-3

### 2-3. 레이트 리미팅, 채널사 TPS 제한 대응

**토큰 버킷 vs 리키 버킷**

| | 동작 | 특징 |
|---|---|---|
| **토큰 버킷** | 일정 속도로 토큰을 채우고, 요청마다 하나씩 소비 | **버스트 허용** (토큰이 쌓여 있으면 한꺼번에) |
| **리키 버킷** | 요청을 큐에 넣고 **일정 속도로 흘려보냄** | 출력이 **완전히 균일** |

- 채널사가 "초당 100건"이라고 하면 보통 **토큰 버킷**이 맞다 (순간 버스트를 흡수)
- 채널사가 균일한 유입을 요구하면 리키 버킷

**분산 환경에서의 함정** ← 이 지적을 하면 앞서간다
워커가 5대인데 각자 "초당 100건"을 지키면 **전체로는 500건**이 나간다. 채널사는 500건을 받는다.
→ **레이트 리밋은 전역이어야 한다.** Redis 카운터나 토큰을 공유해야 한다 ([Redis](../datastore/redis.md)).

> **TCP는 이 조율을 저절로 얻는다.** 각 연결이 독립적으로 AIMD를 하는데도 대체로 균등해진다. 많이 쓰던 쪽이 절반씩 깎일 때 절대량으로 더 많이 잃기 때문이다. 애플리케이션 레이트 리밋에는 그 성질이 없어서 토큰을 명시적으로 공유해야 한다 → [전송 계층](../network/transport-layer.md) §2-4, §2-6

### 2-4. 서킷 브레이커는 왜 빠르게 실패시키나

**채널사 하나가 죽었다. 계속 때리면 무슨 일이 생기나?**

1. 요청마다 **타임아웃(예: 10초)까지 기다린다**
2. 그동안 **내 스레드가 묶여 있다**
3. 스레드 풀이 고갈된다
4. → **채널사 A가 죽었는데, 채널사 B로 가는 발송까지 멈춘다**

**이게 캐스케이딩 장애(연쇄 장애)다.** 남의 장애가 내 장애가 되는 것.

**서킷 브레이커는 나를 지키는 장치다.**
```
CLOSED (정상)  --실패율이 임계치 초과-->  OPEN (차단)
                                            |
                                     일정 시간 뒤
                                            ↓
                                    HALF-OPEN (탐색)
                                    시험 요청 몇 개만 보내 본다
                                     성공 → CLOSED / 실패 → OPEN
```
- **OPEN 상태에서는 호출을 아예 안 한다.** 즉시 실패시킨다 → 스레드가 안 묶인다. Resilience4j는 이때 `CallNotPermittedException`을 던진다
- **HALF-OPEN**이 있는 이유: 무작정 기다리면 언제 살아났는지 모른다. 조금씩 찔러 본다(`permittedNumberOfCallsInHalfOpenState`), OPEN에 머무는 시간은 `waitDurationInOpenState`다
- 구현: **Resilience4j** (Hystrix는 유지보수 종료)

**⚠️ 위 그림에서 두 가지가 빠져 있다.** Resilience4j 문서를 보면 이렇다.
- **여는 조건이 실패율 하나가 아니다.** 실패율 임계치와 **느린 호출 비율** 임계치가 각각 있고, 둘 중 하나만 넘어도 열린다. 타임아웃 직전까지 끌다가 성공하는 채널사는 실패율로는 안 잡히고 이쪽으로 잡힌다
- **최소 호출 수를 채우기 전에는 열리지 않는다.** 전이는 *"a minimum number of calls were recorded"* 이후에만 일어난다. 그래서 **트래픽이 적은 채널은 3건 연속 실패해도 서킷이 안 열린다.** "왜 안 열리지"의 답이 대체로 여기 있다
- 상태는 셋이 아니라 여섯이다. 정상 3종(CLOSED · OPEN · HALF_OPEN) 외에 운영용 특수 상태 셋이 더 있다. `DISABLED`(항상 통과, 기록 안 함) · `FORCED_OPEN`(항상 차단) · `METRICS_ONLY`(통과시키되 지표만 기록). **장애 대응 중 수동으로 끊거나 열어 둘 때 쓰는 손잡이다**

**⚠️ 함께 가야 하는 것: 타임아웃**
서킷 브레이커가 있어도 **타임아웃이 없으면 소용없다.** 무한 대기하면 실패로 카운트도 안 된다.
→ **connect timeout과 read timeout을 반드시 걸 것** ([신뢰성 패턴](../network/reliability-patterns.md) §2-1)

**발송 도메인 적용**: 채널사 A가 OPEN이면 대체 채널로 우회하거나, 큐에 보관했다가 나중에 재시도한다. "실패 처리"가 아니라 "지연 처리"로 가는 게 이 도메인의 정답인 경우가 많다.

### 2-5. 재시도, 지수 백오프 + 지터

**그냥 재시도하면 안 되는 이유:**
- **즉시 재시도** → 죽어 있는 서버를 더 세게 때린다. 회복을 방해한다
- **고정 간격 재시도** → 여러 워커가 동시에 재시도한다 → 살아나는 순간 다시 죽는다

**지수 백오프**: 1초 → 2초 → 4초 → 8초. 간격을 늘려 회복할 시간을 준다
**지터(jitter)**: 여기에 랜덤을 섞는다. 안 섞으면 1000개의 워커가 정확히 같은 시각에 재시도한다 (thundering herd)

> 지터는 사소해 보이지만 **없으면 지수 백오프의 효과가 사라진다.** 이 지적을 하면 실무 감각이 보인다.

**⚠️ 더 중요한 것: 재시도해도 되는 요청인가**
- **재시도해도 되는 것**: 타임아웃, 5xx, 커넥션 실패처럼 결과를 모르는 상태
- **재시도하면 안 되는 것**: 4xx(잘못된 요청, 템플릿 반려). 다시 보내도 같은 결과다
- **⚠️ 가장 위험한 케이스**: 요청은 도착했는데 응답만 못 받은 경우. 재시도하면 중복 발송이다
  → **그래서 멱등성이 필요하다.** 재시도와 멱등성은 세트다

### 2-6. 멱등성이 이 도메인의 심장이다

**정의**: 같은 요청을 여러 번 처리해도 결과가 같다.

왜 이 도메인에서 특히 중요한가. **중복 발송 = 고객사 과금 사고**다. 문자 한 건에 돈이 나가고, 고객사 고객이 같은 문자를 두 번 받는다. 가장 비싼 실수다.

**어디서 중복이 생기나.** 전부 "결과를 모르는" 지점이다.
1. 클라이언트가 API를 재요청 (응답을 못 받아서)
2. 큐의 at-least-once 재배달 ([Kafka](../messaging/kafka.md) §2-6)
3. 배치 재실행
4. 채널사 API 타임아웃 후 재시도 (§2-5)

**3층 방어**

| 층 | 무엇 | 막는 것 | 한계 |
|---|---|---|---|
| **1층. Redis 멱등키** | `SET key NX EX` | 대부분의 중복을 **DB 가기 전에** 차단 | **최종 보장 아님** (영속성·TTL·GC 정지) |
| **2층. DB 유니크 제약** ★ | `UNIQUE(고객사, 캠페인, 수신번호, 회차)` | **경합에서도 뚫리지 않는다** | DB까지 가야 안다 |
| **3층. 채널사 요청 ID** | 채널사에 고유 ID를 함께 전달 | 채널사 쪽 중복도 차단 | 채널사가 지원해야 함 |

**★ 최종 방어선은 반드시 DB 유니크 제약이어야 한다.**
애플리케이션에서 "이미 있나 조회 후 없으면 INSERT"는 동시에 두 요청이 오면 둘 다 통과한다. 조회와 INSERT 사이에 틈이 있기 때문이다. **DB 제약만이 그 틈을 없앤다.**

**멱등키를 무엇으로 잡을 것인가**
- 클라이언트가 주는 경우: `Idempotency-Key` 헤더 ([신뢰성 패턴](../network/reliability-patterns.md) §2-2)
- 도메인 키로 만드는 경우: **(고객사 ID, 캠페인 ID, 수신번호, 발송 회차)**
- ⚠️ **"회차"가 왜 필요한가**: 같은 캠페인을 일부러 두 번 보내는 요구가 있다(재발송). 회차가 없으면 정당한 재발송까지 막힌다. "중복 방지"와 "재발송 허용"을 어떻게 구분할 것인가는 좋은 되물음이다

**발송 이력을 언제 남기나.** 선기록이 정답이다.
```
❌ 발송 → 성공하면 이력 기록      : 발송 후 죽으면 기록이 없다 → 재시도 시 중복
✅ 이력을 SENDING으로 먼저 기록 → 발송 → 결과로 상태 갱신
```
선기록이면 "이미 시도한 건"을 알 수 있다. 애매한 상태(SENDING인 채로 남은 건)는 별도로 조사·정리한다. **유실보다 중복이 무섭기 때문에 이 순서다.**

### 2-7. 파티셔닝 / 샤딩, 핫스팟을 피하는 키 선택

**분할 기준(키)이 전부다.** 잘못 고르면 한 곳에 몰린다(핫스팟).

- **단조 증가 키(타임스탬프, 순번)** → 항상 마지막 파티션에만 쓰기가 몰린다. 최악의 선택
- **고객사 ID** → 자연스럽지만, **대형 고객사 하나가 전체의 절반**이면 그 파티션만 터진다
- **수신번호 해시** → 고르게 분산되지만 **고객사 단위 순서 보장이 깨진다**

**→ 정답은 요구에 달렸다.** "순서를 어느 단위로 지켜야 하는가"를 먼저 물어야 한다.
- 순서가 필요 없으면 → 균등 분산 우선
- 고객사 단위 순서가 필요하면 → 고객사 ID 키 + **대형 고객사는 별도 처리**

(Kafka 파티션 §[Kafka](../messaging/kafka.md) 2-3, ES 샤드 §[Elasticsearch](../datastore/elasticsearch.md) §2-3이 **전부 같은 원리**다.)

⚠️ 여기서 말하는 파티셔닝은 "여러 노드로 나누는 것"이다. 이름이 같은 다른 얘기가 하나 더 있다. **단일 DB 안에서 테이블을 시간 단위로 쪼개는 테이블 파티셔닝**이다. 보존 기간이 있는 발송 이력에서는 이쪽이 훨씬 자주 쓰인다(`DROP PARTITION`으로 통째로 버리기). → `[DB 인덱스](../database/basics/b-tree-index.md)` §2-12

### 2-8. 벌크 처리는 건당을 묶는다

- **DB**: 건당 INSERT 대신 배치 INSERT. 왕복 횟수가 곧 비용이다
- **채널사 API**: 대량 전송 규격이 있으면 묶어서 보낸다
- **⚠️ 트레이드오프**: 묶으면 실패 단위도 묶인다. 100건을 묶어 보냈는데 하나가 실패하면? **부분 실패를 어떻게 처리할지**가 설계 포인트다
  → 채널사 API가 건별 결과를 돌려주는지 확인해야 한다. 안 돌려주면 묶기 어렵다

### 2-9. 관측 가능성, "조용한 실패"를 잡는 법

**3요소**: 메트릭(수치 추이) / 로그(개별 사건) / 트레이싱(요청 흐름 추적)

**★ 에러 로그만으로는 안 잡히는 실패가 있다.**
- 채널사가 200 OK를 주고 **실제로는 안 보냈을 때**
- 예외를 삼키는 `catch` 블록이 있을 때
- 발송량이 **조용히 절반으로 줄었을 때**. 아무 에러도 안 난다

**→ "에러가 없다"는 "정상"이 아니다.** 필요한 건 성공률과 처리량 지표다.
- 발송 성공률, 채널별 성공률, 시간당 처리량, 큐 적체량(consumer lag)
- **임계치를 벗어나면 알람.** "에러가 났을 때"가 아니라 "평소와 다를 때"다

### 2-10. 채널 확장, 변하는 축을 어댑터 뒤에 가둔다

메시징 플랫폼은 시간이 지나면 **발송 엔진 하나 위에 채널이 계속 쌓이는** 모양이 된다. SMS/LMS/MMS → 알림톡/친구톡 → RCS → 앱 푸시 → 이메일 → 사내 메신저·그룹웨어까지.

설계 관점에서 이게 뜻하는 것은 하나다. **채널이 변하는 축이다.** 그러면 채널을 추상화하고 나머지를 공통으로 두는 게 정답이다.

```
[공통]  발송 요청 접수 → 대상 검증 → 중복 차단(멱등) → 큐 → 워커
                                                          ↓
[가변]                                          채널 어댑터 인터페이스
                                       ┌──────────┬──────────┬──────────┐
                                     SMS       알림톡       RCS      사내메신저
```

**채널마다 다른 것 / 같은 것을 구분할 수 있어야 한다:**

| 채널마다 **다른** 것 | 채널 무관 **공통** |
|---|---|
| 인증 방식, 요청 규격 | 발송 요청 접수·검증 |
| **TPS 제한** | **멱등 처리** |
| **결과 수신 방식** (동기 응답 / 비동기 리포트 / 웹훅) | 재시도·서킷 브레이커 |
| **실패 코드 체계** | 이력 기록·상태 관리 |
| **템플릿 심사 여부** (알림톡은 사전 심사 필요) | 통계·과금 집계 |
| 대체 발송 규칙 (알림톡 실패 → SMS) | 관측 지표 |

이 구조의 값어치는 **채널을 하나 더 붙일 때 기존 발송 흐름을 건드리지 않아도 된다**는 데 있다. 공통 파이프라인은 그대로 두고 어댑터 구현만 추가한다.

**어려운 지점이 하나 있다. 실패 판정 시점이 채널마다 다르다.**
- SMS: 통신사 응답 → 나중에 **결과 리포트**가 따로 온다
- 알림톡: API 응답은 "접수 성공"일 뿐, **실제 도달 여부는 별도 리포트**
- → **"발송 성공"을 언제 확정할 것인가**가 통계·과금 정합성을 좌우한다
- → 그래서 상태를 `접수 / 전송 / 도달 / 실패`로 나눠 두지 않으면, 리포트가 늦게 오는 채널에서 집계가 어긋난다

### 2-11. 외부 플랫폼 정책 변경 대응

**외부 플랫폼(구글·카카오·통신사)이 규칙을 바꾸면 솔루션 전체가 따라가야 한다.** 메시징 도메인에서는 이게 이벤트가 아니라 상시 업무다. FCM 레거시 API 종료, Gmail 대량 발신자 요건처럼 채널 쪽 사정으로 규격이 바뀌는 일이 주기적으로 생긴다.

여기에 **설치형 솔루션은 고객사마다 버전이 다르다**는 조건이 붙으면, 외부 변경 한 번에 전 버전을 훑어야 하는 작업으로 번진다.

**설계 관점의 교훈**: 외부 규격 의존을 어댑터 뒤에 가둬 두면 정책 변경의 충격이 어댑터에서 멈춘다. §2-10의 구조가 곧 이 문제의 대비책이다.

### 2-12. 그 외 어휘 한 줄씩

- **CAP / PACELC**: 분할 시 C냐 A냐. 분할이 없을 때도 지연(L)과 일관성(C)의 거래는 계속된다
- **Fan-out**: 하나의 이벤트를 여러 소비자에게. 발송 이벤트 → 통계·과금·모니터링
- **Outbox 패턴**: DB 트랜잭션과 메시지 발행의 원자성 문제. 같은 트랜잭션으로 outbox 테이블에 쓰고, 별도 프로세스가 그걸 읽어 발행한다. "DB는 커밋됐는데 메시지는 안 나갔다"를 막는다
- **SAGA**: 분산 트랜잭션을 보상 트랜잭션으로. 발송은 되돌릴 수 없어서(문자는 회수 불가) 오히려 멱등이 답
- **블룸 필터**: "확실히 없음"만 판정. 대량 발송의 중복 수신자 1차 필터로 쓸 수 있다
- **Consumer lag**: 컨슈머가 얼마나 뒤처졌나. **큐 시스템의 가장 중요한 지표**

---

> **기준 버전**: 제품 버전에 묶이지 않는 설계 개념 정리. 대조한 것은 §2-2의 429와 §2-4의 서킷 브레이커 동작뿐이고, 나머지는 패턴 서술이다
> **확인한 출처**:
> - [RFC 6585 §4 (429 Too Many Requests)](https://www.rfc-editor.org/rfc/rfc6585.html) — §2-2. 정의 원문, `Retry-After` 허용, *"Responses with the 429 status code MUST NOT be stored by a cache."*
> - [Resilience4j CircuitBreaker 문서](https://resilience4j.readme.io/docs/circuitbreaker) — §2-4. **상태 6종**(CLOSED · OPEN · HALF_OPEN + DISABLED · FORCED_OPEN · METRICS_ONLY), OPEN에서 *"rejects calls with a `CallNotPermittedException`"*, **실패율과 느린 호출 비율 두 임계치**, 전이 전에 *"a minimum number of calls were recorded"*가 필요하다는 조건, `waitDurationInOpenState`·`permittedNumberOfCallsInHalfOpenState`
> - [Resilience4j Retry 문서](https://resilience4j.readme.io/docs/retry) — §2-5. `waitDuration`(기본 500ms)·`intervalFunction`이 있고 `ofExponentialBackoff`·`ofRandomized` 같은 팩토리가 제공된다는 것까지
> - [RabbitMQ Consumer Prefetch](https://www.rabbitmq.com/docs/consumer-prefetch) — §2-2. prefetch가 제한하는 대상이 "받아 가는 개수"가 아니라 **채널·커넥션의 미확인(unacknowledged) 메시지 수**라는 것. 본문을 이 표현으로 고쳤다
> **미확인**:
> - **지터의 근거**(§2-5) — Resilience4j에 랜덤 간격 함수가 있다는 것은 확인했지만, **문서는 지터가 왜 필요한지를 설명하지 않는다.** thundering herd 서술은 통설이고 원전 대조를 하지 못했다
> - **토큰 버킷 / 리키 버킷**(§2-3) — 단일 공식 출처가 없어 대조하지 않았다. 표의 "버스트 허용 / 완전 균일" 구분은 교과서 서술이다
> - **Kafka의 pull 모델이 백프레셔라는 서술**(§2-2) — Kafka 공식 문서의 Design > Push vs. pull 절을 열려 했으나 kafka.apache.org가 본문을 내려 주지 않아 대조하지 못했다
> - **멱등성과 재시도가 세트라는 서술**(§2-5, §2-6) — RFC 9110 §2.4의 *"Some requests can be automatically retried by a client in the event of an underlying connection failure, as described in Section 9.2.2."*까지는 확인했다. **§9.2.2 본문은 문서가 너무 커서 끝까지 읽어 내지 못해 정의문과 멱등 메서드 목록을 원문으로 확보하지 못했다**
> - **3층 방어와 선기록**(§2-6) — 도메인 설계 판단이다. DB 유니크 제약만이 조회-INSERT 사이의 틈을 없앤다는 원리는 [트랜잭션 · 락](../database/basics/transaction-and-lock.md) 쪽 서술에 기대고 있고 여기서 재대조하지 않았다
> - **파티셔닝 핫스팟 · 벌크 처리 · 관측 3요소 · 채널 어댑터 구조**(§2-7 ~ §2-11) — 제품 문서로 확인할 대상이 아닌 설계 서술이다. Kafka 파티션과 ES 샤드의 실물은 각 문서에 있다
> - **CAP / PACELC · Outbox · SAGA**(§2-12) — 어휘 정리 수준이고 원전(Brewer · Abadi 등) 대조를 하지 않았다
> **미작성**: 정확히 한 번(exactly-once) 의미론과 트랜잭셔널 아웃박스의 한계 · 데드레터 큐 운영 · 멀티 리전과 지역 장애 격리 · 셀 기반 아키텍처 · 부하 테스트 설계와 용량 산정 절차 · SLO/에러 버짓
