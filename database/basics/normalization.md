# 쪼개는 규칙과 되돌리는 판단

## 30초 요약

- 정규화는 미적 규칙이 아니다. **[데이터 모델링](data-modeling.md) §2-3의 이상현상을 없애는 절차**이고, 도구는 함수 종속 하나뿐이다
- 단계는 한 문장씩으로 줄어든다. 1NF는 한 칸에 값 하나, 2NF는 키 일부에만 딸린 것 제거, 3NF는 키가 아닌 것에 딸린 것 제거, BCNF는 **결정자가 전부 후보키**
- 흔한 오해가 하나 있다. **2NF는 복합키가 아니면 자동으로 만족된다.** 단일 PK 테이블이라면 사실상 3NF부터 보면 된다
- 쪼갤 때 지켜야 할 것이 둘이다. **무손실 조인**(다시 붙였을 때 원본과 같은가)과 종속성 보존(제약을 조인 없이 검사할 수 있는가)
- **반정규화는 정규화의 실패가 아니라 다음 단계다.** 다만 조건이 붙는다. 읽기가 압도적으로 많고, 갱신 경로가 하나로 통제될 때만이다

---

## 원리 — 왜 그런가

### 2-1. 1NF는 한 칸에 값 하나

```
발송건(발송ID, 수신번호목록)
1,  "010-1111, 010-2222, 010-3333"     ← 위반
```

**왜 안 되나.** `WHERE 수신번호 = '010-2222'`가 인덱스를 못 탄다. 문자열 중간 검색이 되는데, 그건 [DB 인덱스](b-tree-index.md) §2-2에서 본 대로 풀 스캔이다. 개수를 세는 것도, 하나만 지우는 것도 문자열 조작이 된다.

**해법은 행으로 펴는 것**이다. 값 3개면 행 3개.

> **JSON 컬럼은 1NF 위반인가.** 형식적으로는 그렇지만, 현대 DB는 JSON에 인덱스를 걸 수 있어(MySQL 멀티밸류 인덱스, PostgreSQL `jsonb` + GIN) 위 논거가 약해진다. 판단 기준은 "그 안의 값으로 검색·조인·집계를 하는가"다. 한다면 컬럼으로 빼고, 통째로 읽고 쓰기만 하면 JSON도 괜찮다.

### 2-2. 2NF는 키 일부에만 딸린 것을 뺀다

**복합키일 때만 문제가 된다.**

```
발송상세(캠페인ID, 수신번호, 캠페인명, 발송결과)
        └───── 복합 PK ─────┘

캠페인ID          → 캠페인명        ← 키의 "일부"만으로 결정된다 (부분 함수 종속)
캠페인ID, 수신번호 → 발송결과        ← 정상. 키 전체가 필요
```

`캠페인명`은 `수신번호`와 아무 상관이 없는데 같은 테이블에 있다. 이게 §2-3 이상현상의 원인이다.

**분해:**
```
캠페인(캠페인ID, 캠페인명)
발송상세(캠페인ID, 수신번호, 발송결과)
```

> **PK가 단일 컬럼이면 2NF는 자동으로 만족된다.** "키의 일부"라는 게 존재하지 않으니까. 대리키를 쓰는 실무 테이블 대부분이 여기 해당하고, 그래서 실전에서 실제로 보는 건 3NF부터다.

### 2-3. 3NF는 키가 아닌 것에 딸린 것을 뺀다

```
발송건(발송ID, 채널코드, 채널사명, 채널사연락처)

발송ID   → 채널코드              (정상)
채널코드 → 채널사명, 채널사연락처  ← 키가 아닌 것이 다른 것을 결정 (이행 함수 종속)
```

`발송ID → 채널코드 → 채널사명`으로 **한 단계 건너서** 결정된다. 그래서 이행(transitive)이다.

문제는 §2-2와 똑같다. 채널사 연락처가 바뀌면 **그 채널을 쓴 모든 발송건**을 갱신해야 한다.

**분해:**
```
채널(채널코드, 채널사명, 채널사연락처)
발송건(발송ID, 채널코드)
```

3NF를 한 문장으로 줄이면 *"모든 비-키 속성은 **키에 대해서만** 종속되어야 한다."* 흔히 쓰는 표현은 **"키, 오직 키, 키 외에는 아무것도(the key, the whole key, and nothing but the key)"**다. 앞부분이 1NF·2NF, 마지막이 3NF다.

### 2-4. BCNF가 메우는 3NF의 빈틈

3NF는 **"결정하는 쪽이 후보키의 일부일 때"**를 놓친다.

```
강의배정(학생, 과목, 교수)
- 한 교수는 한 과목만 가르친다     →  교수 → 과목
- 학생은 과목마다 교수 한 명에 배정 →  학생, 과목 → 교수

후보키: {학생, 과목}, {학생, 교수}
```

`교수 → 과목`에서 `교수`는 후보키가 아니다(단독으로 행을 식별 못 함). 그런데 `과목`은 후보키 `{학생, 교수}`의 일부라서 3NF 정의상 걸리지 않는다. **3NF는 통과하는데 중복은 그대로 있다.**

BCNF는 더 단순하게 요구한다. **결정자(→의 왼쪽)는 전부 후보키여야 한다.**

> **실무에서 BCNF까지 따질 일은 드물다.** 후보키가 여러 개이고 서로 겹칠 때만 나타나는 상황이라서다. 다만 "3NF면 안전하다"가 참이 아니라는 것은 알아 둘 값어치가 있다.

### 2-5. 쪼갤 때 지켜야 하는 두 가지

아무렇게나 쪼개면 안 된다. **분해에는 지켜야 할 성질이 둘 있고, 둘 다 만족하지 못하는 경우가 실제로 있다.**

**(1) 무손실 조인.** 다시 붙이면 원본이 나오는가

```
원본:  발송(발송ID, 캠페인ID, 수신번호)

나쁜 분해:  A(발송ID, 캠페인ID)   B(캠페인ID, 수신번호)
```

A와 B를 `캠페인ID`로 조인하면 원본에 없던 조합이 생긴다. 캠페인 100에 발송건 2개, 수신번호 2개가 있으면 조인 결과는 4행이다. **정보가 늘어난 게 아니라 망가진 것**이다.

조건은 이렇다. 두 조각의 **공통 속성이 최소한 한쪽의 후보키**여야 한다. 위 분해는 `캠페인ID`가 어느 쪽의 키도 아니라서 깨진다. §2-2~2-4의 분해는 전부 이 조건을 만족한다.

**(2) 종속성 보존.** 제약을 조인 없이 검사할 수 있는가

원본에 있던 함수 종속이 분해 후에도 **한 테이블 안에서** 확인 가능해야 한다. 안 그러면 제약을 지키려고 매번 조인해야 한다.

**무손실 조인은 반드시 지켜야 하고, 종속성 보존은 못 지킬 수도 있다.** BCNF로 밀어붙이면 종속성 보존을 포기해야 하는 경우가 있는데, 그럴 땐 3NF에서 멈추는 게 맞다.

### 2-6. 반정규화는 언제 정당한가

정규화하면 테이블이 늘고 조회에 조인이 붙는다. 그 조인에도 값이 붙는다([쿼리 실행](query-execution.md) §2-2).

**반정규화는 정규화를 안 한 것과 다르다.** 정규화된 모델을 이해한 뒤 의도적으로 되돌리는 것이다. 안 한 것은 사고이고, 되돌린 것은 설계다.

**정당화되는 조건이 셋이고, 셋 다 만족해야 한다.**

1. **읽기가 압도적으로 많다.** 조회 1만 회 : 갱신 1회 같은 비율
2. **갱신 경로가 통제된다.** 그 값을 바꾸는 코드가 한 곳뿐이거나, 갱신을 트리거·이벤트로 확실히 전파할 수 있다
3. **실측한 문제가 있다.** "조인이 많아 보여서"는 근거가 아니다

**발송 도메인의 실제 예:**

```
발송이력(발송ID, 캠페인ID, 캠페인명, ...)   ← 캠페인명을 일부러 복제
```
- 발송 이력 조회 화면이 초당 수백 번 호출되고 **매번 캠페인 테이블과 조인**한다
- 캠페인명은 **캠페인 생성 후 거의 안 바뀐다**
- 이력은 **한 번 쓰고 안 고치는 데이터**라, 애초에 과거 시점의 이름을 남기는 게 오히려 정확하다

**마지막 줄이 중요하다.** 이건 성능을 위한 복제가 아니라 "그 시점의 값을 보존한다"는 요구사항일 수 있다. 주문서에 남는 상품명·가격이 대표적이다. 상품 가격이 바뀌어도 과거 주문의 결제 금액은 바뀌면 안 된다. 이런 건 반정규화가 아니라 **처음부터 다른 사실**이다.

> **반정규화의 진짜 비용은 저장 공간이 아니라 "두 값이 언제부터 달라졌는지 아무도 모르게 되는 것"**이다. 되돌릴 때는 동기화가 깨졌을 때 어떻게 감지할지를 같이 정해야 한다.

### 2-7. 그래서 어디까지 하나

| 상황 | 목표 |
|---|---|
| OLTP 원장 (주문·과금·회원) | **3NF까지.** 정합성이 생명이고 갱신이 잦다 |
| 로그·이력 | 3NF를 고집하지 않는다. **불변이라 갱신 이상이 안 생긴다** |
| 분석·리포트 | **의도적으로 반정규화**(스타 스키마). 읽기 전용이고 조인을 줄이는 게 목적 |

**"불변이면 갱신 이상이 없다"가 실무의 핵심 감각**이다. §2-3의 세 이상현상 중 둘(갱신·삭제)은 데이터가 바뀔 때만 생긴다. 한 번 쓰고 안 고치는 데이터는 정규화 압박이 훨씬 약하다.
