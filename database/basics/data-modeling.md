# 데이터 모델링 — 키와 함수 종속

## 30초 요약

- 지금까지의 DB 문서가 전부 **물리 계층**(저장·인덱스·락)이었다면 여기부터는 **논리 계층**이다 — 어떤 테이블에 무엇을 둘 것인가
- **키의 종류가 여럿인 이유**는 시험용 분류가 아니라, **"유일성"과 "실제로 쓰는 식별자"가 다른 개념**이기 때문이다
- **함수 종속(A → B)** 은 "A가 정해지면 B도 정해진다"는 제약이다. **정규화의 모든 판단이 이 하나 위에 선다**
- 잘못된 모델은 **이상현상(anomaly)** 으로 드러난다 — 삽입·갱신·삭제할 때 **엉뚱한 데이터가 같이 휘말린다**
- 실무 감각 하나: **자연키를 PK로 쓰지 마라.** 현실의 식별자는 생각보다 자주 바뀐다

---

## 원리 — 왜 그런가

### 2-1. 키 — 왜 이름이 이렇게 많은가

키 분류는 **"유일하게 식별할 수 있는가"**와 **"그중 무엇을 실제로 쓸 것인가"**를 나눠 보기 위한 것이다.

```
회원(회원ID, 이메일, 휴대폰, 이름, 가입일)
```

| 이름 | 정의 | 위 예시에서 |
|---|---|---|
| **슈퍼키** | 유일성만 만족. 군더더기 붙어도 됨 | `{회원ID}`, `{회원ID, 이름}`, `{이메일, 가입일}` … |
| **후보키** | 슈퍼키 중 **최소**인 것(하나라도 빼면 유일성 깨짐) | `{회원ID}`, `{이메일}`, `{휴대폰}` |
| **기본키(PK)** | 후보키 중 **골라 쓰기로 한 것** | `{회원ID}` |
| **대체키** | 후보키인데 PK로 안 뽑힌 것 | `{이메일}`, `{휴대폰}` |
| **외래키(FK)** | 다른 테이블의 PK를 참조 | 주문 테이블의 `회원ID` |

**핵심은 "후보키가 여러 개일 수 있다"는 것**이다. 이메일도 휴대폰도 유일하다. 그런데 **PK는 하나만 고른다.** 무엇을 고르느냐가 실무 판단이다.

**자연키 vs 대리키**

- **자연키**: 현실에 이미 존재하는 식별자 — 이메일, 사업자등록번호, 주민번호
- **대리키**: 시스템이 만든 무의미한 번호 — `AUTO_INCREMENT` id, UUID

**대리키를 쓰는 게 거의 항상 옳다.** 이유가 셋이다.

1. **현실의 식별자는 바뀐다.** 이메일 변경, 휴대폰 변경, 사업자번호 승계. PK가 바뀌면 **그걸 참조하는 모든 FK가 같이 바뀌어야 한다**
2. **PK는 물리 구조에 직결된다.** InnoDB에서 PK는 곧 데이터 정렬 순서이고 모든 세컨더리 인덱스에 복제된다([저장과 I/O](storage-and-io.md) §2-6). 이메일(가변 길이 문자열)을 PK로 쓰면 **모든 인덱스가 그만큼 뚱뚱해진다**
3. **개인정보가 키가 되면 못 지운다.** 파기 요청이 와도 PK라서 지울 수 없는 상황이 생긴다

> **다만 자연키를 버리라는 뜻이 아니다.** 이메일은 **UNIQUE 제약**으로 남긴다. **"유일성 보장"과 "식별자로 쓰기"를 분리하는 것**이 요점이다.

### 2-2. 함수 종속 — 정규화의 유일한 도구

**A → B** ("A가 B를 함수적으로 결정한다") = **A 값이 같으면 B 값도 반드시 같다.**

```
발송이력(발송ID, 캠페인ID, 캠페인명, 수신번호, 발송시각)

발송ID  → 수신번호, 발송시각     (발송 건이 정해지면 정해진다)
캠페인ID → 캠페인명              ★ 이게 문제다
```

**★ 표시가 핵심이다.** `캠페인명`은 `발송ID` 전체가 아니라 **`캠페인ID`만 알면 결정된다.** 그런데 이 테이블의 키는 `발송ID`다.

**"키가 아닌 것이 다른 것을 결정하고 있다"** — 이 상태가 모든 문제의 근원이다. 왜냐하면 **같은 사실이 여러 행에 반복 저장**되기 때문이다.

```
발송ID  캠페인ID  캠페인명        수신번호
1       100      "8월 프로모션"   010-...
2       100      "8월 프로모션"   010-...     ← 같은 사실이 또
3       100      "8월 프로모션"   010-...     ← 또
...   (1천만 행)
```

### 2-3. 이상현상 — 중복이 만드는 세 가지 사고

§2-2의 중복은 저장 공간 낭비가 문제가 아니다. **데이터가 틀어지는 경로**를 세 개 만든다.

**(1) 갱신 이상 (update anomaly)**

캠페인명을 "8월 프로모션"에서 "8월 여름 프로모션"으로 바꾼다.

```sql
UPDATE 발송이력 SET 캠페인명 = '8월 여름 프로모션' WHERE 캠페인ID = 100;
-- 1천만 행을 갱신해야 한다
```

느린 것도 문제지만 **진짜 위험은 일부만 갱신되는 경우**다. 중간에 실패하거나 조건을 빠뜨리면 **같은 캠페인인데 이름이 두 종류**가 된다. 이 시점에 **"진짜 이름이 뭔가"에 답할 수 없다.**

**(2) 삽입 이상 (insert anomaly)**

캠페인을 만들었는데 아직 발송을 안 했다. **캠페인을 등록할 자리가 없다** — 발송 이력 행이 있어야만 캠페인명이 존재하니까. 억지로 넣으려면 수신번호를 NULL로 둔 가짜 행을 만들어야 한다.

**(3) 삭제 이상 (delete anomaly)**

보존 기간이 지나 그 캠페인의 발송 이력을 전부 지웠다. **캠페인이 존재했다는 사실 자체가 같이 사라진다.** 지우려던 건 이력이지 캠페인이 아니었는데.

**세 이상현상은 전부 같은 원인이다** — **독립적인 사실이 한 테이블에 섞여 있다.** 캠페인은 캠페인의 생명주기가 있고 발송은 발송의 생명주기가 있는데, 한 곳에 두니 한쪽의 조작이 다른 쪽을 건드린다.

해법은 **함수 종속을 따라 테이블을 쪼개는 것**이고, 그 절차가 [정규화](normalization.md)다.

### 2-4. ER 모델 — 쪼개기 전에 그리는 것

정규화가 "이미 있는 테이블을 고치는" 절차라면, ER 모델은 **처음부터 개체 단위로 생각하는** 방법이다.

- **개체(Entity)**: 독립적으로 존재하고 식별되는 것 — 회원, 캠페인, 발송건
- **속성(Attribute)**: 개체가 갖는 값 — 이름, 생성일
- **관계(Relationship)**: 개체 사이의 연결 — "회원이 캠페인을 만든다"

**실무에서 실제로 판단이 갈리는 건 관계의 차수(cardinality)다.**

| 관계 | 구현 | 예 |
|---|---|---|
| **1:N** | N쪽에 FK를 둔다 | 캠페인 1 : 발송건 N → 발송건이 `캠페인ID`를 가짐 |
| **1:1** | 어느 쪽에든 FK. **대개 한 테이블로 합쳐도 된다** | 회원 : 회원상세 |
| **N:M** | **중간 테이블이 반드시 필요** | 회원 : 태그 → `회원_태그` 테이블 |

**N:M에서 중간 테이블이 필요한 이유가 함수 종속으로 설명된다.** 회원 하나가 태그 여럿을 갖고 태그 하나가 회원 여럿에 붙으면, **어느 쪽에 FK를 둬도 한 칸에 여러 값을 넣어야 한다.** 한 칸에 값 하나만 넣는다는 규칙(1NF)이 깨진다.

> **1:1을 발견하면 합칠지 먼저 검토한다.** 굳이 나누는 정당한 이유는 둘 정도다 — **접근 빈도가 크게 다를 때**(자주 안 읽는 큰 텍스트를 분리해 페이지당 행 수를 늘린다 → [저장과 I/O](storage-and-io.md) §2-1), 그리고 **보안 등급이 다를 때**.

### 2-5. 제약조건 — 모델을 코드가 아니라 DB에 새긴다

함수 종속과 관계를 **DB가 강제하게** 만드는 장치다.

| 제약 | 막는 것 |
|---|---|
| `PRIMARY KEY` | 중복·NULL 식별자 |
| `UNIQUE` | 후보키의 중복 (§2-1의 이메일·휴대폰) |
| `FOREIGN KEY` | **존재하지 않는 것을 참조하는 행** |
| `NOT NULL` | 필수 값 누락 |
| `CHECK` | 도메인 위반 (상태값이 정해진 집합 밖) |

**애플리케이션에서 검사하면 되지 않나** — 안 된다. **애플리케이션은 여러 개이고 DB는 하나**다. 배치 스크립트, 운영자의 수동 쿼리, 다른 팀의 서비스가 전부 같은 테이블에 쓴다. **제약을 DB에 두면 그 모든 경로에 한 번에 적용된다.**

**특히 UNIQUE 제약은 이 저장소에서 반복해서 최종 방어선으로 등장한다.** Redis 멱등키도([Redis](../../datastore/redis.md) §2-5), 분산락도, 애플리케이션 중복 체크도 전부 **빠른 사전 차단**일 뿐이다. 경합 상황에서 마지막으로 막아 주는 건 **DB의 UNIQUE 제약 하나**다.

> FK를 안 거는 팀도 있다. 이유는 대개 성능(참조 검사 비용)이나 운영 유연성(대량 삭제·마이그레이션)인데, **거래를 안다면 정당한 선택**이다. 다만 **"FK가 없으니 고아 데이터가 생길 수 있다"를 알고 그 검증을 어딘가에 두는 것**이 조건이다. 모르고 안 거는 것과는 다르다.
