# DB 인덱스 — B+Tree는 왜 그렇게 생겼나

## 30초 요약

- **B+Tree는 관계형 DB의 기본값이지 유일한 인덱스가 아니다** — 해시 · LSM-Tree · 역색인 · BRIN이 각자 이기는 자리가 따로 있다 (§2-2)
- B+Tree는 **리프에만 데이터**가 있고 **리프끼리 양방향 연결**돼 있다(→ 범위 스캔이 순차 읽기). 노드 하나 = **디스크 페이지 하나(InnoDB 16KB)**라 **깊이 1단 = 디스크 I/O 1회**이고, 깊이가 곧 비용이다
- InnoDB는 **PK 순서로 데이터가 물리 정렬**된다(클러스터드). 세컨더리 인덱스는 **값 + PK만** 갖는다
- 인덱스는 **컬럼 원본 값 기준으로 정렬**돼 있다 → 컬럼에 함수를 씌우면 그 정렬을 못 쓴다 → 풀 스캔
- 인덱스는 공짜가 아니다 — **쓰기마다 갱신**된다. 그래서 쓰기 많은 테이블에선 **추가가 아니라 대체**다

---

## 원리 — 왜 그런가

### 2-1. 왜 B-Tree가 아니라 B+Tree인가

먼저 **왜 트리인가**부터. DB 인덱스가 풀어야 할 문제는 "디스크에 있는 수천만 건에서 조건에 맞는 것을 찾기"다. 여기서 지배적인 비용은 **CPU 연산이 아니라 디스크 I/O 횟수**다. 메모리 접근이 나노초 단위라면 디스크(SSD도) 접근은 마이크로초~밀리초 단위다. **1000배 이상 차이**가 난다.

그래서 자료구조 선택 기준이 "비교를 몇 번 하는가"가 아니라 **"디스크를 몇 번 읽는가"**가 된다.

- **이진 탐색 트리**: 노드 하나에 키 하나. 1억 건이면 깊이가 27단 → **디스크 읽기 27회**. 탈락
- **B-Tree**: 노드 하나에 키를 여러 개 담는다 → 깊이가 확 줄어든다. 여기까지가 B-Tree의 아이디어
- **B+Tree**: B-Tree에서 한 걸음 더 — **데이터를 리프로 몰아낸다**

**B+Tree가 B-Tree보다 나은 이유 두 가지:**

**(1) 내부 노드가 더 많은 키를 담는다 → 트리가 더 얕아진다**

B-Tree는 내부 노드에도 실제 데이터(또는 데이터 포인터)가 붙어 있다. 노드 크기는 디스크 페이지 크기로 고정(InnoDB 16KB)이므로, 데이터가 자리를 차지하는 만큼 **담을 수 있는 키 개수가 줄어든다**. 키가 적으면 자식도 적고, 자식이 적으면 트리가 깊어진다.

B+Tree의 내부 노드는 **길잡이 키 + 자식 포인터**만 갖는다. 데이터가 없으니 같은 16KB에 훨씬 많이 들어간다.

**대략적인 계산** (감각용, 정확한 수치가 아니라 자릿수):
```
내부 노드 1개 = 16KB
엔트리 1개 = 키(BIGINT 8B) + 자식 페이지 번호(4B) ≈ 12B
→ 노드 하나가 가리키는 자식 수(팬아웃) ≈ 16384 / 12 ≈ 1,300개
   (오버헤드가 있으니 보수적으로 1,000으로 잡고 계산한다)

리프 노드 1개 = 16KB, 행 하나가 128B라면 → 약 128행

깊이 2 (루트 + 리프)        : 1,000 × 128        ≈ 12만 건
깊이 3 (루트 + 중간 + 리프)  : 1,000 × 1,000 × 128 ≈ 1억 건
```
→ **깊이 3~4면 수천만~수억 건이 커버된다**는 말이 여기서 나온다. 그리고 루트와 상위 노드는 버퍼 풀에 캐시되므로 **실제 디스크 I/O는 사실상 리프 1회**에 가깝다.

**(2) 리프끼리 연결돼 있어 범위 스캔이 순차 읽기가 된다**

B-Tree는 데이터가 트리 전체에 흩어져 있어서, `BETWEEN`이나 `ORDER BY`처럼 연속된 구간을 읽으려면 **트리를 위아래로 오르내려야 한다**(중위 순회). 매번 랜덤 I/O다.

B+Tree는 리프가 양방향 연결 리스트다. 시작점 하나만 찾으면 **옆으로 쭉 따라가면 끝**이다. 그리고 리프는 디스크에 대체로 인접해 있어 **순차 읽기**가 된다.

> **한 줄로 정리하면**: "B+Tree를 쓰는 이유는 결국 두 개입니다. 내부 노드에서 데이터를 빼서 트리를 얕게 만든 것, 그리고 리프를 연결해서 범위 조회를 순차 읽기로 만든 것입니다."

### 2-2. 인덱스가 전부 B+Tree는 아니다 — 다른 자료구조들

**먼저 범위를 분명히 해 둔다. B+Tree는 관계형 DB의 기본값이지 "인덱스 = B+Tree"가 아니다.** 이 문서의 나머지가 전부 B+Tree 이야기라서 오해하기 쉬운데, 실제로는 자료구조가 여럿이고 각자 이기는 자리가 따로 있다.

| 자료구조 | 쓰이는 곳 | 잘하는 것 | 못하는 것 |
|---|---|---|---|
| **B+Tree** | InnoDB의 모든 인덱스, PostgreSQL 기본 인덱스 | 등치 · 범위 · 정렬 · 앞고정 `LIKE` | 전문 검색, 다차원 |
| **해시** | MySQL MEMORY 엔진, InnoDB Adaptive Hash Index, PostgreSQL `hash` | 등치 O(1) | 범위 · 정렬 · 접두 **전부 불가** |
| **LSM-Tree** | RocksDB, Cassandra, HBase | **쓰기 처리량** — 랜덤 쓰기를 순차 쓰기로 몰아낸다 | 읽기 증폭, 컴팩션이 주기적으로 I/O를 먹음 |
| **역색인** | Elasticsearch, PostgreSQL `GIN` | 문서 **안의 단어**로 찾기, 배열 원소 포함 검사 | 범위 · 정렬 |
| **R-Tree 계열** | PostgreSQL `GiST`, MySQL `SPATIAL` | 공간 · 다차원 겹침 질의 | 일반 등치 조회 |
| **블록 범위 요약** | PostgreSQL `BRIN` | 물리 순서와 상관된 대용량(시계열)을 **극소 용량**으로 | 상관이 깨지면 사실상 무용지물 |
| **비트맵** | Oracle, 분석용 DB | 카디널리티 낮은 컬럼들의 조합 조건 | 동시 쓰기 (갱신 시 광범위 락) |

그래서 질문은 "왜 B+Tree인가"가 아니라 **"왜 B+Tree가 기본값 자리를 차지했는가"**가 맞다. 답은 §2-1(디스크 I/O 횟수를 최소화한다)에 더해, **하나로 대부분의 쿼리 형태를 커버한다**는 점이다. 비교 대상으로 해시를 놓으면 그게 드러난다.

**해시는 왜 기본값이 못 되나** — 등치 조회는 O(1)이라 이론상 더 빠른데도 안 쓴다. **해시 함수가 순서를 파괴하기 때문**이다.

- `WHERE id = 5` → 가능
- `WHERE id BETWEEN 5 AND 100` → **불가능**. hash(5)와 hash(100) 사이에 뭐가 있는지 알 수 없다
- `ORDER BY id` → **불가능**
- `WHERE name LIKE '김%'` → **불가능**
- 복합 인덱스의 앞부분만 쓰기 → **불가능**. 해시는 전체 키를 통째로 해싱한다

실제 쿼리는 범위·정렬·접두 검색이 대부분이다. **한 가지만 잘하는 도구보다 전부 되는 도구가 기본값이 된다.**

> **용어 주의 두 가지.**
> **①** PostgreSQL **공식 문서는 기본 인덱스를 "B-tree"라고 부른다** — "B+tree"나 Lehman-Yao라는 표현은 사용자 문서에 나오지 않는다. 실제 구현은 리프에 데이터를 두고 리프를 연결한 B+Tree 계열이지만, **문서에서 그 이름을 찾으려 하면 없다.**
> **②** PostgreSQL에 **비트맵 *인덱스*는 없다.** 실행계획에 나오는 `Bitmap Index Scan`은 저장된 인덱스 종류가 아니라 **여러 인덱스 결과를 실행 중에 비트맵으로 합치는 기법**이다. 이름이 같아서 자주 혼동된다.
>
> 각 타입의 실제 사용법은 `postgresql/heap-and-index.md`에서 다룬다.

### 2-3. InnoDB 클러스터드 인덱스 — PK가 곧 데이터다

InnoDB에서 **PK 인덱스는 인덱스가 아니라 테이블 그 자체**다. 리프 노드에 행 전체가 들어 있다. 즉 **데이터가 PK 순서로 디스크에 물리 정렬**돼 있다.

여기서 파생되는 결과들:

**(1) PK 순서대로 INSERT하는 게 유리하다**
AUTO_INCREMENT PK는 항상 맨 끝에 append된다 → 마지막 페이지만 건드린다.
반대로 **UUID v4를 PK로 쓰면** 삽입 위치가 랜덤이다 → 중간 페이지에 끼워 넣어야 하고, 페이지가 꽉 차 있으면 **페이지 분할(page split)**이 일어난다. 분할은 (a) 쓰기 비용, (b) 페이지 단편화(빈 공간 증가 → 같은 데이터에 더 많은 페이지 → 캐시 효율 하락)를 부른다.

**(2) PK를 짧게 잡아야 한다**
세컨더리 인덱스는 리프에 **인덱스 컬럼 값 + PK**를 갖는다. PK가 길면 **모든 세컨더리 인덱스가 그 길이만큼 뚱뚱해진다.** UUID(16B, 문자열이면 36B)를 PK로 쓰면 세컨더리 인덱스 5개가 전부 그 비용을 나눠 낸다.

**(3) 세컨더리 인덱스 조회는 두 번 탄다**
`WHERE phone = '010...'` 로 세컨더리 인덱스를 타면 → 리프에서 **PK를 얻고** → 그 PK로 **클러스터드 인덱스를 다시 탐색**한다. 이걸 북마크 룩업 / 테이블 액세스라고 부른다. **랜덤 I/O 한 번이 추가된다.**

### 2-4. 커버링 인덱스 — 왜 그렇게 효과가 큰가

2-3(3)의 두 번째 탐색을 **아예 없애는 것**이 커버링 인덱스다. 쿼리가 필요로 하는 **모든 컬럼이 인덱스 안에 이미 들어 있으면**, 테이블(클러스터드 인덱스)에 갈 이유가 없다.

```sql
-- 인덱스: (status, reserved_at, id)
SELECT id, reserved_at FROM send_reserve WHERE status = 'READY' AND reserved_at < NOW();
-- 필요한 컬럼이 전부 인덱스 안에 있음 → 테이블 접근 0회
```
`EXPLAIN`의 `Extra`에 **`Using index`**가 뜨면 커버링이다. (`Using index condition`은 다른 것 — 인덱스 컨디션 푸시다운)

효과가 큰 이유: 1000건을 조회한다면 북마크 룩업이 **1000번의 랜덤 I/O**다. 커버링이면 0번이다.

### 2-5. 복합 인덱스 — 왜 leftmost prefix인가

`(A, B, C)` 복합 인덱스는 **A로 먼저 정렬하고, A가 같은 것끼리 B로 정렬하고, 그 안에서 C로 정렬**한 것이다. 전화번호부가 (성, 이름) 순으로 정렬된 것과 같다.

- **성을 알면** 찾을 수 있다 → `A` 조회 가능
- **성과 이름을 알면** 더 정확히 찾는다 → `A + B` 가능
- **이름만 알면?** → 전화번호부 전체를 뒤져야 한다. **`B`만으로는 못 쓴다**

이게 leftmost prefix다. "왼쪽부터 연속으로" 써야 한다.

**순서 원칙: 등치 조건을 앞에, 범위 조건을 뒤에.**

이유도 정렬로 설명된다. `WHERE A = 1 AND B > 10 AND C = 5` 에 `(A, B, C)` 인덱스가 있다면:
- `A = 1` 로 구간이 좁혀진다 (정렬 이용 O)
- 그 안에서 `B > 10` 으로 시작 지점을 찾는다 (정렬 이용 O)
- **B가 범위이므로, 그 구간 안에서 C는 정렬돼 있지 않다** → `C = 5`는 인덱스로 못 찾고, 읽어온 행을 하나씩 **필터링**만 한다

→ 그래서 `(A, C, B)` 로 잡으면 세 조건이 전부 인덱스 탐색에 쓰인다. **범위 조건 뒤의 컬럼은 탐색이 아니라 필터가 된다**는 게 핵심.

`ORDER BY`도 같은 원리다. 인덱스 순서와 `ORDER BY` 순서가 맞으면 정렬 자체가 공짜다. 안 맞으면 `Using filesort`.

### 2-6. 왜 컬럼에 함수를 씌우면 인덱스를 못 타나

**인덱스는 컬럼의 원본 값을 기준으로 정렬돼 있다.** 이 문장이 전부다.

```sql
-- 인덱스를 못 탐
WHERE DATE_ADD(reserved_at, INTERVAL 1 DAY) < NOW()
```

인덱스는 `reserved_at` 값 순으로 줄 세워져 있다. 그런데 조건은 `DATE_ADD(reserved_at, ...)`에 대한 것이다. **DB는 "reserved_at이 정렬돼 있으면 DATE_ADD(reserved_at)도 같은 순서로 정렬된다"는 것을 알지 못한다.** (사람은 알지만, 옵티마이저는 함수의 단조성을 보장받지 못한다.)

그러면 조건을 만족하는 구간이 인덱스의 어디서 시작하는지 알 수 없다 → **모든 행에 함수를 적용해서 확인**할 수밖에 없다 → 풀 스캔.

**해법은 조건을 컬럼 원본에 대한 범위로 이항하는 것**:
```sql
WHERE reserved_at < NOW() - INTERVAL 1 DAY
```
이제 조건이 `reserved_at` 자체에 대한 것이 되었다 → 인덱스에서 시작점을 바로 찾을 수 있다.

**같은 함정의 다른 얼굴들** (전부 원리가 같다):
- `WHERE YEAR(created_at) = 2026` → `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'`
- `WHERE phone LIKE '%1234'` → 접두가 없으니 시작점을 못 찾는다. `'010%'` 는 탄다
- **암묵적 형변환**: `phone`이 VARCHAR인데 `WHERE phone = 01012345678` (숫자)로 조회하면 DB가 컬럼 쪽을 숫자로 캐스팅한다 → **컬럼에 함수를 씌운 것과 동일** → 인덱스 못 탐. 실무에서 제일 자주 밟는 지뢰
- `WHERE col + 1 = 10` → `WHERE col = 9`

> MySQL 8.0.13+는 함수 기반 인덱스를 지원한다. 다만 **범위 조건으로 이항할 수 있으면 그게 먼저**다 — 인덱스를 새로 만들지 않아도 되니까.

### 2-7. 카디널리티와 옵티마이저 — 인덱스가 있는데도 안 타는 경우

**카디널리티** = 해당 컬럼의 고유값 개수. 높을수록(중복이 적을수록) 한 번의 탐색으로 걸러지는 양이 많다.

`status` 컬럼처럼 값이 3종류뿐이면(카디널리티 3), `WHERE status = 'READY'` 로 전체의 1/3이 걸러진다. 이때 **옵티마이저는 인덱스를 일부러 안 탈 수도 있다.**

이유는 2-3(3)의 북마크 룩업이다. 전체의 30%를 세컨더리 인덱스로 읽으면 **랜덤 I/O가 30만 번**이지만, 풀 스캔은 **순차 I/O 한 번**이다. 순차가 랜덤보다 압도적으로 빠르므로 **풀 스캔이 이긴다.** 대략 전체의 20~30%를 넘게 읽어야 하면 옵티마이저는 인덱스를 버린다.

→ **"인덱스를 만들었는데 왜 안 타나요?"의 가장 흔한 답이 이것이다.** 통계 정보가 낡은 경우(`ANALYZE TABLE`)도 있다.

- 확인 방법: `SHOW INDEX FROM t` 의 `Cardinality` 컬럼 / `information_schema.STATISTICS` / `SELECT COUNT(DISTINCT col)`
- ⚠️ `SHOW INDEX`의 Cardinality는 **샘플링 기반 추정치**다. 정확한 값이 아니다

### 2-8. 인덱스의 비용

인덱스는 **읽기를 위해 쓰기를 파는 거래**다.

- **INSERT**: 인덱스 개수만큼 B+Tree에 삽입이 일어난다. 인덱스 5개면 쓰기가 6번(테이블 1 + 인덱스 5)
- **UPDATE**: 인덱스 컬럼을 바꾸면 트리에서 **삭제 후 재삽입**이다. 위치가 바뀌니까
- **DELETE**: 모든 인덱스에서 지워야 한다
- **페이지 분할**: 삽입 위치의 페이지가 꽉 차면 반으로 쪼갠다. 순간적으로 비싸고, 단편화를 남긴다
- **저장 공간**: 세컨더리 인덱스는 (인덱스 컬럼 + PK)를 통째로 복제한다. 인덱스가 테이블보다 커지는 것도 흔하다
- **버퍼 풀 경쟁**: 인덱스도 메모리를 먹는다. 안 쓰는 인덱스가 캐시를 밀어낸다

**발송 이력처럼 쓰기가 지배적인 테이블**에 인덱스를 하나 더 얹는다는 것은, 조회 한 번을 살리려고 **모든 쓰기의 처리량을 깎는 것**이다. 그래서 이런 테이블에서는 **추가가 아니라 대체를 먼저 검토한다** — 기존 인덱스의 컬럼 순서를 바꿔 새 쿼리까지 태울 수 있으면, 인덱스 개수를 늘리지 않고 끝난다.

### 2-9. EXPLAIN 읽는 법

| 컬럼 | 봐야 할 것 |
|---|---|
| `type` | `ALL`(풀스캔) < `index`(인덱스 풀스캔) < `range` < `ref` < `eq_ref` < `const`. **`ALL`이면 일단 의심** |
| `key` | 실제로 탄 인덱스. `NULL`이면 못 탔다 |
| `key_len` | **복합 인덱스를 어디까지 썼는지**. `(A,B,C)` 중 A만 탔는지 A+B까지 탔는지가 여기서 보인다 |
| `rows` | 옵티마이저의 **추정** 스캔 행 수 |
| `filtered` | 조건으로 걸러질 비율(%). `rows × filtered`가 실제 결과 예상치 |
| `Extra` | `Using index`(커버링, 좋음) / `Using where` / **`Using filesort`**(정렬 별도 수행) / **`Using temporary`**(임시 테이블, 나쁨) |

- **`EXPLAIN ANALYZE`(MySQL 8.0.18+)**는 쿼리를 **실제로 실행**해서 단계별 실측 시간과 실제 행 수를 보여준다. 추정치인 `rows`와 실제가 크게 다르면 **통계가 낡았다는 신호**
- `type: index`는 함정이다 — 인덱스를 "탔다"가 아니라 **인덱스 전체를 스캔**했다는 뜻이라 대체로 나쁘다

### 2-10. 느린 쿼리를 어떻게 **찾나** — EXPLAIN 앞 단계

**EXPLAIN은 범인을 이미 안 뒤에 쓰는 도구다.** 범인을 찾는 도구는 따로 있다. 조사 순서는 거의 항상 3단이다:

> **"느려진 걸 어떻게 알았나 → 어떤 쿼리인지 어떻게 찾았나 → 왜 느렸나"**

앞의 두 단계가 비면 "운 좋게 눈에 띈 것"이 된다.

| 단계 | 도구 | 무엇을 보나 |
|---|---|---|
| **① 알아챈다** | APM, 응답시간 지표 | p99 응답시간, 특정 API의 지연 증가 |
| **② 후보를 좁힌다** | **`slow_query_log`** | `long_query_time` 초과 쿼리. `log_queries_not_using_indexes`로 인덱스 못 탄 것만 뽑을 수도 있다 |
| | `performance_schema` / `sys` 스키마 | `sys.statement_analysis` — **총 실행시간 기준 상위 쿼리**. 한 건은 빠른데 호출이 100만 번인 쿼리는 슬로우 로그에 안 잡힌다 |
| **③ 원인을 판정한다** | `EXPLAIN` / `EXPLAIN ANALYZE` | 여기서부터가 §2-9 |
| **④ 재측정한다** | 같은 지표 | 고쳤다고 끝이 아니다 |

**②에서 두 도구를 구분하는 게 포인트다.** 슬로우 로그는 **한 방에 느린 쿼리**를 잡고, `sys.statement_analysis`는 **자주 불려서 총합이 큰 쿼리**를 잡는다. 후자가 실제로 더 자주 문제다.

> ⚠️ **`slow_query_log`는 운영에서 기본이 꺼져 있는 경우가 많다.** "켜져 있었나"부터가 확인 사항이다.

### 2-11. 딥 페이징 — `LIMIT 1000000, 20`이 왜 느린가

**OFFSET은 건너뛰는 게 아니라 읽고 버리는 것이다.** 100만 건을 실제로 읽어서 998만... 아니, 100만 건을 읽고 그중 20건만 반환한다. 뒤로 갈수록 선형으로 느려진다.

**해법 1 — 커서(seek) 방식.** 페이지 번호 대신 **마지막으로 본 값**을 기준으로 잡는다.
```sql
-- 나쁨
SELECT * FROM send_history ORDER BY id DESC LIMIT 1000000, 20;
-- 좋음
SELECT * FROM send_history WHERE id < :last_seen_id ORDER BY id DESC LIMIT 20;
```
→ 인덱스에서 시작점을 바로 찾으니 **몇 번째 페이지든 같은 속도**다.
→ 대신 **임의 페이지 점프(7페이지로 바로)가 안 된다.** 무한 스크롤에는 완벽하고, 페이지 번호 UI에는 안 맞는다

**해법 2 — 커버링 인덱스로 PK만 먼저.** 페이지 UI를 포기할 수 없을 때.
```sql
SELECT h.* FROM send_history h
JOIN (SELECT id FROM send_history ORDER BY id DESC LIMIT 1000000, 20) t ON h.id = t.id;
```
→ 서브쿼리는 **인덱스만 읽고**(커버링, §2-4) 100만 건을 훑으므로 훨씬 싸다. 본체 조회는 20건만.

**발송 도메인 연결**: 발송 결과 조회 화면이 정확히 이 문제다. 캠페인 하나에 1천만 건인데 페이지 번호로 넘기면 뒤로 갈수록 죽는다. **[Elasticsearch](../../datastore/elasticsearch.md)의 `search_after`도 같은 발상의 ES판**이다.

### 2-12. 테이블 파티셔닝 — 보존 정책의 정석

메시징 제품의 흔한 정책이 **"상세 내역은 최근 3개월까지만 조회, 이후엔 성공/실패 건수만"** 이다. 이걸 RDB로 구현한다면 답은 파티셔닝이다.

```sql
PARTITION BY RANGE (TO_DAYS(created_at)) (
  PARTITION p202606 VALUES LESS THAN (TO_DAYS('2026-07-01')),
  PARTITION p202607 VALUES LESS THAN (TO_DAYS('2026-08-01')), ...
)
```

**왜 파티셔닝인가 — DELETE와 비교하면 명확하다**

| | `DELETE WHERE created_at < ?` | `ALTER TABLE ... DROP PARTITION` |
|---|---|---|
| 시간 | 1억 건이면 몇 시간 | **즉시** (파일 삭제) |
| undo 로그 | 지운 만큼 전부 쌓인다 | 없음 |
| 락 | 행 단위 락이 대량으로 | 메타데이터 락 잠깐 |
| 복제 지연 | **심각** (슬레이브가 같은 DELETE를 다시 수행) | 거의 없음 |
| 공간 반환 | 안 된다 (`OPTIMIZE TABLE` 별도 필요) | **즉시 반환** |

**파티션 프루닝**: `WHERE created_at BETWEEN ...` 처럼 **파티션 키가 조건에 있어야** 해당 파티션만 스캔한다. 없으면 전 파티션을 다 뒤진다 — **파티셔닝했는데 더 느려지는 전형적 실패**가 이것이다.

> ⚠️ **MySQL의 결정적 제약**: **파티션 키는 테이블의 모든 유니크 인덱스(PK 포함)에 포함돼야 한다.**
> 즉 PK가 `id`라면 `PARTITION BY RANGE(created_at)`을 못 쓴다. PK를 `(id, created_at)`으로 바꿔야 한다.
> → **이게 실무에서 파티셔닝 도입을 막는 가장 큰 걸림돌**이다. 설계 단계에서 PK를 정할 때 미리 고려해야 한다.

**정리 한 줄**: **보존 기간이 있는 대용량 이력은 "지우는 설계"를 처음부터 해야 한다.** 파티셔닝(RDB)이든 시계열 인덱스+ILM(ES, →[Elasticsearch](../../datastore/elasticsearch.md) §2-6)이든, 발상은 같다 — **행 단위로 지우지 말고 덩어리째 버려라.**

### 2-13. 암호화 컬럼과 인덱스 — 개인정보의 함정

**수신번호는 개인정보다.** 고객사가 카드사·항공사인 회사에서 이 얘기가 안 나올 리 없다. 그런데 **암호화하는 순간 §2-6과 같은 문제가 생긴다.**

**왜 인덱스가 무력해지나**
- 인덱스는 **컬럼 값의 정렬**이다(§2-6). 암호문은 원문과 정렬 순서가 **완전히 무관**하다
- → **범위 검색 불가, `LIKE '010%'` 불가, `ORDER BY` 무의미**
- 등치 검색조차 **같은 키·같은 IV로 암호화해야** 가능하다. 그런데 IV를 고정하면(결정적 암호화) **같은 번호는 항상 같은 암호문** → 빈도 분석에 취약해진다

**실무 해법 — 검색용 컬럼을 분리한다**

| 컬럼 | 용도 | 방식 |
|---|---|---|
| `phone_enc` | 실제 저장·복호화 | AES 양방향. **인덱스 안 건다** |
| `phone_hash` | **검색용** | HMAC-SHA256(고정 솔트). **여기에 인덱스** |
| `phone_masked` | 화면 표시 | `010-****-5678` |

→ 등치 검색은 `WHERE phone_hash = HMAC(:input)` 으로 인덱스를 탄다.
→ **범위 검색은 여전히 불가능하다.** 그건 포기하거나 다른 축(고객사·기간)으로 조회한다.

**[Elasticsearch](../../datastore/elasticsearch.md) 설계의 전제를 흔든다**: ES에 발송 상세를 넣고 "수신번호로 자유 검색"한다고 썼는데, **암호화 정책이 있으면 ES에도 평문 번호를 못 넣는다.** ES에도 해시를 넣고 해시로 검색해야 한다. → **[Elasticsearch](../../datastore/elasticsearch.md) §2-2의 `keyword` 필드가 사실은 해시값**이 된다.

> **설계할 때 이걸 먼저 짚어야 한다.** "발송 상세를 ES에 넣겠다"까지는 누구나 말한다. **"다만 수신번호가 개인정보라 평문으로는 못 넣고, 검색용 해시 컬럼을 따로 두는 구조가 될 것 같습니다"**까지 가면 도메인을 아는 사람이 된다.
