# 동시성 제어 이론 — 격리 수준은 어디서 나왔나

## 30초 요약

- [트랜잭션 · 락](transaction-and-lock.md)이 **격리 수준을 이상현상 목록으로** 설명했다면, 여기는 **그 목록이 어디서 나왔는지**다
- 기준은 하나다 — **직렬 가능성(serializability)**. "동시에 실행했는데 **한 줄로 세워 실행한 것과 결과가 같은가**"
- **2PL(2단계 락)** 은 그걸 보장하는 방법이다. **락을 늘리는 단계와 푸는 단계를 섞지 않으면** 직렬 가능해진다
- 그런데 2PL만으로는 **연쇄 롤백**이 생긴다 → 그래서 실제 DB는 **락을 커밋까지 쥐는 Strict 2PL**을 쓴다
- **의도 락은 다중 입도 락의 부품**이다. "행 락이 걸린 테이블에 테이블 락을 걸려는" 충돌을 **전수 검사 없이** 잡기 위한 장치다

---

## 원리 — 왜 그런가

> [트랜잭션 · 락](transaction-and-lock.md) §2-2는 격리 수준을 "무엇을 막고 무엇이 남는가"로 설명했다. 그 표는 **결과**다. 이 문서는 그 결과가 나온 **기준**을 다룬다.

### 2-1. 무엇이 "올바른 동시 실행"인가

동시 실행의 정답을 정의해야 한다. 기준은 의외로 단순하다.

> **트랜잭션들을 한 줄로 세워 하나씩 실행한 결과와 같으면 올바르다.**

이걸 **직렬 가능(serializable)** 하다고 한다. 순서는 아무거나 좋다 — T1→T2든 T2→T1이든, **어떤 순차 실행과든 결과가 같기만 하면** 된다.

**왜 이 기준인가.** 순차 실행은 정의상 안전하다(간섭이 없으니까). 그런데 순차로만 돌리면 처리량이 죽는다. 그래서 **"실제로는 섞어 돌리되, 결과는 순차와 구분이 안 되게"** 만드는 게 목표가 된다. **동시성은 성능을 위한 것이고, 직렬 가능성은 그 성능이 정확성을 깨지 않았다는 증명서**다.

### 2-2. 충돌 — 무엇이 순서를 결정하나

두 연산이 **다른 트랜잭션이고, 같은 데이터를 건드리고, 최소 하나가 쓰기**면 **충돌(conflict)** 한다.

| 조합 | 충돌? |
|---|---|
| read - read | **아니다.** 순서를 바꿔도 결과가 같다 |
| read - write | 충돌 |
| write - read | 충돌 |
| write - write | 충돌 |

**충돌하지 않는 연산은 순서를 바꿔도 된다.** 그래서 판정법이 나온다 — **충돌하는 연산들의 순서만 유지한 채 나머지를 재배열해서 순차 실행 모양을 만들 수 있으면** 직렬 가능하다(**충돌 직렬 가능성**).

```
T1: read(A) ... write(A)
T2:        read(A) ...          ← T1의 write와 충돌. 순서가 고정된다
```

**"read끼리는 충돌하지 않는다"는 한 줄이 MVCC의 근거**다([트랜잭션 · 락](transaction-and-lock.md) §2-3). 읽기가 서로를 막을 이유가 없으니 락을 안 잡아도 된다.

### 2-3. 2PL — 직렬 가능성을 보장하는 규칙

충돌 그래프를 매번 그려서 검사할 수는 없다. **규칙만 지키면 자동으로 직렬 가능해지는 방법**이 필요하다. 그게 **2단계 락(Two-Phase Locking)** 이다.

```
확장 단계(growing) : 락을 획득만 한다. 해제 금지
────────── 정점 ──────────
축소 단계(shrinking): 락을 해제만 한다. 획득 금지
```

**규칙 하나뿐이다 — 한 번 락을 풀기 시작하면 다시는 새 락을 잡지 않는다.**

**왜 이게 직렬 가능성을 보장하나.** 각 트랜잭션의 "정점"(마지막 락 획득 시점)을 그 트랜잭션의 순서로 삼으면, **모든 충돌이 그 순서와 일치**하게 된다. 락을 쥐고 있는 동안은 아무도 그 데이터를 못 건드리니까.

**대가는 동시성이다.** 락을 일찍 잡고 늦게 푸니 대기가 길어진다. 그리고 **2PL은 데드락을 막지 못한다** — 서로가 확장 단계에서 상대의 락을 기다리면 그대로 순환이다([트랜잭션 · 락](transaction-and-lock.md) §2-7).

### 2-4. Strict 2PL — 왜 커밋까지 쥐고 있나

2PL만으로는 문제가 하나 남는다.

```
T1: write(A) → A의 락 해제 (축소 단계, 아직 커밋 전)
T2: read(A)  → 커밋 안 된 값을 읽음
T1: 롤백!
T2: 이미 틀린 값으로 계산했다 → T2도 롤백해야 한다
T3: T2의 결과를 읽었다면 → T3도 롤백
```

**연쇄 롤백(cascading rollback)** 이다. 하나가 죽으면 줄줄이 딸려 죽는다.

**해법: 락을 커밋(또는 롤백)까지 쥔다.** 이게 **Strict 2PL**이고, **실제 DB가 쓰는 것**이다.

```
2PL        : 축소 단계에서 락을 하나씩 푼다
Strict 2PL : 쓰기 락은 커밋 시점까지 전부 쥐고 있다가 한꺼번에 푼다
```

여기서 [트랜잭션 · 락](transaction-and-lock.md)의 실무 조언이 이론적 근거를 얻는다 — **"트랜잭션을 짧게 하라"가 왜 근본 조치인가.** Strict 2PL에서 **락 보유 시간 = 트랜잭션 길이**이기 때문이다. 트랜잭션 안에 외부 API 호출을 넣으면 **그 네트워크 대기 시간 내내 락을 쥐고 있는 것**이 된다.

### 2-5. 다중 입도 락 — 의도 락은 왜 있나

지금까지는 "데이터 하나"를 잠근다고 했다. 실제로는 **잠글 수 있는 단위가 여럿**이다 — 행, 페이지, 테이블.

**여기서 문제가 생긴다.**

```
T1: 어떤 테이블의 행 하나에 배타 락을 걸었다
T2: 같은 테이블 전체에 배타 락을 걸려고 한다
```

T2는 충돌을 어떻게 알아채나? **테이블 안의 모든 행을 뒤져 락이 있는지 확인**해야 한다. 1억 행이면 1억 번이다. **락 검사가 풀 스캔이 되는** 우스운 상황이다.

**의도 락(intention lock)이 이걸 푼다.** 하위 단위에 락을 걸기 전에 **상위 단위에 "아래에 락을 걸 것이다"라는 표식**을 먼저 남긴다.

```
T1이 행에 배타 락을 걸려면:
   ① 테이블에 IX(의도 배타) 락을 건다
   ② 그다음 행에 X 락을 건다

T2가 테이블 전체에 X 락을 걸려 할 때:
   테이블 수준에서 IX를 발견 → 즉시 충돌 판정. 행을 뒤질 필요가 없다
```

**의도 락은 "실제 락"이 아니라 "아래에 락이 있다는 이정표"**다. 그래서 **의도 락끼리는 서로 충돌하지 않는다** — 여러 트랜잭션이 각자 다른 행을 잠그는 건 정상이니까. 충돌하는 건 **의도 락과 상위 단위의 실제 락** 사이다.

> [트랜잭션 · 락](transaction-and-lock.md) §2-4 표에 "의도 락"이 이름만 나오는데, **그 근거가 여기다.** 락 단위가 하나뿐이면 의도 락은 필요 없다. **여러 입도를 동시에 지원하기로 한 순간 반드시 따라오는 부품**이다.

### 2-6. 락을 안 쓰는 길 — 타임스탬프와 검증

직렬 가능성을 보장하는 방법이 2PL만은 아니다.

**타임스탬프 순서화(Timestamp Ordering)**

트랜잭션마다 시작 시각(타임스탬프)을 부여하고, **모든 충돌이 타임스탬프 순서와 일치하도록 강제**한다. 어긋나는 연산이 오면 **기다리게 하는 게 아니라 그 트랜잭션을 죽인다.**

- 장점: **데드락이 원천적으로 없다.** 기다리지 않으니 순환 대기가 안 생긴다
- 단점: 경합이 심하면 **롤백이 폭증**한다

> **Thomas Write Rule**: "이미 더 나중 트랜잭션이 쓴 값을 덮어쓰려는 늦은 쓰기"는 **무시해도 안전하다**(어차피 아무도 안 읽을 값이니). 롤백 대신 무시로 넘겨 처리량을 올리는 최적화다.

**낙관적 방식(검증 기반)**

일단 다 하고, **커밋 직전에 "충돌이 있었나"를 검사**해서 있으면 롤백한다. 충돌이 드물다는 가정이 맞으면 락 비용이 0이다 — [트랜잭션 · 락](transaction-and-lock.md) §2-8의 낙관적 락이 이 계열이다.

**데드락 예방 기법**도 타임스탬프를 쓴다.

| 기법 | 규칙 | 성격 |
|---|---|---|
| **wait-die** | 나이 많은(먼저 시작한) 쪽만 기다린다. 어린 쪽은 죽는다 | 비선점 |
| **wound-wait** | 나이 많은 쪽이 어린 쪽을 죽이고 뺏는다 | 선점 |

**둘 다 "한쪽 방향으로만 기다리게" 만든다.** 순환이 성립하려면 양방향 대기가 필요한데, 나이 순서로 방향을 고정하면 **순환 자체가 불가능**해진다. [트랜잭션 · 락](transaction-and-lock.md) §2-7의 "접근 순서를 일관되게" 조언과 **같은 원리**다.

### 2-7. 그래서 엔진이 갈라지는 것

| 항목 | MySQL (InnoDB) | PostgreSQL |
|---|---|---|
| 기본 격리 수준 | REPEATABLE READ | READ COMMITTED |
| RR에서 팬텀 차단 | **갭 락·넥스트키 락**(락 기반) | 차단하지 않음(RR에서는 스냅샷만) |
| SERIALIZABLE 구현 | **락 기반**(사실상 모든 읽기가 잠금 읽기) | **SSI**(직렬화 스냅샷 격리) — 검증 기반 |
| 충돌 시 | 대기 후 데드락 감지 | **직렬화 실패로 롤백** → 애플리케이션이 재시도 |

**마지막 줄이 실무에서 제일 크게 갈린다.** PostgreSQL의 SERIALIZABLE은 §2-6의 **낙관적 계열**이라, 락으로 기다리게 하는 대신 **커밋 시점에 "이 실행은 직렬 가능하지 않았다"며 롤백**한다. 그래서 **PG에서 SERIALIZABLE을 쓰려면 재시도 로직이 필수**다. MySQL 감각으로 접근하면 "왜 자꾸 실패하지"가 된다.

각 엔진의 실제 동작은 `mysql/` · `postgresql/`에서 이어간다.
