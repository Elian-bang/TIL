# 내구성과 복구 — COMMIT은 무엇을 보장하나

## 30초 요약

- `write()`는 디스크에 쓴 게 아니다. **OS 페이지 캐시까지만**이다. 진짜로 디스크에 내리는 건 **`fsync()`**이고, **커밋 비용의 정체는 이 fsync 한 번**이다
- 로그가 둘인 이유는 방향이 다르기 때문이다 — **redo는 앞으로 되감고(커밋된 것 다시 적용), undo는 뒤로 되감는다(미완료 되돌리기)**
- fsync는 건당으로 하면 답이 없다. **그룹 커밋** — 동시에 대기 중인 트랜잭션들의 로그를 모아 **fsync 한 번**으로 끝낸다
- **체크포인트**는 "로그를 여기까지 정산했다"는 표식이다. 이게 없으면 로그가 무한히 쌓이고 복구 시간도 무한해진다
- 로그만으로 못 고치는 고장이 하나 있다 — **찢어진 페이지(torn page)**. 16KB를 쓰다 전원이 나가면 redo를 적용할 **바탕 자체가 깨져 있다**

---

## 원리 — 왜 그런가

> [저장과 I/O](storage-and-io.md) §2-4에서 "커밋은 데이터 파일을 안 쓰고 로그만 쓴다"까지 봤고, [트랜잭션 · 락](transaction-and-lock.md) §2-1에서 ACID의 D가 redo log라는 것까지 봤다. 이 문서는 **그 아래층** — 그래서 커밋이 정확히 무엇을 하고, 죽으면 무엇이 어떻게 살아나는가.

### 2-1. `write()`는 디스크에 쓴 게 아니다

"로그를 디스크에 쓰고 커밋을 반환한다"에서 **"쓴다"가 두 단계**라는 게 출발점이다.

```
애플리케이션 →  write()  → OS 페이지 캐시  →  fsync()  → 디스크
                 (빠름, 반환됨)              (느림, 진짜)
```

`write()`는 커널 메모리에 복사하고 곧바로 반환한다. **이 시점에 전원이 나가면 그 데이터는 사라진다.** OS가 알아서 나중에 내려주긴 하지만 "나중에"가 언제인지 보장이 없다.

`fsync()`는 "지금 디스크에 내리고, 물리적으로 기록될 때까지 기다렸다가 반환하라"는 명령이다. 밀리초 단위로 걸린다(장비에 따라 0.1~수 ms). **커밋이 이 함수를 부르지 않으면 D를 지킬 수 없고, 부르는 순간 그게 커밋 비용의 대부분이 된다.**

그래서 정확한 커밋 절차는 이렇다.

```
트랜잭션 진행 중 : 변경 내역을 메모리의 로그 버퍼에 쌓는다 (디스크 접근 없음)
COMMIT           : ① 로그 버퍼를 로그 파일에 write()
                   ② fsync()  ← 여기서 기다린다. 이게 커밋 지연의 실체
                   ③ 클라이언트에 성공 반환
데이터 파일       : 여전히 안 건드림. 나중에 체크포인트가 처리 (§2-5)
```

> ⚠️ **MySQL은 이 동기화가 커밋당 한 계통이 아니다.** 복제·PITR용 binlog가 redo log와 별개 파일이라, **둘을 각각 디스크에 동기화**한다. 공식 문서도 *"binary log와 InnoDB log를 트랜잭션 커밋 전에 디스크에 동기화하도록 서버를 구성해야 한다 — InnoDB log는 기본적으로 동기화되고, `sync_binlog=1`(기본값)이 binary log 동기화를 보장한다"*로 둘을 나란히 놓는다. 그래서 **아래 계산은 MySQL 기본 구성에서 하한**이고, 실제로는 그 위다. 이 이중 로그 구조가 부르는 결과는 §2-8에서 다시 나온다. PostgreSQL은 WAL 하나뿐이라 해당 없다.

**실무 감각**: 발송 이력 100만 건을 건당 커밋하면 **fsync가 최소 100만 번**이다. fsync 1회를 0.5ms로만 잡아도 **500초** — 로직이 아니라 fsync가 시간을 다 쓴다. (자릿수 감각용 계산이다. 실제 값은 장비와 §2-3의 그룹 커밋에 따라 달라진다.) 배치를 chunk 단위로 묶는 이유가 여기 있다([Spring](../../spring/di-aop-transaction-jpa.md) §2-7).

### 2-2. 로그가 왜 둘인가 — redo와 undo

`redo`와 `undo`가 따로 있는 건 이름이 다른 게 아니라 **되감는 방향이 반대**여서다.

| | 무엇을 적나 | 언제 쓰나 |
|---|---|---|
| **redo** | 변경 **후** 값 ("이 페이지의 이 위치를 이 값으로") | 크래시 후 **커밋된 변경을 다시 적용**할 때 |
| **undo** | 변경 **전** 값 ("이 행은 원래 이랬다") | **롤백**할 때, 그리고 **MVCC 과거 버전을 읽을** 때 |

크래시 시점을 생각하면 왜 둘 다 필요한지가 보인다. 죽는 순간 디스크에는 **두 종류의 어긋남**이 동시에 존재한다.

```
A. 커밋됐는데 데이터 파일에 아직 반영 안 된 변경  → redo로 다시 적용해야 한다 (roll forward)
B. 커밋 안 됐는데 데이터 파일에 이미 반영된 변경  → undo로 되돌려야 한다  (roll back)
```

B가 왜 생기냐면, 버퍼 풀은 **커밋 여부와 무관하게** dirty page를 내린다. 메모리가 부족하면 커밋 안 된 트랜잭션이 고친 페이지도 디스크로 밀려난다. 그래서 **"디스크에 있다"가 "커밋됐다"를 뜻하지 않는다.** 이 둘을 분리하기 때문에 DB가 버퍼 풀을 자유롭게 운용할 수 있다.

> undo가 롤백과 MVCC에 **같이** 쓰인다는 게 중요하다([트랜잭션 · 락](transaction-and-lock.md) §2-3). "긴 트랜잭션이 undo를 붙잡아 둔다"는 부작용이 여기서 나온다.

**여기서 엔진이 갈린다.** 위 구조는 undo를 별도 영역에 두는 InnoDB 얘기다. PostgreSQL은 옛 버전을 **힙 안에 그대로 두므로**(→ [저장과 I/O](storage-and-io.md) §2-5) 되돌릴 것이 없다 — 롤백은 "이 트랜잭션은 실패했다"고 표시만 하면 끝난다. 대신 그 옛 튜플이 쓰레기로 남는다.

**롤백 비용이 정반대가 된다**는 실무 차이가 여기서 나온다. 1억 건 DELETE를 롤백하면 **InnoDB는 undo를 1억 건 되감느라 커밋보다 오래 걸리고**, PostgreSQL은 거의 즉시 끝난다(대신 나중에 VACUUM이 청구서를 받는다).

### 2-3. 그룹 커밋 — fsync를 나눠 내기

§2-1의 계산대로면 초당 커밋 수는 **fsync 처리량에 갇힌다**. 커밋 1000개면 fsync 1000번, 초당 2000회가 한계인 장비라면 TPS 2000이 천장이다.

**그룹 커밋**은 이 천장을 걷어낸다.

```
같은 순간 커밋을 기다리는 트랜잭션 T1, T2, ... T50
  → 로그 버퍼에는 이미 50개 분량이 순서대로 쌓여 있다
  → fsync를 한 번만 호출한다
  → 50개 전부 "디스크에 안착"이 보장된다 → 50개 동시에 커밋 성공 반환
```

로그가 **하나의 순차 스트림**이기 때문에 가능한 일이다. 뒤엣것이 디스크에 닿았으면 앞엣것은 당연히 닿아 있다.

**역설적인 결과 하나**: 동시 커밋이 많을수록 커밋당 fsync 비용이 싸진다. 한산할 때 1건 커밋은 fsync 1번을 혼자 부담하지만, 붐빌 때 50건 커밋은 fsync 1번을 나눠 낸다. **부하가 올라가도 TPS가 선형으로 안 무너지는 이유** 중 하나다.

### 2-4. 내구성 손잡이 — 얼마나 잃을 각오인가

fsync가 비싸다면 "안 하면 안 되나"라는 질문이 나온다. 그래서 두 엔진 다 **내구성을 깎아 성능을 사는 손잡이**를 열어 뒀다.

| 설정 | 커밋 때 하는 일 | 크래시 시 잃는 것 |
|---|---|---|
| 가장 안전 (기본) | write + **fsync** | **없음**. 커밋 응답을 받은 건 전부 살아 있다 |
| 중간 | write만 (fsync는 주기적으로) | **OS가 죽으면 최근 1초 안팎.** DB 프로세스만 죽는 건 안전 |
| 가장 빠름 | 주기적으로만 write+fsync | DB 프로세스만 죽어도 최근 변경 손실 |

MySQL은 `innodb_flush_log_at_trx_commit`, PostgreSQL은 `synchronous_commit`이 이 손잡이다.

**판단 기준은 성능이 아니라 데이터의 성격이다.**

- 결제·발송 요청 접수 → **끄면 안 된다.** "성공했다고 응답해 놓고 실제로는 없는 주문"이 만들어진다. 이건 느린 것보다 나쁘다
- 발송 결과 이력 같은 재생성 가능한 로그성 데이터 → 완화가 정당할 수 있다. 원본에서 다시 만들 수 있으니까

> ⚠️ **디스크가 거짓말하는 경우가 있다.** 쓰기 캐시가 켜진 저가 SSD나 일부 가상화 스토리지는 fsync에 "다 됐다"고 답해 놓고 실제로는 휘발성 캐시에만 갖고 있다. **DB 설정을 아무리 안전하게 해도 이 아래에서 무너진다.** 내구성이 진짜 필요하면 하드웨어/스토리지 계층까지 확인해야 한다.

### 2-5. 체크포인트 — 로그를 언제 정산하나

로그는 무한히 늘어날 수 없다. 그리고 로그가 길수록 **크래시 복구 시간이 길어진다** — 재생할 양이 많아지니까.

**체크포인트**는 "이 지점까지의 변경은 데이터 파일에 확실히 반영됐다"고 선언하는 작업이다.

```
체크포인트가 하는 일:
  ① 특정 시점까지의 dirty page를 데이터 파일에 내린다
  ② "여기까지 정산 완료"를 기록한다
  ③ 그 앞쪽 로그는 이제 복구에 필요 없다 → 재사용/삭제 가능
```

**여기에 긴장이 하나 있다.**

- 체크포인트를 **자주** 하면 → 복구는 빠르지만 평상시 디스크 쓰기가 늘어난다
- 체크포인트를 **드물게** 하면 → 평상시는 한가하지만 **한 번에 몰아 내리느라 I/O 스파이크**가 생기고, 복구도 오래 걸린다

두 번째가 실제로 자주 문제가 된다. **"주기적으로 응답시간이 튄다"의 흔한 범인**이 체크포인트다. 그래서 두 엔진 다 한 번에 몰아 내리지 않고 **조금씩 지속적으로 내리는 방식**(퍼지 체크포인트 / 체크포인트 분산)을 쓴다.

**로그 공간이 꽉 차면 어떻게 되나** — 체크포인트가 못 따라잡으면 재사용할 로그 공간이 없어진다. 이때 DB는 **쓰기를 멈추고 강제로 flush한다.** 증상은 "갑자기 전체 쓰기가 몇 초간 정지"다. 대량 적재 중에 이게 터지면 배치가 통째로 밀린다. **로그 파일 크기를 넉넉히 잡으라는 조언의 근거**가 이것이다.

### 2-6. 크래시 복구 — 재생하고, 되돌린다

재기동 시 절차는 §2-2의 A/B를 그대로 처리하는 것이다.

```
① 마지막 체크포인트 위치를 찾는다
② 거기서부터 로그 끝까지 redo를 전부 재생한다   ← 커밋 여부 안 따진다. 일단 다 적용
③ 그러고 나서 커밋되지 않은 트랜잭션을 undo로 되돌린다
```

②에서 **커밋 안 된 것까지 일단 적용**하는 게 처음엔 이상해 보이는데, 이유가 있다. 재생 시점에는 그 트랜잭션이 커밋됐는지 아직 모른다(로그를 끝까지 읽어야 안다). 그래서 **먼저 디스크를 크래시 직전 상태로 정확히 복원해 놓고, 그다음에 미완료분을 걷어내는** 순서가 된다.

이 절차의 성질 하나가 실무에서 중요하다. **복구는 멱등하다** — 복구 도중에 또 죽어도, 다시 시작해서 같은 절차를 반복하면 된다. 로그의 각 변경에는 순번이 붙어 있어서 **이미 반영된 것은 건너뛴다.** 그래서 "복구하다 죽어서 DB가 더 망가지는" 일은 구조적으로 없다.

### 2-7. 찢어진 페이지 — 로그만으로 못 고치는 고장

redo log는 **"이 페이지의 이 부분을 이렇게 바꿔라"**라는 변경분만 갖고 있다. 여기 구멍이 하나 있다.

페이지는 16KB인데 디스크의 원자적 쓰기 단위는 보통 4KB다. **16KB를 쓰는 도중에 전원이 나가면 앞의 4KB만 새 내용이고 나머지는 옛 내용인 페이지**가 남는다. 이걸 torn page라 한다.

문제는 **redo를 적용할 바탕 자체가 깨져 있다는 것**이다. "이 위치를 이렇게 바꿔라"는 명령은 **원본 페이지가 멀쩡하다는 전제**에서만 유효하다. 반쪽짜리 페이지에 적용하면 결과는 여전히 쓰레기다.

해법은 둘 다 "페이지 전체를 어딘가에 한 번 더 써 두는" 것이고, 어디에 쓰느냐가 갈린다.

- **MySQL — 더블라이트 버퍼**: 데이터 파일에 쓰기 전에 **전용 영역에 페이지 전체를 먼저** 쓴다. 데이터 파일 쪽이 찢어졌으면 그 사본에서 복구한다
- **PostgreSQL — `full_page_writes`**: 체크포인트 이후 **처음 수정되는 페이지는 WAL에 페이지 전체를 통째로** 기록한다. 복구 때 그 온전한 이미지를 깔고 그 위에 변경분을 재생한다

**둘 다 쓰기가 두 배가 된다.** 내구성의 실제 청구서다. PostgreSQL에서 "체크포인트 직후에 WAL이 급증한다"는 현상이 여기서 나온다 — 체크포인트마다 각 페이지의 첫 수정이 전체 이미지를 남기기 때문이다.

### 2-8. 로그는 백업·복제와 같은 물건이다

지금까지 로그를 "크래시 복구용"으로 봤는데, **같은 로그가 시간여행과 복제에도 쓰인다.**

**PITR(Point-In-Time Recovery)** — 전체 백업 하나 + 그 이후의 로그가 있으면, **원하는 시각까지만 로그를 재생**해서 그 순간의 상태를 만들 수 있다.

```
일요일 전체 백업  +  로그(월~수 14:37)  =  수요일 14:37의 데이터베이스
```

**"실수로 `DELETE`를 커밋했다"를 되돌리는 유일한 수단**이 이것이다. 백업만 있으면 일요일로만 갈 수 있지만, 로그가 있으면 **사고 1초 전**으로 갈 수 있다.

**복제**도 원리가 같다. 리플리카에 로그를 흘려보내고 그쪽에서 재생하면 같은 상태가 된다. **복제는 "다른 장비에서 무한히 계속되는 크래시 복구"**다. → 다음 편 **복제와 파티셔닝**(작성 예정)

여기서 MySQL의 구조적 특이점이 하나 나온다. MySQL은 **복제·PITR용 로그(binlog)가 redo log와 별개**다. 로그가 둘이니 **"redo에는 썼는데 binlog에는 못 쓴 채로 죽는" 어긋남**이 가능해지고, 그래서 MySQL은 커밋할 때마다 **두 로그 사이에 내부적으로 2단계 커밋을 수행**한다. PostgreSQL은 WAL 하나가 복구·복제·PITR을 전부 겸하므로 이 문제 자체가 없다.

### 2-9. 그래서 갈라지는 것들

| 항목 | MySQL (InnoDB) | PostgreSQL |
|---|---|---|
| 로그 구성 | **redo + undo + binlog** (셋) | **WAL 하나**가 복구·복제·PITR 전부 |
| 커밋 시 2단계 커밋 | **필요** (redo ↔ binlog 정합) | 불필요 |
| 미완료 트랜잭션 되돌리기 | undo 적용 → **큰 롤백은 비싸다** | 표시만 → **롤백이 싸다**, 대신 VACUUM 부담 |
| 내구성 손잡이 | `innodb_flush_log_at_trx_commit` | `synchronous_commit` |
| torn page 대응 | 더블라이트 버퍼 | `full_page_writes`(WAL에 전체 페이지) |
| 로그 공간 고갈 시 | 강제 flush → **쓰기 스톨** | 아카이브 실패 시 WAL 누적 → **디스크 고갈** |

마지막 줄은 성격이 다르다. PostgreSQL에서는 복제 슬롯이나 WAL 아카이빙이 막히면 **WAL이 지워지지 않고 계속 쌓여 디스크를 채운다.** 죽은 리플리카를 방치했다가 마스터가 멈추는 사고가 여기서 나온다. 각각의 운영 항목은 `mysql/` · `postgresql/`에서 이어간다.
