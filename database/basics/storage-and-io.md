# 저장과 I/O — DB는 디스크를 어떻게 다루나

## 30초 요약

- DB는 행 단위가 아니라 **페이지 단위**로 읽고 쓴다(InnoDB 16KB, PostgreSQL 8KB). 1행만 필요해도 페이지 하나가 통째로 올라온다
- 페이지는 **버퍼 풀**에 올라온다. 여기서 읽고 여기서 고친다. **디스크는 백업본이지 작업 장소가 아니다**
- 그래서 커밋은 데이터 파일을 건드리지 않는다 — **로그에 순차로 먼저 쓰고(WAL) 반환**한다. 데이터 파일 반영은 나중에 몰아서
- 행을 파일 어디에 두느냐가 갈림길이다: **힙(무순서, PostgreSQL)** vs **PK 정렬(클러스터드, InnoDB)**. 두 엔진 차이의 대부분이 이 한 줄에서 파생된다
- 지배 원리는 하나다: **순차 I/O ≪ 랜덤 I/O**. 인덱스도 WAL도 파티셔닝도 전부 이 부등호를 이용하려는 설계다

---

## 원리 — 왜 그런가

### 2-1. 왜 행이 아니라 페이지 단위인가

`SELECT * FROM member WHERE id = 5` 는 행 하나를 원한다. 그런데 디스크에서 올라오는 건 그 행이 속한 **페이지 전체**(InnoDB 16KB)다. 행이 128B라면 **필요한 것의 128배를 읽는 셈**이다. 낭비처럼 보이는데 왜 이렇게 하나.

**디스크 접근 비용이 "얼마나 읽느냐"가 아니라 "몇 번 가느냐"로 결정되기 때문**이다. 요청 한 번에 붙는 고정 비용(SSD면 컨트롤러 왕복과 플래시 페이지 읽기, HDD면 탐색 시간)이 지배적이라, 128B를 읽든 16KB를 읽든 걸리는 시간이 크게 다르지 않다.

그래서 계산이 이렇게 바뀐다.

```
128B씩 128번 읽기  = 요청 128번 × 고정비용   → 비싸다
16KB 한 번 읽기    = 요청 1번 × 고정비용     → 싸다
```

즉 페이지는 **낭비가 아니라 "어차피 한 번 갈 거면 주변까지 들고 오자"는 도박**이다. 그리고 이 도박은 대체로 이긴다 — 방금 읽은 행 옆의 행을 곧 읽게 될 확률이 높기 때문이다(지역성). B+Tree가 **노드 하나 = 페이지 하나**로 설계된 것도([DB 인덱스](b-tree-index.md) §2-1) 이 단위에 자신을 맞춘 것이다.

여기서 실무 규칙 하나가 나온다. **행이 작을수록 페이지 하나에 더 많이 들어가고, 같은 데이터를 더 적은 I/O로 읽는다.** 안 쓰는 컬럼을 `VARCHAR(4000)`으로 잡아 두는 게 공짜가 아닌 이유다.

### 2-2. 버퍼 풀 — 캐시가 아니라 작업 공간이다

버퍼 풀(InnoDB `innodb_buffer_pool_size`, PostgreSQL `shared_buffers`)을 "자주 쓰는 걸 캐시해 두는 곳"으로 이해하면 절반만 맞다. 정확히는 **DB가 페이지를 읽고 고치는 유일한 장소**다.

읽기든 쓰기든 흐름이 같다.

```
1. 필요한 페이지가 버퍼 풀에 있나?
   있으면  → 메모리에서 처리. 끝 (디스크 I/O 0회)
   없으면  → 디스크에서 페이지를 올린다 (I/O 1회)
2. 수정은 메모리 위의 페이지에 한다 → 이 페이지를 dirty page라고 부른다
3. dirty page를 디스크에 내리는 건 나중에, 백그라운드가 몰아서 한다
```

**"수정을 메모리에서 한다"는 게 핵심**이다. 100건을 UPDATE했는데 그게 전부 같은 페이지 안이면 디스크 쓰기는 **결국 1회**다. 건당 쓰기가 아니라 페이지당 쓰기로 뭉쳐진다.

여기서 두 가지가 따라온다.

**(1) DB 성능 질문의 대부분은 "그 페이지가 메모리에 있느냐"로 환원된다.** 인덱스를 잘 타는데도 느리다면, 인덱스가 문제가 아니라 그 인덱스 페이지가 버퍼 풀에서 계속 밀려나고 있을 수 있다. **활성 데이터(working set)가 버퍼 풀보다 크면** 페이지가 올라왔다 밀려나기를 반복한다 — 캐시 스래싱이다(OS에서 같은 현상이 왜 스스로 악화되는지는 → [메모리와 페이징](../../os/memory-and-paging.md) §2-5).

**(2) 메모리 배분 철학이 두 엔진에서 다르다.** InnoDB는 **버퍼 풀을 크게 잡아 DB가 직접 관리하는 쪽**, PostgreSQL은 `shared_buffers`를 보수적으로 잡고 **나머지를 OS 페이지 캐시에 맡기는 쪽**이다. 그래서 PG는 같은 페이지가 shared_buffers와 OS 캐시에 둘 다 올라오는 이중 캐싱이 일어나지만, 대신 OS의 캐시 알고리즘을 공짜로 쓴다. **어느 쪽이 옳다기보다, 튜닝할 때 보는 손잡이가 다르다**는 게 실무에서 중요하다. (InnoDB가 OS 캐시를 실제로 우회하는지는 `innodb_flush_method` 설정에 달렸다 — 기본값은 아래 출처 블록의 미확인 항목)

### 2-3. 밀어낼 페이지를 어떻게 고르나 — 스캔 저항성

버퍼 풀이 꽉 차면 뭔가를 버려야 한다. 순진하게 LRU(가장 오래 안 쓴 것부터)를 쓰면 **치명적인 구멍**이 하나 생긴다.

MySQL 공식 문서가 그 구멍을 이렇게 적어 뒀다 — *"테이블 스캔은 대량의 데이터를 버퍼 풀에 올리면서 그만큼의 오래된 데이터를 밀어낸다. **그 새 데이터를 다시 쓸 일이 없더라도** 그렇다."*

**발송 도메인에서 이게 어떻게 나타나는가:**

```
평상시  : 발송 예약 조회가 쓰는 인덱스 페이지들이 버퍼 풀에 상주 → 응답 5ms
02:00   : 월간 발송 이력 집계 배치가 1억 건 테이블을 풀 스캔
        → 1억 건어치 페이지가 버퍼 풀을 통과하며 상주 페이지를 전부 밀어냄
02:05   : 배치는 끝났고, 그 페이지들은 두 번 다시 안 쓰인다
        → 그런데 온라인 조회는 이제 매번 디스크를 간다. 응답 5ms → 80ms
```

**한 번 쓰고 버릴 데이터가 계속 쓸 데이터를 쫓아냈다.** 배치가 끝난 뒤에도 한동안 느린 이유가 이것이다 — 캐시를 다시 데우는 데 시간이 걸린다.

InnoDB의 해법은 **LRU 리스트를 둘로 쪼개는 것**이다.

```
[ young sublist 5/8 ]  ← 실제로 재사용된 페이지. 오래 살아남는다
──── midpoint ────      ← 새 페이지는 여기로 들어온다 (맨 앞이 아니라!)
[ old sublist   3/8 ]  ← 수습 기간. 밀려나는 건 여기 꼬리부터
```

새로 읽은 페이지를 **맨 앞이 아니라 중간에 넣는다**(midpoint insertion). 한 번 쓰고 마는 스캔 페이지는 young 구역에 발도 못 들이고 old 구역 꼬리로 흘러나간다. **자주 쓰는 페이지가 사는 5/8은 스캔에 오염되지 않는다.**

여기에 안전장치가 하나 더 있다. 스캔은 한 페이지 안의 여러 행을 **연달아** 읽으므로 "두 번 접근됐다"고 오해받기 쉽다. 그래서 InnoDB는 **old 구역에 들어온 뒤 일정 시간이 지나야 young으로 승격**시킨다(`innodb_old_blocks_time`). **시간 간격을 두고 다시 찾은 페이지만 진짜 재사용**으로 친다는 뜻이다.

> **프리페치(read-ahead)는 반대 방향의 도박이다.** 순차 접근 패턴이 보이면 **아직 요청하지 않은 페이지를 미리 올려 둔다**(linear read-ahead / random read-ahead). 맞으면 디스크 대기가 사라지고, 틀리면 버퍼 풀만 오염시킨다. 그래서 프리페치와 스캔 저항성은 **같은 자원을 두고 반대로 당기는 한 쌍**이다.

### 2-4. 왜 커밋이 데이터 파일 쓰기가 아닌가 — WAL

`COMMIT`은 "이 변경은 이제 절대 사라지지 않는다"는 약속이다(ACID의 D). 약속을 지키려면 디스크에 뭔가 확실히 써야 한다. 그런데 **dirty page를 데이터 파일에 바로 내리면** 문제가 생긴다.

수정된 페이지들은 파일 여기저기에 흩어져 있다. 커밋마다 그걸 내리면 **랜덤 쓰기 여러 번**이다. 게다가 페이지 전체(16KB)를 써야 한다 — 실제로 바뀐 건 100B인데도.

WAL(Write-Ahead Logging)은 순서를 뒤집어 이 문제를 푼다.

```
COMMIT 시점에 하는 일:
  "무엇을 어떻게 바꿨는지"만 로그 파일 끝에 append → 순차 쓰기 1회 → fsync → 커밋 반환

데이터 파일 반영:
  나중에 백그라운드가 몰아서 (체크포인트)
```

**바뀐 것은 "언제 쓰느냐"가 아니라 "어디에 쓰느냐"다.** 흩어진 랜덤 쓰기 N회가, 로그 파일 끝에 붙이는 순차 쓰기 1회로 바뀌었다.

이 로그를 MySQL은 redo log, PostgreSQL은 WAL이라 부른다.

> **한 줄로 정리하면**: "커밋이 빠른 이유는 데이터를 안 쓰기 때문입니다. 변경 내역만 로그에 순차로 쓰고 반환하고, 진짜 데이터 파일 반영은 나중에 몰아서 합니다."

**이 문서에서 WAL 이야기는 여기까지다.** 커밋이 정확히 어떤 시스템 콜을 부르는지, 로그가 왜 둘(redo·undo)인지, 크래시에서 무엇이 어떻게 살아나는지는 전부 → **[내구성과 복구](durability-and-recovery.md)**가 정본이다.

### 2-5. 행을 파일 어디에 두나 — 힙 vs 클러스터드

앞의 넷은 두 엔진이 사실상 같다. **갈라지는 지점은 여기 하나다: 행을 파일의 어느 위치에 두는가.**

**힙 (PostgreSQL, Oracle 기본)**

정해진 순서가 없다. **빈 자리가 있으면 거기 넣는다.** 행의 주소는 `(페이지 번호, 페이지 안 슬롯 번호)`이고 PG에서는 이걸 `ctid`라 부른다.

- 인덱스는 전부 **동등하다**. PK 인덱스든 이메일 인덱스든 똑같이 "값 → ctid"를 담는다. 특별한 인덱스가 없다
- 인덱스를 타면 **한 번의 포인터 참조로 행에 도달**한다
- 대신 **행이 이사하면 그 행을 가리키는 모든 인덱스를 고쳐야 한다**

**클러스터드 (InnoDB, SQL Server 기본)**

**PK 순서로 물리 정렬**해서 저장한다. PK 인덱스의 리프가 곧 행이다 — 테이블과 PK 인덱스가 같은 물건이다.

- PK 범위 조회가 **순차 읽기**가 된다. `WHERE id BETWEEN` 이 빠른 이유
- 세컨더리 인덱스는 ctid 같은 물리 주소가 아니라 **PK 값**을 담는다 → 조회가 **두 번 탄다**(세컨더리 → PK → 행). [DB 인덱스](b-tree-index.md) §2-3
- 대신 행이 페이지 안에서 이사해도 **세컨더리 인덱스는 고칠 게 없다**. 물리 주소가 아니라 PK를 갖고 있으니까

**교환 조건이 대칭이다.** 힙은 도달이 한 번이지만 이사에 약하고, 클러스터드는 도달이 두 번이지만 이사에 강하다. 어느 쪽도 공짜가 아니다.

### 2-6. 그래서 갈라지는 것들

§2-5의 선택 하나에서 파생되는 실무 차이를 모아 보면 이렇다. 지금은 지도만 그려 두고, 각 항목은 `mysql/` · `postgresql/`에서 각각 다룬다.

| 문제 | InnoDB (클러스터드) | PostgreSQL (힙) | 그래서 실무에서 |
|---|---|---|---|
| PK 선택 | **매우 중요**. PK 순서 = 물리 순서라 랜덤 PK(UUID v4)는 페이지 분할을 부른다. PK 길이가 모든 세컨더리 인덱스를 부풀린다 | 상대적으로 **덜 중요**. PK도 그냥 인덱스 하나 | InnoDB에서 UUID PK는 실질 비용이 있다. PG에선 그만큼은 아니다 |
| 세컨더리 인덱스 조회 | 두 번 탐색(북마크 룩업) | 인덱스 → 힙 한 번 | 커버링 인덱스 효과는 **InnoDB에서 더 극적**이다 |
| UPDATE 시 인덱스 | 바꾼 컬럼의 인덱스만 갱신 | 행이 이사하면 **그 테이블의 모든 인덱스**를 갱신(HOT update로 회피 가능) | PG는 인덱스 개수가 UPDATE 비용에 직접 붙는다 |
| 갱신 전 버전 보관 | undo 세그먼트(별도 영역) | **힙 안에 옛 버전을 그대로 둠** | PG는 UPDATE만 해도 테이블이 부풀고 **VACUUM이 필요**하다 |
| PK 범위 조회 | 순차 읽기 | 값이 흩어져 있어 랜덤 접근 | PG는 `CLUSTER`로 한 번 정렬할 수 있지만 **유지되지 않는다** |

마지막 두 줄이 PostgreSQL 운영의 대표 주제인 VACUUM으로 이어지고, 첫 두 줄이 MySQL 인덱스 설계의 대표 주제로 이어진다. **원리는 하나인데 운영에서 신경 쓸 것이 정반대로 나오는 것**이 이 표의 요점이다.

### 2-7. 반복해서 돌아오는 부등호

이 문서에 나온 설계가 전부 같은 문장을 다르게 말하고 있다.

| 설계 | 무엇을 무엇으로 바꿨나 |
|---|---|
| 페이지 단위 I/O | 작은 요청 여러 번 → 큰 요청 한 번 |
| 버퍼 풀 | 디스크 접근 → 메모리 접근 |
| WAL | 흩어진 랜덤 쓰기 → 로그 끝에 순차 쓰기 |
| B+Tree 리프 연결 | 트리 오르내리기(랜덤) → 옆으로 스캔(순차) |
| 클러스터드 인덱스 | PK 범위 조회를 순차 읽기로 |
| 테이블 파티셔닝 | 행 단위 DELETE → 덩어리째 DROP |

**순차 I/O ≪ 랜덤 I/O.** DB 내부 설계에서 "왜 이렇게 했나"가 막히면 대체로 여기로 환원된다. ([자료구조](../../fundamentals/data-structures.md) §복잡도보다 I/O 횟수, [DB 인덱스](b-tree-index.md) §2-11 딥 페이징도 같은 이야기다)
