# DB 한 대로 안 될 때

## 30초 요약

- 한 대로 안 되는 이유가 둘이다. **못 버틴다(장애·읽기 부하)**와 **안 들어간다(용량·쓰기량)**. 복제가 앞을, 파티셔닝이 뒤를 푼다
- 복제는 새로운 기술이 아니다. [내구성과 복구](durability-and-recovery.md)의 로그를 다른 장비로 흘려보내 재생하는 것, 곧 **"끝나지 않는 크래시 복구"**다
- **복제 지연은 버그가 아니라 구조다.** 없애려고 동기로 만들면 지연 대신 가용성을 잃는다. 스탠바이가 죽으면 커밋이 안 끝난다
- 읽기 분산의 청구서는 **"방금 쓴 걸 못 읽는다"**(read-your-writes 붕괴)와 **"값이 되돌아간다"**(monotonic reads 붕괴)다
- 파티셔닝의 이득은 프루닝과 덩어리째 버리기뿐이다. 둘 다 **키를 조건에 안 쓰면 그냥 사라진다**

---

## 원리 — 왜 그런가

### 2-1. 한 대로 안 되는 두 가지 이유

"DB를 여러 대로 나눈다"는 말이 두 개의 다른 문제를 가리킨다. 섞으면 대화가 어긋난다.

| 문제 | 증상 | 해법 | 데이터는 |
|---|---|---|---|
| **못 버틴다** | 장비가 죽으면 서비스가 멈춘다 / 읽기가 몰려 느리다 | **복제** | **같은 것을 여러 벌** |
| **안 들어간다** | 테이블이 너무 커서 인덱스가 메모리에 안 올라간다 / 쓰기가 한 장비 한계를 넘는다 | **파티셔닝·샤딩** | **다른 것을 나눠서** |

**복제는 쓰기 문제를 못 푼다.** 리플리카를 10대 붙여도 쓰기는 여전히 한 대가 받는다. 모든 리플리카가 같은 쓰기를 다 받아야 하니까. 읽기 부하가 아니라 쓰기 부하가 병목이면 복제는 답이 아니다.

**파티셔닝은 가용성 문제를 못 푼다.** 나눠 놨는데 한 조각이 죽으면 그 조각의 데이터는 못 읽는다. 오히려 장비가 늘어난 만큼 어딘가 죽을 확률이 올라간다.

→ 그래서 실무에서는 **둘을 같이 쓴다.** 파티션마다 복제본을 둔다.

### 2-2. 복제는 로그 재생이다

[내구성과 복구](durability-and-recovery.md) §2-8에서 로그가 크래시 복구·PITR·복제에 **같이 쓰인다**고 했다. 복제가 그 세 번째다.

```
프라이머리 : 평소처럼 로그를 쓴다 (WAL / binlog)
            → 그 로그를 리플리카로 흘려보낸다
리플리카   : 받은 로그를 재생한다
            → 크래시 복구와 정확히 같은 절차를, 끝없이
```

**복제는 "다른 장비에서 영원히 계속되는 크래시 복구"**다. 별도 메커니즘이 아니라 이미 있는 것의 재활용이다.

**보내는 것이 무엇이냐로 두 갈래가 나뉜다.**

| | 물리 복제 | 논리 복제 |
|---|---|---|
| 보내는 것 | **"몇 번 페이지의 몇 바이트를 이렇게"** | **"이 행이 이렇게 바뀌었다"** |
| 결과 | 바이트 단위로 동일한 사본 | 같은 데이터, 물리 배치는 다를 수 있음 |
| 가능한 것 | 전체 복제만 | **테이블 일부만**, 다른 버전 간, 다른 스키마로 |
| 비용 | 싸다 | 해석이 필요해 비싸다 |

**PostgreSQL은 둘 다 있다.** 스트리밍 복제(물리)와 publication/subscription(논리)다. MySQL의 binlog는 태생이 논리 쪽이고 포맷을 고를 수 있다(ROW / STATEMENT / MIXED).

> **STATEMENT 포맷에는 함정이 있다.** SQL 문장을 그대로 보내는 방식인데, `NOW()`나 `RAND()`처럼 실행할 때마다 값이 달라지는 함수가 들어가면 프라이머리와 리플리카의 결과가 갈린다. ROW 포맷(바뀐 행의 값을 보냄)이 안전하고 지금 기본값에 가깝다. "복제는 재생"이라는 원리에서 왜 문제가 되는지가 바로 보인다. 재생이 원본과 같은 결과를 내야 하는데 그 전제가 깨진다.

### 2-3. 동기냐 비동기냐

프라이머리가 **커밋을 반환하기 전에 리플리카를 얼마나 기다리느냐**의 문제다. PostgreSQL 문서가 이 단계를 명시적으로 나눠 놨다.

| 어디까지 기다리나 | 잃는 것 |
|---|---|
| **안 기다린다**(비동기) | 프라이머리가 죽으면 **아직 안 간 커밋이 사라진다** |
| **받아서 OS에 썼다**(`remote_write`) | 리플리카 OS가 같이 죽으면 손실 |
| **디스크에 안착했다**(`on`) | 손실 거의 없음. 대신 **왕복이 커밋 지연에 그대로 붙는다** |
| **재생까지 끝났다**(`remote_apply`) | 가장 느림. 대신 **읽기 분산해도 최신이 보인다** |

**마지막 줄이 §2-5 문제의 해법**이라는 게 중요하다. 공식 문서도 `remote_apply`를 *"인과 일관성을 갖춘 로드 밸런싱을 허용한다"*고 설명한다. 다만 모든 커밋이 리플리카 재생까지 기다리므로 쓰기 지연을 대가로 낸다.

**동기 복제의 진짜 위험은 지연이 아니다.** 공식 문서에 이렇게 적혀 있다. *"동기 스탠바이 중 하나가 죽으면 그 트랜잭션 커밋은 **영영 완료되지 않을 수 있다**."*

```
동기 복제를 켰다 → 리플리카가 죽었다 → 프라이머리는 멀쩡한데 커밋이 전부 멈춘다
```

**가용성을 높이려고 붙인 리플리카가 가용성을 떨어뜨린다.** 이게 [저장소 선택](../../datastore/selection.md) §2-1의 CAP가 추상론이 아니라 설정 한 줄로 나타나는 지점이다. 동기를 켜는 건 C를 택하고 A를 버리는 선택이다.

> 그래서 실무에서는 **반동기**(리플리카 여럿 중 하나만 확인되면 진행)나 **자동 강등**(응답 없는 스탠바이를 동기 목록에서 빼기)으로 절충한다. MySQL의 반동기 복제도 같은 자리에 있다.

### 2-4. 복제 지연을 없앨 수 없는 이유

비동기라면 지연이 있다. **얼마나 벌어지느냐가 문제인데, 벌어지는 원인이 셋이다.**

1. **네트워크**. 로그가 물리적으로 이동하는 시간
2. **재생 속도**. 리플리카가 로그를 적용하는 속도이고, 여기가 진짜 병목이다
3. **리플리카의 자기 부하**. 조회 쿼리를 받고 있으면 재생이 밀린다

**2번이 구조적이다.** 프라이머리는 여러 커넥션이 병렬로 쓰는데, 재생은 순서를 지켜야 한다. 순서를 안 지키면 결과가 달라지니까. 쓰기는 병렬이고 재생은 (기본적으로) 직렬인데, 이 비대칭이 지연을 만든다.

그래서 **쓰기가 몰리는 순간 지연이 급격히 벌어진다.** 대량 배치를 돌리면 평소 0.1초이던 지연이 수십 초가 된다. "평소엔 괜찮은데 배치 돌면 통계가 이상하다"는 신고의 정체다.

> 모니터링 지표는 MySQL이 `Seconds_Behind_Master`, PostgreSQL이 `pg_stat_replication`의 lag 컬럼들이다. **⚠️ `Seconds_Behind_Master`는 신뢰도가 낮기로 유명하다.** 연결이 끊기면 0이나 NULL이 되고, 재생이 멈춰도 값이 안 늘어나는 경우가 있다. "0이니까 괜찮다"는 위험한 판단이다.

### 2-5. 읽기 분산의 청구서

리플리카로 읽기를 보내면 프라이머리가 가벼워진다. 대가는 **일관성 모델이 바뀌는 것**이다.

**(1) read-your-writes 붕괴.** 방금 쓴 게 안 보인다

```
사용자: 발송 예약을 등록한다   → 프라이머리에 INSERT
화면  : 목록으로 돌아간다      → 리플리카에서 SELECT
결과  : 방금 만든 예약이 없다   ← 복제가 아직 안 갔다
```

**사용자에게는 명백한 버그로 보인다.** "저장 눌렀는데 없어졌어요."

해법 셋:
- **쓰기 직후 N초는 프라이머리로 읽는다.** 가장 단순하고 가장 많이 쓴다. N을 얼마로 잡을지가 감이라는 게 약점
- **위치를 들고 다닌다.** 쓰기 응답에 로그 위치(GTID / LSN)를 실어 주고, 읽을 때 "이 위치까지 재생된 리플리카"만 고른다. 정확하지만 구현이 무겁다
- **§2-3의 `remote_apply`.** DB 계층에서 해결한다. 대신 모든 쓰기가 느려진다

**(2) monotonic reads 붕괴.** 값이 되돌아간다

리플리카가 여럿이고 각자 지연이 다르면 이런 일이 생긴다.

```
첫 조회  → 리플리카 A(최신)   → "발송 완료 100건"
새로고침 → 리플리카 B(뒤처짐)  → "발송 완료 80건"     ← 시간이 거꾸로 갔다
```

한 번 본 것이 사라진다. **read-your-writes보다 더 혼란스럽다.** 내가 쓴 것도 아닌데 값이 왔다 갔다 한다.

해법은 **같은 사용자는 같은 리플리카로 고정**(sticky routing)하는 것이다. 그 리플리카가 뒤처져 있어도 최소한 뒤로 가지는 않는다.

> **판단 기준은 데이터의 성격이다.** 과금 잔액·발송 상태는 프라이머리에서 읽고, 통계·리포트처럼 몇 초 늦어도 되는 것만 리플리카로 보낸다. **"읽기니까 전부 리플리카로"는 사고를 부른다.**

### 2-6. 승격이 왜 어려운가

프라이머리가 죽으면 리플리카 하나를 승격시킨다. 절차 자체는 단순한데 **판단이 어렵다.**

**(1) 정말 죽었는가, 안 보이는 것인가**

네트워크가 끊긴 것과 장비가 죽은 것을 **밖에서는 구분할 수 없다.** 여기서 최악의 사고가 나온다.

```
네트워크 단절 → "프라이머리가 죽었다" 판단 → 리플리카를 승격
그런데 옛 프라이머리는 살아 있고 여전히 쓰기를 받고 있다
→ 프라이머리가 둘 (split-brain)
→ 양쪽에 서로 다른 데이터가 쌓인다 → 합칠 방법이 없다
```

**split-brain은 복구가 아니라 손실이다.** 한쪽을 버려야 한다.

막는 방법은 둘 다 "혼자 결정하지 않는 것"이다.
- **쿼럼**: 과반이 동의해야 승격한다. 소수파 쪽은 스스로 쓰기를 멈춘다
- **펜싱**: 승격 전에 옛 프라이머리를 확실히 죽인다(전원 차단, 네트워크 격리)

**(2) 얼마나 잃을 것인가**

비동기 복제였다면 **아직 안 넘어간 커밋은 사라진다.** 프라이머리가 사용자에게 "성공"이라고 응답한 것이 소실될 수 있다. §2-3의 선택이 여기서 청구된다.

**(3) 자동이냐 수동이냐**

| | 장점 | 위험 |
|---|---|---|
| 자동 | 복구가 빠르다(수십 초) | **오판이 곧 split-brain** |
| 수동 | 사람이 상황을 보고 판단 | 새벽에 사람이 필요하다 |

**자동 페일오버는 "빠른 복구"와 "오판 위험"을 바꾼 것**이다. 잘못된 자동화가 멀쩡한 시스템을 두 조각 내는 건 [Kubernetes](../../infra/kubernetes.md) §2-4에서 프로브를 잘못 걸어 멀쩡한 앱을 계속 죽이는 것과 같은 종류의 사고다. 판단 근거가 부실한 자동화는 강력한 만큼 강하게 틀린다.

### 2-7. 나누면 무엇이 좋아지나

> **⚠️ 이름이 같은 두 가지가 있다.** 이 절은 한 DB 안에서 테이블을 쪼개는 것을 다룬다. 여러 노드로 데이터를 나누는 샤딩은 [대용량 처리](../../system-design/high-throughput.md) §2-7, 보존 정책으로서의 파티셔닝(`DROP PARTITION`)은 [DB 인덱스](b-tree-index.md) §2-12에 있다. 여기서는 **그 둘이 기대고 있는 원리**만 본다.

**나누는 축이 둘이다.**

- **수직 분할**: 컬럼을 쪼갠다. 자주 안 읽는 큰 텍스트를 분리하면 **페이지 하나에 더 많은 행**이 들어간다([저장과 I/O](storage-and-io.md) §2-1)
- **수평 분할**: 행을 쪼갠다. 보통 "파티셔닝"이라 하면 이쪽이다

**수평 분할의 이득은 정확히 둘뿐이다.**

**(1) 프루닝.** 안 볼 조각은 아예 안 읽는다

```sql
-- send_history를 sent_at 월 단위로 파티셔닝
SELECT * FROM send_history WHERE sent_at >= '2026-08-01';
→ 2026-08 파티션만 읽는다. 나머지 35개월치는 손도 안 댄다
```

**(2) 덩어리째 버리기.** `DELETE`가 아니라 `DROP PARTITION`이다. 행 단위 삭제의 로그·인덱스 갱신 비용이 전부 사라진다.

**그리고 여기에 함정이 하나 있다.**

```sql
SELECT * FROM send_history WHERE receiver_phone = '010-...';
→ 파티션 키(sent_at)가 조건에 없다 → 36개 파티션을 전부 읽는다
```

**프루닝은 조건이 파티션 키를 포함할 때만 일어난다.** 안 그러면 파티션은 이득 없이 관리 복잡도만 늘린 것이 된다. 나누기 전에 **"주요 조회가 이 키를 항상 포함하는가"**를 먼저 확인해야 하는 이유다.

**파티션 키가 PK에 포함돼야 하는 제약도 여기서 나온다.** 두 엔진 다 이 제약이 있고, 이유가 같다. 유니크성을 보장하려면 모든 파티션을 다 뒤져야 하는데, 그러면 §(1)의 프루닝이 무의미해진다. 그래서 유니크는 파티션 안에서만 보장하고, 그러려면 파티션 키가 키에 들어 있어야 한다.

> **"파티션을 나누면 빨라진다"는 오해다.** 인덱스가 이미 잘 동작하는 조회는 파티셔닝해도 안 빨라진다. B+Tree 깊이가 1 줄어드는 정도다([DB 인덱스](b-tree-index.md) §2-1). 파티셔닝의 값어치는 조회 속도가 아니라 관리성에 있다. 오래된 것을 싸게 버리고, 안 볼 것을 안 읽는 것이다.

### 2-8. 복제 로그가 하나냐 둘이냐

| 항목 | MySQL | PostgreSQL |
|---|---|---|
| 복제 기반 | **binlog**(redo와 별개, 논리 계열) | **WAL 하나**(물리) + 논리 복제 별도 |
| 포맷 선택 | ROW / STATEMENT / MIXED | 물리 복제는 선택 없음 |
| 동기 수준 | 비동기 기본, **반동기** 플러그인 | `synchronous_commit`으로 4단계 |
| 재생 후 가시성 보장 | 대응 옵션 없음 | **`remote_apply`** |
| 지연 지표 | `Seconds_Behind_Master`(신뢰도 낮음) | `pg_stat_replication`의 lag 컬럼들 |
| 파티셔닝 | RANGE/LIST/HASH/KEY | 선언적 파티셔닝(10+), RANGE/LIST/HASH |
| 복제 슬롯 | 없음 | **있다.** 리플리카가 못 받은 WAL을 프라이머리가 보관한다. 죽은 리플리카를 방치하면 프라이머리 디스크가 찬다 |

**마지막 줄이 운영에서 성격이 제일 다르다.** PostgreSQL의 복제 슬롯은 "리플리카가 놓치지 않게" 해 주는 안전장치인데, 그 리플리카가 영영 안 돌아오면 그대로 디스크 폭탄이 된다. 각 엔진의 실제 운영은 `mysql/` · `postgresql/`에서 이어간다.
