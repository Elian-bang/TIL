# 옵티마이저는 왜 그 플랜을 골랐나

## 30초 요약

- SQL에는 "무엇을"만 적고 "어떻게"는 안 적는다. 그 대가로 실행 방법은 옵티마이저가 정하고, **같은 SQL이 데이터가 바뀌면 다른 플랜으로 실행된다**
- 조인 알고리즘은 사실상 셋이다. **Nested Loop · Hash · Sort-Merge**. 셋 다 존재하는 이유는 이기는 조건이 서로 다르기 때문이다
- Nested Loop 비용 ≈ **드라이빙 테이블 행 수 × 안쪽 탐색 비용**. 그래서 "작은 쪽을 먼저, 안쪽 조인 컬럼에 인덱스"라는 규칙이 나온다
- 옵티마이저는 통계로 행 수를 추정한다. **틀린 플랜의 대부분은 알고리즘 선택이 아니라 추정 실패**다
- `filesort` · `temporary`는 **정렬·그룹핑을 인덱스로 해결하지 못했다**는 신호다. 인덱스 컬럼 순서로 없앨 수 있는 경우가 많다

---

## 원리 — 왜 그런가

### 2-1. SQL은 "무엇을"만 적는다

`SELECT ... FROM a JOIN b ON ...` 어디에도 **"a를 먼저 읽어라", "해시 테이블을 만들어라"** 같은 말은 없다. 원하는 결과의 모양만 적혀 있다. 그 결과를 만드는 절차는 DB가 만든다.

```
SQL 텍스트
  → 파서       : 문법 검사, 구문 트리
  → 전처리기    : 테이블·컬럼 존재 확인, 권한 확인
  → 옵티마이저  : 가능한 실행 방법 여러 개를 만들고 비용을 매겨 하나를 고른다  ★
  → 실행기      : 고른 계획대로 스토리지 엔진에 페이지를 요청한다
```

★ 단계가 이 문서의 전부다. 여기서 두 가지가 따라온다.

**(1) 성능은 SQL이 아니라 플랜의 속성이다.** SQL을 한 글자도 안 바꿨는데 어제는 50ms, 오늘은 8초가 나올 수 있다. 데이터가 늘어 통계가 바뀌면 옵티마이저가 다른 선택을 하기 때문이다. "쿼리를 안 건드렸는데 갑자기 느려졌다"는 버그가 아니라 정상 동작이다.

**(2) 비용은 실측이 아니라 추정이다.** 옵티마이저는 후보 플랜을 실제로 실행해 보고 고르는 게 아니다. 통계를 보고 "이 플랜이면 페이지를 몇 번 읽겠다"를 계산한다. 계산의 입력이 틀리면 결론도 틀린다. §2-4의 주제다.

### 2-2. 조인 알고리즘은 왜 셋이나 있나

두 테이블을 붙이는 방법은 근본적으로 세 가지다. 하나로 안 되는 이유는, **각각이 잘하는 상황이 겹치지 않기** 때문이다.

**(1) Nested Loop Join.** 바깥 한 행마다 안쪽을 찾는다

```
for outer_row in A:              -- 드라이빙(outer) 테이블
    for match in B[join_key]:    -- 안쪽(inner)에서 찾기
        emit(outer_row, match)
```

비용 = **A의 행 수 × B에서 한 번 찾는 비용**.

B의 조인 컬럼에 인덱스가 있으면 "한 번 찾는 비용"이 인덱스 탐색 한 번이다. A가 10행이면 탐색 10번. **작은 결과 × 인덱스된 큰 테이블**에서 압도적이다.

인덱스가 없으면 "한 번 찾는 비용"이 B 풀 스캔이 된다. A가 10만 행이면 B 풀 스캔 10만 번이다. 사실상 죽는다. MySQL 8.0 이전에는 이 경우 **Block Nested Loop**로 완화했다. A의 행들을 조인 버퍼에 모아 두고 B를 한 번 스캔할 때 버퍼 전체와 비교하는 방식이다. B 스캔 횟수가 `A행수 / 버퍼당 행수`로 줄지만, 여전히 곱셈이다.

**(2) Hash Join.** 작은 쪽으로 해시 테이블을 만들어 둔다

```
build : 작은 쪽을 통째로 읽어 조인 키로 해시 테이블 생성 (메모리)
probe : 큰 쪽을 한 번 훑으며 해시 테이블에 던져 본다
```

비용 = **A 한 번 읽기 + B 한 번 읽기**. 곱셈이 덧셈으로 바뀐다. 인덱스가 없어도 큰 테이블끼리 붙일 수 있다.

대신 조건이 붙는다. **등치 조인(`=`)에만 쓸 수 있다.** 해시는 순서를 파괴하므로 `>` `BETWEEN` 조인에는 못 쓴다([DB 인덱스](b-tree-index.md) §2-2와 정확히 같은 이유다). 그리고 해시 테이블이 메모리에 들어가야 한다(MySQL `join_buffer_size`, PostgreSQL `work_mem`). 넘치면 양쪽을 디스크에 나눠 쓰고 조각별로 처리하는데, 이때 성능이 급격히 나빠진다.

**(3) Sort-Merge Join.** 양쪽을 정렬해 놓고 나란히 훑는다

```
양쪽을 조인 키로 정렬 → 두 커서를 동시에 전진시키며 맞는 것을 짝지음
```

정렬이 이미 돼 있으면(예: 양쪽 다 조인 키 인덱스를 순차 스캔) **정렬 비용이 0이고 메모리도 거의 안 쓴다.** 해시 테이블이 메모리에 안 들어가는 초대형 조인에서 안전한 선택이 되고, 범위 조인(`a.x < b.y`)도 처리할 수 있다.

**정리하면 이렇게 갈린다.**

| | 잘하는 상황 | 못하는 상황 |
|---|---|---|
| Nested Loop | 드라이빙 결과가 작다 + 안쪽에 인덱스 | 드라이빙이 크거나 안쪽에 인덱스 없음 |
| Hash | 큰 것 × 큰 것, 인덱스 없음, 등치 조인 | 비등치 조인, 메모리 부족 |
| Sort-Merge | 이미 정렬돼 있음, 초대형, 범위 조인 | 정렬을 새로 해야 하고 입력이 큼 |

> ⚠️ **MySQL에는 Sort-Merge Join이 없다.** 그리고 Hash Join은 8.0.18에서야 들어왔다. 그전까지 선택지는 Nested Loop 계열뿐이었다. "조인 컬럼에는 반드시 인덱스"라는 규칙이 MySQL 진영에서 유독 강하게 각인된 이유가 이것이다. PostgreSQL은 인덱스가 없어도 Hash Join으로 무난히 넘어가지만, MySQL 5.7에서는 같은 쿼리가 그냥 죽었다.

### 2-3. 드라이빙 테이블이 왜 결과를 지배하나

Nested Loop 비용이 곱셈이므로, **어느 쪽을 바깥에 두느냐가 곧 성능**이다.

```sql
-- 캠페인 3건, 그 캠페인들의 발송 이력 1천만 건
SELECT ... FROM campaign c JOIN send_history h ON h.campaign_id = c.id
WHERE c.created_at >= '2026-08-01';
```

- **campaign이 드라이빙**: 3행 × (`h.campaign_id` 인덱스 탐색) → 탐색 3번
- **send_history가 드라이빙**: 1천만 행 × (campaign 탐색) → 탐색 1천만 번

같은 SQL, 같은 결과, **비용은 백만 배 차이**다.

**규칙은 "작은 테이블을 먼저"가 아니라 "필터를 적용한 뒤 행 수가 작은 쪽을 먼저"다.** 1억 건 테이블이라도 `WHERE`로 3건이 남으면 그쪽이 드라이빙이어야 한다. 그래서 §2-4의 추정이 중요해진다. 옵티마이저가 "몇 건 남을지"를 틀리면 드라이빙 선택을 틀리고, 그러면 곱셈의 방향이 뒤집힌다.

순서를 강제하는 손잡이는 있다(MySQL `STRAIGHT_JOIN` · 옵티마이저 힌트, PostgreSQL `join_collapse_limit` · `pg_hint_plan` 확장). 다만 **힌트는 통계가 개선되면 오히려 방해가 된다.** 먼저 통계를 의심하고, 힌트는 마지막에 쓴다.

### 2-4. 옵티마이저가 틀리는 이유

플랜이 나쁠 때 "옵티마이저가 멍청하다"가 아니라 **"무엇을 잘못 알고 있었나"**를 묻는 게 맞다. 틀리는 경로는 대체로 넷이다.

**(1) 통계가 낡았다.** 가장 흔하다. 대량 적재 직후, 파티션 교체 직후에 특히 그렇다. `ANALYZE TABLE`(MySQL) / `ANALYZE`(PostgreSQL). 자동 갱신 임계치가 있지만 큰 테이블일수록 임계치에 늦게 도달한다.

**(2) 컬럼 간 상관관계를 모른다.** 옵티마이저는 조건들이 서로 독립이라고 가정하고 선택도를 곱한다.

```sql
-- 회원 1000만 행, 그중 서울 180만 행(18%). 서울 회원의 지역번호는 사실상 전부 '02'
WHERE city = '서울특별시' AND area_code = '02'

-- 옵티마이저 : 시도 17종 → 1/17, 지역번호 15종 → 1/15
--              두 조건이 독립이라 가정하고 곱한다 → 0.4% ≈ 4만 행
-- 실제       : 두 조건은 같은 조건이다. 겹쳐도 줄지 않는다 → 18% ≈ 180만 행
```

45배 과소추정이다(자릿수 감각용 계산이고, 실제 배수는 데이터 분포에 달렸다). "4만 건이면 Nested Loop가 싸다"고 판단했는데 실제로 180만 건이 쏟아지면 §2-3의 곱셈이 그대로 재앙이 된다. **컬럼 간 상관관계는 옵티마이저의 구조적 맹점**이고, 해법이 엔진마다 다르다(PostgreSQL은 `CREATE STATISTICS`로 다중 컬럼 통계를 만들 수 있고, MySQL의 히스토그램은 단일 컬럼만 다룬다).

**(3) 오차가 여러 단을 거치며 곱해진다.** 3-테이블 조인에서 1단계 추정이 10배 틀리면, 그걸 입력으로 쓰는 2단계는 이미 10배 틀린 값 위에서 계산한다. 조인 단계가 깊을수록 플랜을 신뢰하기 어려워진다.

**(4) 바인드 변수라 값을 모른다.** `WHERE status = ?` 에서 `?`가 'READY'(1%)냐 'DONE'(95%)냐에 따라 최적 플랜이 정반대인데, 플랜을 캐시해 재사용하면 한쪽에만 맞는 플랜을 양쪽에 쓴다.

> 추정과 실제를 대조하는 방법은 `EXPLAIN ANALYZE`다. 추정 행 수와 실제 행 수를 나란히 보여준다. **둘이 자릿수로 차이 나면 (1)~(4) 중 하나다.** 읽는 법은 [DB 인덱스](b-tree-index.md) §2-9.

### 2-5. `filesort` · `temporary`는 왜 생기나

인덱스는 **이미 정렬된 자료구조**다([DB 인덱스](b-tree-index.md) §2-5). 그래서 `ORDER BY`가 인덱스 순서와 맞으면 정렬 작업 자체가 없다. 인덱스를 순서대로 읽으면 그게 곧 정렬된 결과다.

맞지 않으면 DB가 결과를 모아서 **따로 정렬한다.** 이게 `Using filesort`다.

```sql
-- 인덱스: (campaign_id, sent_at)
WHERE campaign_id = 1 ORDER BY sent_at       -- 정렬 없음. 인덱스 순서 그대로
WHERE campaign_id > 1 ORDER BY sent_at       -- filesort. campaign_id별로 sent_at이 따로 정렬돼 있음
WHERE campaign_id = 1 ORDER BY status        -- filesort. 인덱스에 없는 순서
```

> `filesort`가 곧 디스크는 아니다. 정렬 버퍼 안에서 끝나면 메모리 정렬이고, 넘칠 때만 디스크 병합 정렬로 떨어진다. 이름이 오해를 부른다.

**`ORDER BY` + `LIMIT`에서 차이가 극단적이 된다.**

```sql
SELECT * FROM send_history WHERE campaign_id = 1 ORDER BY sent_at DESC LIMIT 20;
```
- 인덱스를 타면: 뒤에서부터 **20건만 읽고 끝**
- filesort면: **조건에 맞는 1천만 건을 전부 읽어 정렬한 뒤** 20건 반환

같은 `LIMIT 20`인데 하나는 20건을 읽고 하나는 1천만 건을 읽는다. **`LIMIT`이 붙은 화면이 느리면 여기부터 본다.**

`Using temporary`도 같은 구조다. `GROUP BY`가 인덱스 순서와 맞으면 스캔하면서 바로 집계할 수 있지만, 안 맞으면 **중간 결과를 임시 테이블에 쌓아 두고** 집계한다. 임시 테이블이 메모리 한도를 넘으면 디스크로 내려간다. `DISTINCT` + `ORDER BY` 조합, `UNION`(중복 제거)도 같은 경로를 탄다.

> ⚠️ MySQL 8.0부터 **`GROUP BY`의 암묵적 정렬이 사라졌다.** 예전엔 그룹핑 부산물로 정렬이 따라왔는데 이제는 아니다. 순서가 필요하면 `ORDER BY`를 명시해야 한다.

### 2-6. 서브쿼리를 왜 조인으로 바꿔 쓰라고 하나

서브쿼리는 옵티마이저가 변환에 성공하면 조인과 같은 플랜이 되고, 실패하면 재앙이 된다. 조언의 실체는 "조인이 빠르다"가 아니라 **"변환 실패 위험을 없애라"**다.

**`IN (subquery)`의 세미조인 변환**
```sql
SELECT * FROM member WHERE id IN (SELECT member_id FROM send_history WHERE ...);
```
현대 옵티마이저는 이걸 세미조인(존재하면 한 번만 매칭)으로 바꿔 조인처럼 처리한다. 변환에 실패하면 **바깥 행마다 서브쿼리를 재실행**한다(dependent subquery). 100만 행이면 100만 번이다.

**`FROM (subquery)`의 파생 테이블**
병합(merge)되면 바깥 조건이 안쪽으로 밀려 들어가 인덱스를 탄다. 병합이 안 되면 임시 테이블로 물질화되는데, **물질화된 임시 테이블에는 인덱스가 없다.** 이후 조인이 전부 풀 스캔이 된다.

**`NOT IN`의 NULL 함정.** 이건 성능이 아니라 정확성 문제다
```sql
WHERE id NOT IN (SELECT member_id FROM blacklist)   -- member_id에 NULL이 하나라도 있으면
```
결과가 항상 빈 집합이 된다. `id != NULL`이 참이 아니라 UNKNOWN이기 때문이다. **`NOT EXISTS`를 쓰면 이 문제가 없다.** 발송 제외 대상 필터처럼 "빼는 조건"에서 이게 터지면 보내면 안 될 곳에 보내는 사고가 된다. 성능 튜닝보다 먼저 봐야 하는 항목이다.

### 2-7. N+1은 애플리케이션이 손으로 짠 Nested Loop다

```
SELECT * FROM campaign WHERE ...            -- 1번, 100건
  → for each: SELECT * FROM message WHERE campaign_id = ?   -- 100번
```

구조가 §2-2(1)과 **완전히 같다.** 다른 건 하나뿐이다. 안쪽 탐색이 DB 내부의 함수 호출이 아니라 네트워크 왕복이라는 것.

```
DB 안의 Nested Loop  : 100 × 인덱스 탐색(마이크로초)     ≈ 무시 가능
애플리케이션의 N+1   : 100 × 네트워크 왕복(0.5~1ms)     ≈ 50~100ms
```

**같은 알고리즘인데 단위 비용이 1000배 비싼 곳에서 돌리고 있는 것**이 N+1의 정체다. 그래서 해법도 "루프를 없애라"가 아니라 "루프를 싼 곳(DB 안)으로 옮겨라"가 된다. fetch join, `IN` 절 묶기, 배치 사이즈. → [Spring](../../spring/di-aop-transaction-jpa.md) §2-6

### 2-8. 조인 선택지가 갈라놓는 두 엔진

| 항목 | MySQL | PostgreSQL |
|---|---|---|
| 조인 알고리즘 | Nested Loop, Hash(8.0.18+). **Sort-Merge 없음** | Nested Loop, Hash, Merge **전부** |
| 인덱스 없는 큰 조인 | 8.0 미만은 Block NL → 사실상 불가 | Hash Join으로 무난 |
| 다중 컬럼 상관관계 통계 | 없음(히스토그램은 단일 컬럼) | `CREATE STATISTICS` |
| 힌트 | 옵티마이저 힌트 내장(`STRAIGHT_JOIN` 등) | 기본 제공 없음, `pg_hint_plan` 확장 |
| 실행계획 표현 | 표 형태 | 트리 형태(노드별 비용·행 수) |

각 항목의 실전 사용법은 `mysql/` · `postgresql/`에서 이어간다.
