# 트랜잭션 · 락 · 데드락 (+ 커넥션 풀)

## 30초 요약

- **MVCC**: 읽기는 과거 스냅샷을 본다 → **읽기가 쓰기를 막지 않는다**. 일반 `SELECT`는 락을 안 잡는다
- 그런데 **쓰기끼리는 MVCC로 못 푼다** → 그래서 락이 필요하다
- **InnoDB의 락은 테이블 행이 아니라 인덱스 레코드에 걸린다.** 인덱스를 못 타는 조건으로 UPDATE하면 **락 범위가 폭발**한다 ← 데드락의 가장 흔한 원인
- **갭 락 / 넥스트키 락**: InnoDB는 REPEATABLE READ에서도 레코드 사이 빈 구간까지 잠가 팬텀을 막는다. 대신 **락 범위가 넓어져 데드락이 늘어난다**
- **데드락 = 서로가 쥔 락을 기다리는 순환 대기.** 줄이는 근본 조치는 **트랜잭션을 짧게** 하나뿐이다. 나머지는 보강이다

## 원리 — 왜 그런가

### 2-1. 트랜잭션 — ACID는 어떻게 구현되나

정의만 외우면 쓸 데가 없다. **어떻게 구현되는지**를 한 줄씩 붙일 수 있어야 한다.

| | 뜻 | InnoDB에서 어떻게 |
|---|---|---|
| **A**tomicity | 전부 되거나 전부 안 되거나 | **undo log** — 변경 전 값을 기록해 두고, 롤백하면 되돌린다 |
| **C**onsistency | 제약을 깨지 않는다 | 제약조건·트리거·애플리케이션 책임. 나머지 셋의 결과에 가깝다 |
| **I**solation | 동시 트랜잭션이 서로 간섭하지 않는다 | **MVCC + 락**. 이 페이지의 본론 |
| **D**urability | 커밋되면 장애가 나도 남는다 | **redo log (WAL)** — 데이터 파일보다 **먼저** 로그를 디스크에 쓴다 |

**WAL(Write-Ahead Logging)이 왜 필요한가**: 커밋 때마다 데이터 파일 전체를 디스크에 내리면 **랜덤 쓰기**라 느리다. 대신 "무엇을 바꿨는지"를 **순차 쓰기**인 redo log에 먼저 쓰고 커밋을 반환한다. 데이터 파일 반영은 나중에 몰아서 한다. 중간에 죽어도 redo log로 복구된다. → **순차 쓰기가 랜덤 쓰기보다 압도적으로 싸다**는 것이 여기서도 지배 원리다([DB 인덱스](../database/b-tree-index.md) §2-7과 같은 논리).

### 2-2. 격리 수준 — 왜 4단계나 있나

**격리는 공짜가 아니다.** 완벽히 격리하려면 트랜잭션을 한 줄로 세우면 되지만(SERIALIZABLE) 동시성이 죽는다. 그래서 **"어떤 이상현상까지 감수할 것인가"를 고르게 해 둔 것**이 격리 수준이다.

| 수준 | 막는 것 | 남는 문제 |
|---|---|---|
| READ UNCOMMITTED | — | **Dirty Read** — 커밋도 안 된 값을 읽음 |
| READ COMMITTED | Dirty Read | **Non-Repeatable Read** — 같은 행을 두 번 읽었는데 값이 다름 |
| **REPEATABLE READ** ← MySQL InnoDB 기본 | + Non-Repeatable Read | **Phantom Read** — 조건에 맞는 **행 수**가 달라짐 |
| SERIALIZABLE | 전부 | 동시성 최악 |

**세 이상현상의 차이를 헷갈리지 말 것:**
- Dirty Read — **커밋 안 된** 값을 봤다
- Non-Repeatable Read — **같은 행의 값**이 바뀌었다 (UPDATE 때문)
- Phantom Read — **행의 개수**가 바뀌었다 (INSERT/DELETE 때문)

> **PostgreSQL과 Oracle의 기본은 READ COMMITTED**, MySQL InnoDB는 REPEATABLE READ다. 이유는 역사적으로 MySQL의 복제(statement-based replication)가 RR을 요구했기 때문이다. **기본 격리 수준은 DB마다 다르다**는 것만 기억해도 된다.

### 2-3. MVCC — 읽기가 쓰기를 막지 않는 방법

**Multi-Version Concurrency Control.** 핵심 아이디어: **값을 덮어쓰지 않고 버전을 쌓는다.**

- 행을 UPDATE하면 이전 값이 **undo log**에 남는다 (2-1의 원자성과 같은 장치를 재활용)
- 각 행에는 **어느 트랜잭션이 마지막으로 건드렸는지**(트랜잭션 ID)가 붙어 있다
- 트랜잭션이 읽기를 시작할 때 **Read View(스냅샷)**를 뜬다 — "내가 볼 수 있는 버전은 어디까지인가"
- 읽을 때 현재 행이 내 스냅샷보다 최신이면, **undo log를 거슬러 올라가 내 시점의 버전**을 찾아 읽는다

**결과**: 읽는 쪽은 락을 잡지 않는다. 쓰는 쪽도 읽는 쪽을 기다리지 않는다. → **"읽기가 쓰기를 막지 않고, 쓰기가 읽기를 막지 않는다"**

**READ COMMITTED와 REPEATABLE READ의 차이도 여기서 나온다:**
- READ COMMITTED — **쿼리마다** 스냅샷을 새로 뜬다 → 같은 트랜잭션 안에서 두 번 읽으면 값이 다를 수 있다 (Non-Repeatable Read)
- REPEATABLE READ — **트랜잭션 시작 시점에 한 번** 뜨고 끝까지 유지 → 몇 번을 읽어도 같은 값

> **부작용 하나**: 긴 트랜잭션이 살아 있으면 그 스냅샷을 위해 **undo log를 못 지운다** → undo 영역이 계속 커진다. "긴 트랜잭션이 나쁘다"의 이유가 락만이 아니다.

### 2-4. MVCC가 있는데 왜 락이 또 필요한가

**MVCC는 읽기-쓰기 충돌만 푼다. 쓰기-쓰기 충돌은 못 푼다.**

두 트랜잭션이 같은 행을 동시에 UPDATE하려 하면, 버전을 나눠 봐도 결국 **최종 값은 하나**여야 한다. 여기서는 한쪽이 기다려야 한다 → **배타 락**.

그래서 InnoDB의 읽기는 두 종류다. **이 구분이 이 페이지에서 가장 중요한 개념이다.**

| | 무엇 | 무엇을 보나 | 락 |
|---|---|---|---|
| **Consistent Read** (스냅샷 읽기) | 일반 `SELECT` | **내 스냅샷**(과거일 수 있음) | 안 잡음 |
| **Current Read** (잠금 읽기) | `SELECT ... FOR UPDATE`, `LOCK IN SHARE MODE`, **`UPDATE`, `DELETE`** | **현재 최신 값** | 잡음 |

**`UPDATE`와 `DELETE`가 current read라는 게 핵심이다.** 과거 버전을 수정하면 갱신 손실이 나므로, 쓰기는 반드시 최신을 보고 락을 잡는다.

### 2-5. 갭 락 — RR에서 팬텀을 왜 MVCC만으로 못 막나

여기가 InnoDB 특유의 부분이다.

**일반 SELECT는 스냅샷을 보니까 팬텀이 안 보인다.** 그럼 끝난 것 아닌가? 아니다. **current read에서는 최신을 보기 때문에 팬텀이 뚫린다.**

```
T1: SELECT * FROM t WHERE age BETWEEN 10 AND 20;   -- 스냅샷: 3건
T2: INSERT INTO t VALUES (age=15);  COMMIT;
T1: UPDATE t SET x=1 WHERE age BETWEEN 10 AND 20;  -- current read: 4건이 갱신됨(!)
```
T1 입장에서 **조회할 땐 3건이었는데 갱신은 4건이 됐다.** 이게 current read로 뚫리는 팬텀이다.

**해법: 있는 레코드만 잠그는 걸로는 부족하다. "앞으로 들어올 자리"까지 잠가야 한다.**

- **레코드 락**: 존재하는 인덱스 레코드에 건다
- **갭 락(Gap Lock)**: 레코드 **사이의 빈 구간**에 건다. 그 구간에 **INSERT를 막는다**
- **넥스트키 락(Next-Key Lock)**: 레코드 락 + 그 앞 갭 락. **InnoDB RR의 기본 동작**

→ 그래서 **InnoDB는 REPEATABLE READ에서도 팬텀을 상당 부분 막는다.** 표준 격리 수준 정의와 다른 부분이라 따로 기억해 둘 만하다.

**대가**: 갭 락은 **존재하지 않는 행까지 잠그는 것**이다. 락 범위가 넓어지고, **서로 다른 트랜잭션이 겹치는 갭을 잡을 확률이 올라간다** → **데드락이 늘어난다.** (그래서 READ COMMITTED에서는 갭 락이 대부분 비활성화된다. RC로 낮추면 데드락이 줄어드는 이유가 이것.)

### 2-6. InnoDB의 락은 인덱스에 걸린다 — [DB 인덱스](../database/b-tree-index.md)과 잇는 다리

**가장 중요한 한 줄이다.**

InnoDB는 "테이블의 3번째 행"을 잠그는 게 아니라 **"인덱스의 이 레코드"**를 잠근다. 그래서:

```sql
UPDATE send_reserve SET status='SENT' WHERE receiver_phone = '010...';
-- receiver_phone에 인덱스가 없다면?
```

인덱스가 없으면 **전체를 스캔하면서 지나가는 모든 레코드에 락을 건다.** 조건에 안 맞는 행도 일단 읽어야 판단할 수 있으니까. 결과적으로 **사실상 테이블 락**이 된다.

> (정확히는 조건에 안 맞는 행의 락은 즉시 해제되지만, **잠깐이라도 잡는다**는 사실이 경합을 만든다.)

**여기서 나오는 결론 두 개:**
1. **인덱스 설계가 곧 락 설계다.** 인덱스를 잘 타면 락은 몇 건에만 걸린다. 못 타면 범위가 폭발한다
2. **인덱스 튜닝과 데드락 해소는 별개의 작업이 아니다.** 락 범위를 줄이는 가장 실질적인 수단이 인덱스이므로, 둘은 같은 문제의 양면이다

### 2-7. 데드락 — 왜 생기고 어떻게 줄이나

**정의**: 두 트랜잭션이 **서로가 쥔 락을 기다리는 순환 대기**. 기다리기만 하면 영원히 안 풀린다.

```
T1: A 락 획득 → B 락 요청 (T2가 쥠, 대기)
T2: B 락 획득 → A 락 요청 (T1이 쥠, 대기)   → 순환
```

**InnoDB는 이걸 방치하지 않는다.** 락 대기 그래프(wait-for graph)에서 **순환을 감지하면 한쪽을 즉시 롤백**시킨다. 그래서 무한 대기 대신 `Deadlock found when trying to get lock; try restarting transaction` 에러가 난다.

> **감지(deadlock detection)와 타임아웃(`innodb_lock_wait_timeout`, 기본 50초)은 다른 장치다.** 순환이 아닌 단순 대기는 타임아웃으로 끊긴다.

**확인 수단**: `SHOW ENGINE INNODB STATUS` → **`LATEST DETECTED DEADLOCK`** 섹션. 어느 트랜잭션이 어떤 락을 쥐고 무엇을 기다렸는지, **어떤 인덱스**에 걸렸는지까지 나온다.

**데드락을 줄이는 3원칙 — 성격을 구분해서 말할 것**

| 원칙 | 왜 효과가 있나 | 구체적 수단 | 성격 |
|---|---|---|---|
| **1. 트랜잭션을 짧게** | 락을 쥐고 있는 **시간**이 곧 충돌 확률이다. 시간을 줄이면 확률이 곱으로 준다 | **조회를 트랜잭션 밖으로 분리** | **근본 조치** |
| **2. 락 범위·점유량 축소** | 한 번에 잡는 행이 적을수록 겹칠 확률이 준다 | chunk 크기 축소, BATCH UPDATE | 보강 조치 |
| **3. 접근 순서 일관화** | 모두가 **같은 순서**로 락을 잡으면 순환이 물리적으로 안 생긴다 | 여러 트랜잭션이 같은 순서로 접근하게 | 구조 조치 |

> **"근본 조치"와 "보강 조치"를 구분해서 볼 것.**
> 나열하면 운 좋게 고친 것이고, 구분하면 원인을 이해한 것이다.

**추가로 알아둘 것**
- **트랜잭션 안에서 외부 API 호출** → 커넥션과 락을 쥔 채 네트워크를 기다린다. **발송 도메인에서 가장 흔한 사고**이고, 원칙 1의 가장 극단적인 위반이다
- **데드락은 완전히 없앨 수 없다.** 확률을 낮추는 것이고, 그래서 **애플리케이션에 재시도 로직**이 있어야 한다. "데드락을 0으로 만들었다"는 대체로 사실이 아니다

### 2-8. 비관적 락 vs 낙관적 락

| | 방식 | 언제 | 비용 |
|---|---|---|---|
| **비관적** | `SELECT ... FOR UPDATE` 로 **미리 잠근다** | 충돌이 잦을 때 | 락 대기·데드락 위험 |
| **낙관적** | 버전 컬럼(`@Version`)으로 **업데이트 시점에 충돌 감지** | 충돌이 드물 때 | 실패 시 **재시도 필요** |

낙관적 락은 락을 안 잡는다. `UPDATE ... WHERE id=? AND version=?` 로 갱신하고, **영향받은 행이 0이면 그 사이에 누가 바꿨다는 뜻**이라 예외를 던진다.

**`FOR UPDATE SKIP LOCKED` (MySQL 8.0+)** ← 발송 도메인에서 강력하다
```sql
SELECT * FROM send_queue WHERE status='READY' LIMIT 100 FOR UPDATE SKIP LOCKED;
```
다른 워커가 이미 잡은 행을 **기다리지 않고 건너뛴다.** 워커 N대가 같은 큐를 경합 없이 나눠 소비할 수 있다. **대량 발송 워커 설계의 정석에 가깝다.** (`NOWAIT`는 대기 대신 즉시 에러)

### 2-9. 트랜잭션 전파(Propagation) — Spring

- **`REQUIRED`** (기본): 진행 중인 트랜잭션이 있으면 참여, 없으면 생성
- **`REQUIRES_NEW`**: 항상 새 트랜잭션. 기존 건 잠시 보류
  → **실패해도 롤백되면 안 되는 것**에 쓴다. 예: **발송 실패 이력 기록** — 본 트랜잭션이 롤백돼도 "실패했다"는 기록은 남아야 한다
  → ⚠️ 함정: 커넥션을 **두 개** 쓴다. 풀 크기가 작으면 자기 자신을 기다리다 데드락 난다
- **`NESTED`**: 세이브포인트 기반 부분 롤백
- 자세한 프록시 함정은 [Spring](../spring/di-aop-transaction-jpa.md)

### 2-10. 커넥션 풀 — 왜 크다고 좋은 게 아닌가

**왜 필요한가**: TCP 3-way handshake + DB 인증은 비싸다(수~수십 ms). 쿼리 하나 실행에 그 비용을 매번 내면 손해다. 미리 만들어 두고 빌려 쓴다.

**HikariCP**(Spring Boot 기본) 핵심 설정:
- `maximumPoolSize` — 최대 커넥션 수
- `connectionTimeout` — **풀에서 커넥션을 못 빌릴 때 대기 한도**. 이걸 넘으면 예외
- `idleTimeout` / `maxLifetime` — 놀고 있는·오래된 커넥션 회수 (`maxLifetime`은 DB의 `wait_timeout`보다 짧아야 한다)

**풀 크기는 클수록 좋지 않다.** 이유:
- DB가 동시에 실제로 처리할 수 있는 양은 **코어 수와 디스크 성능**으로 정해진다
- 커넥션을 100개 열어도 코어가 8개면 **92개는 컨텍스트 스위칭 대기**다
- 오히려 컨텍스트 스위칭·락 경합이 늘어 **전체 처리량이 떨어진다**
- 경험칙(HikariCP 문서): **`코어 수 × 2 + 디스크 수`**

> **직관에 반하는 결론**: 풀을 줄였더니 처리량이 올라가는 경우가 실제로 있다. 대기열이 애플리케이션 쪽에 생기는 게 DB 안에서 서로 밟는 것보다 낫기 때문이다.

**⚠️ Virtual Thread와의 함정** ← 내 1core/1GB 환경 얘기와 직결
가상 스레드를 1만 개 띄워도 **커넥션 풀이 10개면 동시에 DB에 가는 건 10개**다. 나머지는 `connectionTimeout`을 기다리다 예외로 터진다. **스레드를 늘려서 해결되는 병목이 아니다.** → [Java](../java/jvm-gc-concurrency.md) §Virtual Thread와 같은 이야기
