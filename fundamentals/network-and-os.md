# 네트워크 · OS

## 30초 요약

- **429(Too Many Requests)와 503(Service Unavailable)은 발송 도메인의 일상**이다. 채널사 rate limit과 장애
- **타임아웃은 두 종류다**: connect(연결 수립) / **read(응답 대기)**. **read timeout을 안 걸면 스레드가 무한 대기**한다
- **멱등한 메서드**: GET/PUT/DELETE는 멱등, **POST는 아니다.** 그래서 **`Idempotency-Key`**를 붙인다
- **커넥션 풀이 필요한 이유**: TCP 3-way handshake + TLS 협상이 비싸다. 매 요청마다 내면 손해
- **프로세스 vs 스레드**: 메모리 공간 분리 여부. 컨텍스트 스위칭 비용이 Virtual Thread 이야기의 배경

---

## 원리 — 왜 그런가

### 2-1. HTTP 상태코드 — 발송 도메인에서 의미 있는 것만

| 코드 | 의미 | 발송 도메인에서 |
|---|---|---|
| 200 / 201 / 204 | 성공 / 생성됨 / 내용 없음 | — |
| **400** | 잘못된 요청 | 템플릿 형식 오류, 번호 형식 오류. **재시도해도 소용없다** |
| 401 / 403 | 인증 실패 / 권한 없음 | 채널사 API 키 만료 ← **알람 대상** |
| 404 | 없음 | — |
| **409** | 충돌 | **중복 요청**을 알릴 때 쓸 수 있다 (멱등 처리 결과) |
| **429** | **Too Many Requests** | **채널사 rate limit 초과.** 백오프 후 재시도 |
| 500 | 서버 오류 | 채널사 내부 오류. 재시도 대상 |
| **502 / 503 / 504** | 게이트웨이 오류 / 서비스 불가 / 게이트웨이 타임아웃 | **채널사 장애.** 서킷 브레이커 대상 |

**★ 재시도 판단이 여기서 갈린다** (→ [대용량 처리](../system-design/high-throughput.md) §2-5)
- **4xx = 내 잘못.** 다시 보내도 같은 결과 → **재시도 금지** (단 **429는 예외** — 시간이 지나면 풀린다)
- **5xx / 타임아웃 = 결과를 모름** → **재시도 대상**, 단 멱등성 필요

**429를 받으면 `Retry-After` 헤더를 봐야 한다.** 채널사가 "몇 초 뒤에 다시 오라"고 알려주는 경우가 있다. 이걸 무시하고 지수 백오프만 쓰면 불필요하게 늦어지거나 여전히 튕긴다.

### 2-2. 타임아웃 — 안 걸면 무슨 일이 생기나

**두 종류를 구분해야 한다.**
- **connect timeout**: TCP 연결을 맺기까지. 상대가 죽어 있으면 여기서 걸린다
- **read timeout**: 연결은 됐는데 **응답이 안 올 때**. **이게 진짜 위험한 쪽**이다

**read timeout을 안 걸면:**
1. 채널사가 응답을 안 준다 (죽었지만 연결은 살아 있음)
2. **스레드가 무한 대기한다.** 몇 시간이고 기다린다
3. 요청이 계속 들어오면 스레드가 하나씩 묶인다
4. **스레드 풀 고갈 → 전체 서비스 마비**

**→ "채널사 하나가 죽었는데 우리 서비스 전체가 멈췄다"의 가장 흔한 원인이다.**
서킷 브레이커도 소용없다 — **실패로 카운트조차 안 되니까** 서킷이 안 열린다 (→ [대용량 처리](../system-design/high-throughput.md) §2-4).

> **코드 리뷰에서 타임아웃 없는 HTTP 클라이언트는 1순위 지적 대상**이다. `RestTemplate`을 기본 생성자로 만들면 **타임아웃이 무제한**이다.

### 2-3. 멱등성 — HTTP 메서드와 발송

| 메서드 | 멱등? | 왜 |
|---|---|---|
| GET | O | 읽기만 |
| PUT | O | "이 상태로 만들어라" — 몇 번 해도 같은 상태 |
| DELETE | O | 이미 지워졌으면 여전히 지워진 상태 |
| **POST** | **X** | **"새로 만들어라"** — 부를 때마다 새로 생긴다 |

**발송 요청은 POST다.** 그래서 재시도가 곧 중복 발송이 된다.
**→ `Idempotency-Key` 헤더**: 클라이언트가 요청마다 고유 키를 만들어 보내고, 서버는 **같은 키의 요청이 이미 처리됐으면 새로 처리하지 않고 이전 결과를 돌려준다.**

(결제 API에서 표준처럼 쓰이는 패턴이다. 발송도 **돈이 나가는 도메인**이라 같은 문제를 푼다. → [대용량 처리](../system-design/high-throughput.md) §2-6)

### 2-4. TCP — 커넥션 풀이 왜 필요한가

**연결을 맺는 데 왕복이 필요하다.**
```
3-way handshake:  SYN → SYN-ACK → ACK    (왕복 1.5회)
TLS 협상 추가하면:                        (왕복 1~2회 더)
```
서버가 멀면 왕복 한 번에 수십 ms다. **요청마다 이걸 내면 실제 데이터를 보내기도 전에 100ms를 쓴다.**

**→ 그래서 연결을 재사용한다.**
- **HTTP Keep-Alive**: 응답 후에도 연결을 끊지 않고 다음 요청에 재사용
- **커넥션 풀**: 미리 만들어 두고 빌려 쓴다 (DB도, HTTP 클라이언트도 같은 원리 → [트랜잭션 · 락](../database/transaction-and-lock.md) §2-10)

**⚠️ 커넥션 풀의 함정**: 서버 쪽이 먼저 연결을 끊었는데 클라이언트가 모르고 그 커넥션을 쓰면 에러가 난다. → **`maxLifetime`을 서버의 idle timeout보다 짧게** 잡는다.

**TCP vs UDP** (한 줄 정리): TCP는 **연결·순서·재전송 보장**, UDP는 없다. 대신 UDP가 가볍다.

### 2-5. HTTPS / TLS — 개요만

1. 클라이언트가 서버 인증서를 받아 **신뢰할 수 있는지 검증**(CA 체인)
2. **비대칭키로 대칭키를 안전하게 교환**
3. 이후 통신은 **대칭키로 암호화** (비대칭은 느려서 본 통신엔 안 쓴다)

**왜 이 구조인가**: 비대칭키는 안전하지만 느리고, 대칭키는 빠르지만 키를 어떻게 전달할지가 문제다. → **키 교환만 비대칭으로, 본 통신은 대칭으로.**

### 2-6. 프로세스 vs 스레드 — Virtual Thread의 배경

| | 프로세스 | 스레드 |
|---|---|---|
| 메모리 | **독립** | **힙·코드 영역 공유**, 스택은 따로 |
| 통신 | IPC 필요 (비쌈) | 메모리 공유 (싸지만 **동기화 필요**) |
| 컨텍스트 스위칭 | 비쌈 (메모리 맵 교체) | 상대적으로 쌈 |
| 장애 격리 | **하나가 죽어도 다른 건 산다** | 하나가 죽으면 프로세스 전체 |

**컨텍스트 스위칭 비용**: 레지스터 저장·복원 + **CPU 캐시가 무효화된다**. 캐시 미스가 늘어난다.
→ **스레드를 많이 만든다고 빨라지지 않는 이유**이고, **Virtual Thread가 나온 배경**이다 (JVM 안에서 전환하니 OS 컨텍스트 스위칭이 없다 → [Java](../java/jvm-gc-concurrency.md) §2-6).
→ **커넥션 풀을 크게 잡으면 안 되는 이유**도 같다 (→ [트랜잭션 · 락](../database/transaction-and-lock.md) §2-10).

### 2-7. 동기/비동기 · 블로킹/논블로킹

**두 축이 다르다.** 헷갈리기 쉬우니 구분해서.
- **블로킹 / 논블로킹**: **호출한 쪽이 기다리는가** (제어권을 언제 돌려주는가)
- **동기 / 비동기**: **결과를 누가 처리하는가** (내가 확인하는가, 완료되면 알려주는가)

|  | 블로킹 | 논블로킹 |
|---|---|---|
| **동기** | 일반 I/O — 부르고 기다렸다 결과를 받는다 | 폴링 — 계속 "다 됐어?" 물어본다 |
| **비동기** | (드묾) | 콜백/Future — 완료되면 알려준다 |

**발송 구조 설명에 쓴다**: "발송 요청은 **접수만 하고 즉시 응답**하고, 실제 발송은 **비동기로** 큐를 통해 처리합니다."

### 2-8. 리눅스 — 장애 났을 때 뭘 보나

**명령어를 몇 개 아는지가 아니라, 장애 상황에서 어떤 순서로 좁혀 들어가는지**가 실제로 쓰이는 부분이다.

| 상황 | 명령 |
|---|---|
| CPU·메모리 확인 | `top`, `htop` |
| 디스크 용량 | `df -h`, `du -sh *` ← **디스크 full이 의외로 잦은 장애 원인** |
| 포트·연결 상태 | `ss -tnp`, `netstat -an` ← **TIME_WAIT / CLOSE_WAIT 적체 확인** |
| 로그 실시간 | `tail -f`, `grep`, `awk` |
| 프로세스 | `ps -ef`, `jps` (Java) |
| JVM 상태 | `jstat -gc`, `jmap`, `jstack` ← **스레드 덤프로 어디서 막혔는지** |

**`jstack`을 언급하면 좋다**: "응답이 멈췄을 때 **스레드 덤프를 떠서 어디서 블로킹돼 있는지** 봅니다" — §2-2의 무한 대기를 실제로 잡는 방법이다.
